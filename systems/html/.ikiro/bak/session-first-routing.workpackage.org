* Intent

Replace the =[...viva]= catch-all routing with session-first URLs:
=/daemon/:slug/session/:id=. The session becomes the URL's subject. The
current scheme encodes /where to go/ (mode type, slug, valence); the new
scheme encodes /what you're doing/ (a session). The session already knows
its mode and intent.

This is a client-only migration. The runtime/daemon API surface does not
change — the client simply navigates differently and resolves state from
the session entity instead of URL path segments.

** Motivation

- URL currently leaks registry structure (type/slug) into the address bar
- Session ID is a query param tacked on — it should be the subject
- populate.js is 146 lines of Vector-based multi-branch routing that
  reduces to ~30 lines when the URL just says "which session"
- url.js parse/serialize dance goes away entirely
- Session resumption becomes free — navigate to a session URL, load
  existing buffers
- Mobile deep links point at sessions, not registry paths

** Design Constraints

- Runtime API unchanged. No new server endpoints required beyond what the
  buffer/intent migration already provides.
- Daemon lifecycle (daemon.js) — refactor is deferred but the entity
  renames (valence → intent, product → buffer) from the buffer-intent
  migration will already be in place when this work starts.
- SvelteKit adapter-static (SPA) — all routes still fall back to 200.html.
  The route structure is purely for SvelteKit's client-side router.

** Navigation flow

1. afterNavigate fires → parse(terminal, url) extracts perspective + session seed
2. $perspective atom change triggers populate(terminal)
3. populate uses Vector routing to match URL → resolve daemon/mode/valence
4. Middleware chain: find daemon → find mode → find valence → find/create session
5. Branch: BUFFERED valence → push buffer, PRODUCTIVE → set up stall.withPull()

** Problems

- Vector routing in populate.js is powerful but overkill for 3 URL patterns
- URL segments couple to registry structure — renaming a mode type breaks URLs
- Session is secondary (query param), but it's the actual state
- No session resumption — navigating to a URL always starts fresh
- $perspective atom and url.js parse/serialize add indirection

* Target State

** URL scheme

#+begin_src
/                                  login
/daemon/:slug                      daemon landing (navigation, session list)
/daemon/:slug/session/:id          active session
#+end_src

Session ID is the URL subject. UUID v7 — long but functional, carries
temporal ordering.

** Route structure

#+begin_src
routes/
  +page.svelte                     login (unchanged)
  +layout.svelte                   auth guard (unchanged)
  +layout.js                       lighthouse lifecycle (unchanged)
  daemon/
    [slug]/
      +layout.svelte               daemon context provider
      +page.svelte                 daemon landing
      session/
        [id]/
          +page.svelte             session view (terminal + stream + modeline)
          Frame.svelte             dynamic view rendering (moved from [...viva])
          Modeline.svelte          status line (moved, updated)
          phases/
            Stream.svelte          buffer queue (moved, updated)
#+end_src

** Navigation flow

1. SvelteKit route params give daemon slug + session ID directly
2. Daemon layout resolves daemon from slug, provides via Svelte context
3. Session page fetches session → resolves mode + intent from session
4. Three paths based on session state:
   - Selfevident mode (no intent): create buffer ad hoc
   - Selfevident intent: create buffer from intent.data
   - Applicative intent: stall.withPull() → call emitter via intent.data.mount
5. For existing sessions: load pending/active buffers before generating new

** Populate rewrite

#+begin_src javascript
export async function populate(terminal, daemon, sessionId) {
  const session = await daemon.entities.session.findOne({ id: sessionId });
  terminal.session = session;

  const mode = await daemon.entities.mode.findOne({ id: session.mode });
  terminal.mode = mode;

  if (session.intent) {
    const intent = await daemon.entities.intent.findOne({ id: session.intent });
    terminal.intent = intent;

    if (intent.type === "APPLICATIVE") {
      terminal.stall.withPull(async () => {
        const buffers = await mode.call(intent.data.mount, {
          ...intent.data.mask,
          scope: { session: session.id },
        });
        return buffers.map(pojo => {
          const viewMode = daemon.entities.mode.findOneLocal({ id: pojo.mode });
          return Buffer.hydrate(pojo, viewMode, terminal);
        });
      });
    } else {
      const buffer = Buffer.hydrate(
        { data: intent.data, mode: mode.id },
        mode, terminal,
      );
      terminal.stall.push(buffer);
    }
  } else {
    const buffer = Buffer.hydrate({ data: {}, mode: mode.id }, mode, terminal);
    terminal.stall.push(buffer);
  }

  terminal.stall.$status.set("IDLE");
}
#+end_src

~30 lines vs 146. No Vector routing, no URL parsing, no multi-branch
matching.

* Session Creation

The URL requires a session ID, so sessions must be created before
navigation.

** Daemon landing page

=/daemon/:slug= shows:
1. Available modes (SELFEVIDENT) — click to start new session
2. Available intents (grouped by mode) — click to start new session
3. Active sessions — click to resume

** Creation flow

#+begin_src javascript
async function startMode(mode, daemon) {
  const session = await daemon.entities.session.create({
    mode: mode.id,
  });
  goto(`/daemon/${daemon.slug}/session/${session.id}`);
}

async function startIntent(intent, daemon) {
  const session = await daemon.entities.session.create({
    mode: intent.mode.id,
    intent: intent.id,
  });
  goto(`/daemon/${daemon.slug}/session/${session.id}`);
}

function resumeSession(session, daemon) {
  goto(`/daemon/${daemon.slug}/session/${session.id}`);
}
#+end_src

Session creation is a single INSERT — latency is negligible.

** Post-login redirect

=/daemon/eva=. If multiple, show daemon picker or use env var default.

* Open Questions

** /viva prefix

Current URLs start with =/viva=. New URLs start with =/daemon=. Should we
keep a prefix? =/viva/daemon/:slug/session/:id= vs =/daemon/:slug/session/:id=.
No functional impact — purely aesthetic/organizational.

** Session cleanup

Sessions accumulate. Options:
- Automatic: abandon after N hours of inactivity (server-side cron or TTL)
- Manual: user deletes from daemon landing
- Lazy: mark as CLOSED, clean up on next daemon landing load
- None: let them accumulate (DB is cheap)

** $phase survival

Currently STREAM/CHAT/FEED — only STREAM implemented. Should phase be:
- Removed entirely (only STREAM exists)
- Kept as client-only Terminal state
- Moved to session entity (persisted per-session phase)

** Multiple daemons

Current system supports multiple daemons. Daemon landing at =/daemon/:slug=
works per-daemon. But is there a cross-daemon view? A "home" page showing
all daemons? Or is single-daemon the expected norm?

** Navtree placement

Currently a popup from the modeline. In the new scheme:
- Daemon landing IS the navtree (modes/intents/sessions)
- Do we keep a navtree popup in the session view for quick switching?
- Or does the user navigate back to =/daemon/:slug= to switch?

* Dependencies

This work depends on the buffer-intent migration (=.ikiro/buffer-intent-migration.workpackage.org=)
being complete. Specifically:
- Session entity must have mode + intent references
- Intent entity must exist (was Valence)
- Buffer entity must be the persisted unit (was Product)
- Client entities must already be renamed (valence → intent, product → buffer)
- Mode trait names must be updated (SELFEVIDENT, INTENTIONAL, EMITTER)
