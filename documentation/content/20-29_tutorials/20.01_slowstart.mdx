The README quickstart is a "Hello World" in five commands. This page walks the same five
steps slowly: what each command touches, which variable backs it, what the default is, and
where you can diverge from it. Every walkthrough below was run on a clean Ubuntu 24.04
container; `~` stands for the home it ran in.

## 0 — install

**control**

```sh
# debian/ubuntu: apt-get update && apt-get install -y curl ca-certificates unzip git sqlite3
curl -fsSL https://deno.land/install.sh | sh -s -- -y   # -y persists PATH in your rc
export PATH="$HOME/.deno/bin:$PATH"                     # this shell only
git clone https://github.com/vivalence/vivalence.git
cd vivalence
deno task embed                                         # dependencies, then the `viva` link
```

Deno 2.7+ is the only prerequisite; the repo carries everything else. No compiler is needed.
`deno task embed` fetches the workspace and links the CLI: `~/.deno/bin/viva` points at the
checkout.

**environment** — `VIVA_REPOSITORY_MOUNT`, written by the installer into
`~/.config/viva/env`. Every `viva` sources that file first, so the CLI knows its repo from
anywhere and your shell rc stays untouched.

**walkthrough**

```sh
$ cat ~/.config/viva/env
export VIVA_REPOSITORY_MOUNT="/home/you/vivalence"

$ viva --help
viva · 25 commands

every command takes
  --json  print the command's output as JSON
  --help  this listing
```

`viva --help` exiting 0 proves the link; the ledger itself is step 1. One thing rides along
invisibly: the launcher exports `VIVA_PROCESS_ID`, the pid of the shell that invoked it. That
id is what later lets each terminal hold its own instance
([step 4](#4--viva-instanceuse--install--lighthouse)).

## 1 — `viva ledger/install`

**control**

```sh
viva ledger/install [path]
```

Creates the **ledger** — the one directory Vivalence owns on your machine. Everything the
system remembers between runs lives under it: its recipe and environment, the registry of
tapped packages, a home for instances, plus locks, logs, and sessions.

**environment** — `VIVA_LEDGER_MOUNT`. Bare, the command opens a form and persists your choice
into `~/.config/viva/env`. An explicit `[path]` skips the form and skips persisting — for
scripts, docker, CI; a path other than `~/.viva` then needs `export VIVA_LEDGER_MOUNT=<path>`.

**default** — `~/.viva`.

**walkthrough**

```sh
$ viva ledger/install ~/.viva
mount       ~/.viva
persisted   false
ledger      ~/.viva
scaffolded  locks · logs · registry · instances · sessions
commons     ~/vivalence/commons
recipe      ~/.viva/ledger.viva.json
env         ~/.viva/.env
fill        SECRET_VIVA_JWT · SECRET_VIVA_ANTHROPIC_API_KEY · …

$ ls -a ~/.viva
.env               the machine's environment file, scaffolded from the recipe's schema
environment.json   that schema
ledger.viva.json   the ledger recipe: runtime, lighthouse, datamap, hallucinators, clients
instances.json     known instances on this machine
instances/         cloned instances land here
registry.json      tapped packages; the checkout's commons/ is already in it
registry/          remote packages clone here
locks/             what is running
logs/              per-instance streams
sessions/          per-shell selections

$ cat ~/.viva/.env

# Scheme and authority the runtime is reachable at. Every address below derives from it.
VIVA_RUNTIME_ORIGIN="http://localhost:2501"
# Scheme and authority the anima browser client is reachable at.

…

# Signing secret. Minted by viva instance/install when blank, never by ledger/install; …
# SECRET_VIVA_JWT=""
# Machine-wide Anthropic key. A key left blank leaves its hallucinator dormant.
# SECRET_VIVA_ANTHROPIC_API_KEY=""
# Machine-wide OpenRouter key.
# SECRET_VIVA_OPENROUTER_API_KEY=""

$ viva ledger/doctor
homes
  ledger     ~/.viva
  store      ~/.viva/registry
  instances  ~/.viva/instances
  record     ~/.viva/registry.json

recipe
  path      ~/.viva/ledger.viva.json
  slots     environment · runtime · lighthouse · datamap · hallucinators · clients
…
instances    —

  key                         value                         stratum
  VIVA_RUNTIME_ORIGIN         http://localhost:2501         ledger
  VIVA_CLIENT_ANIMA_ORIGIN    http://localhost:1794         ledger
```

The ledger's `.env` is where a machine keeps what every instance shares: the two origins (the
ports) and the provider keys. An instance reads them from here at stratum `ledger`; it only
writes into its own `.env` what the ledger does not hold (step 4). `ledger.viva.json` is yours
to edit: its `lighthouse.traits` say how a visitor gets in, its `hallucinators` which models
load.

Machine state, never git-managed at the top level — its *children* are the git units.
`viva ledger/doctor` is the report card: the homes, the recipe, the records, then every
environment variable with the stratum that won it. What the packages *supply* is
`viva registry/doctor`'s (step 2). [[12.02_anatomy-of-the-ledger]] is the deep anatomy.

## 2 — `viva registry/tap`

**control**

```sh
viva registry/tap <source: path | git url> [target: path]
viva registry/untap <owner | slug | mount>
```

Adds a **package** to the registry. Packages are modes whose job is to carry other modes:
datasets, domains, services, instance recipes. A local path is recorded in place; a git
URL is cloned into the ledger's `registry/` — or into `[target]`. Either way the package is
recorded and its modes can be used throughout your system.

**environment** — `VIVA_REGISTRY_MOUNT` moves the store.

**default** — the store is `<ledger>/registry/`. `ledger/install` already recorded the repo's
own package: `@commons/package/commons` — the standard library. `viva registry/doctor` reads
the record against the store and lists what every tap supplies.

**walkthrough**

```sh
$ viva registry/doctor
record
  path     ~/.viva/registry.json
  tapped   1
  stale    —
  entries
    owner     slug     mount                 root                  remote
    @commons  commons  ~/vivalence/commons   ~/vivalence/commons   —

store
  path      ~/.viva/registry
  resident  —
  untapped  —

integrity  —
pensieve
  modules  20
  types    13
  owners   1

packages
  owner     mount                 root                  modules
  @commons  ~/vivalence/commons   ~/vivalence/commons   20
    types
      package       commons
      bot           personal
      dashboard     dataspace
      datamap       libsql
      demo          hello-world
      editor        darkroom
      hallucinator  anthropic · deepgram · elevenlabs · openrouter
      harness       runtime
      instance      hello-world · playground
      ledger        ledger
      publisher     blog
      reader        reader
      service       nlp-stanza · ocr-tesseract · reader · whatsapp

$ viva registry/tap https://github.com/vivalence/registry-education
owner   @education
root    ~/.viva/registry/registry-education

$ cat ~/.viva/registry.json
{
  "@commons": {
    "slug": "commons",
    "mount": "/home/you/vivalence/commons"
  },
  "@education": {
    "slug": "education",
    "mount": "./registry/registry-education",
    "remote": "https://github.com/vivalence/registry-education"
  }
}

$ ls ~/.viva/registry/registry-education
README.md  bak  domain  education.viva.js  instances  modes  tests  topographies  topologies
```

The record is keyed by the owner each package declares. The checkout path is absolute. The
remote one was cloned beside the record, so its `mount` is relative to `registry.json`, and its
`remote` is kept so it can be cloned again. `untap @education` removes the entry and keeps the
working copy.

`integrity` names every file a package holds that cannot register. The registry reads every
`*.viva.js` and `*.viva.json` under a package as a module: a file with that ending and no
manifest is listed there as `no manifest.slug — unfit to register`.

What a package looks like — `@commons/package/commons`, the standard library:

```
commons/
  package.viva.js            manifest: { owner: "@commons", type: "package", slug: "commons" }
  datamaps/libsql/           database provider
  ledger/                    the canonical ledger recipe
  hallucinators/anthropic/   AI providers
  hallucinators/elevenlabs/
  services/nlp/
  instances/hello-world/     runnable instance recipes
  instances/playground/
  playground/                demo modes — the development rigs
  fixtures/                  test data and the language-learning fixture corpus
```

Every leaf is a mode with its own `*.viva.js`; the package is the one module at the root
that claims the tree. A mode is referenced by owner/type/slug — `@commons/instance/hello-world`
— where the type comes from the manifest, never the directory name.

## 3 — `viva instance/clone`

**control**

```sh
viva instance/clone [source: slug | @owner/instance/slug | path] [target: path]
                    [--slug=<name>] [--install]
```

An **instance** is one runnable system: a runtime, its daemons, its clients — declared in
one directory. `clone` copies the recipe out of the registry. A full copy, yours to edit and
version: the declaration, and once running a `mountpoint/` with databases and bundles. Two
clones of the same recipe are two copies, not two moods of one.

**environment** — `VIVA_INSTANCE_MOUNT` names the one instance a runtime renders — and a
`*_MOUNT` is always a **path, never a slug**. Slug to path is the shell commands' job.

**default** — the copy lands in `<ledger>/instances/<slug>` and is recorded in
`instances.json`. The slug is the recipe's; `--slug=<name>` names the copy yourself. The
clone is selected for this shell; `--install` runs step 4 on it.

**walkthrough**

```sh
$ viva instance/clone @commons/instance/hello-world
source  @commons/instance/hello-world
slug    hello-world
from    ~/vivalence/commons/instances/hello-world
target  ~/.viva/instances/hello-world
selected
  selected  ~/.viva/instances/hello-world
  stratum   session
  mount     ~/.viva/instances/hello-world
  record    ~/.viva/sessions/95964.json

$ ls ~/.viva/instances/hello-world
README.md  app  docker-compose.yml  harness.js  instance.viva.json  mode.viva.js  page
tests  tools

$ cat ~/.viva/instances.json
{
  "hello-world": {
    "createdAt": "…",
    "mount": "/home/you/.viva/instances/hello-world",
    "updatedAt": "…"
  }
}

$ viva instance/clone hello --slug=second
source  @commons/instance/hello-world
slug    second
from    ~/vivalence/commons/instances/hello-world
target  ~/.viva/instances/second
# and `second` is now this shell's selection
```

A bare slug resolves against the registry, and the `source` line prints what it resolved to.
In a terminal, a slug that matches nothing or several opens a picker. Note what the instance
directory does *not* contain: its own location. You needed its location to read its files, so
storing it inside would be circular. Location is the ledger's knowledge.

## 4 — `viva instance/use` · `install` · `lighthouse`

**control**

```sh
viva instance/use [slug] [--ledger]
viva instance/install [username password]
viva instance/lighthouse/signup <username> [password]
viva instance/lighthouse/signin <username> [password]
viva instance/lighthouse/password <username> <password>
```

`use` selects one instance out of the set for this shell. `install` completes one boot
lifecycle: it writes the instance's `.env`, asking in a form for what cannot be deduced —
mostly service keys; it runs the instance once; it asks you to create the first user; it
stops the instance again. The `lighthouse` commands talk to a running instance (step 5).

**environment** — the selection `use` writes ends up as `VIVA_INSTANCE_MOUNT`, resolved
to a path. Per shell it lives in `<ledger>/sessions/<shell-pid>.json` (the
`VIVA_PROCESS_ID` from step 0); with `--ledger` it is one line in `<ledger>/.env`, the
machine's own environment file.

**default** — nothing is selected. Every instance command resolves its target the same way,
strongest voice first:

```
flag      --instance=<slug|path>              this invocation only
cwd       standing inside an instance directory
os        an exported VIVA_INSTANCE_MOUNT
session   viva instance/use <slug>            this shell
ledger    viva instance/use <slug> --ledger   this machine
```

`--instance` targets one command, the directory you stand in targets implicitly, `use`
makes a shell decision, `--ledger` a machine decision. Two terminals can `use` two instances
and work them in parallel. Bare `viva instance/use` prints the current selection and which
voice won it. The full seven-strata ladder — these plus the instance's own files — is
[[12.02_anatomy-of-the-ledger]].

**walkthrough**

```sh
$ viva instance/use hello-world          # step 3's last clone took the selection; take it back
selected  ~/.viva/instances/hello-world
stratum   session
mount     ~/.viva/instances/hello-world
record    ~/.viva/sessions/95964.json

$ viva instance/install you changeme
# the same as the form, without it: write .env, boot, sign the admin up, stop
mount       ~/.viva/instances/hello-world
lighthouse  booted
signup
  status     SUCCESS
  user
    id      01a218e0-45aa-7391-aa17-84c0347f88f9
    slug    you

$ cat ~/.viva/instances/hello-world/.env
## keys
# Signing secret. Minted by viva instance/install when blank, never by ledger/install; …
SECRET_VIVA_JWT="P5BP…"
# Machine-wide Anthropic key. A key left blank leaves its hallucinator dormant.
# SECRET_VIVA_ANTHROPIC_API_KEY=""

$ viva instance/doctor
mount       ~/.viva/instances/hello-world
…
env
  !  key                             value                   stratum  reason
  !  PUBLIC_VIVA_RUNTIME_REMOTE      http://localhost:2501/  ledger   —
  —  SECRET_VIVA_ANTHROPIC_API_KEY   —                       —        —
  !  SECRET_VIVA_JWT                 ***                     instan   —
  !  VIVA_CLIENT_ANIMA_ORIGIN        http://localhost:1794   ledger   —
  !  VIVA_RUNTIME_ORIGIN             http://localhost:2501   ledger   —

problems    —
faults      —
dormant
  runtime.hallucinators[0]  @commons/hallucinator/anthropic — empty key
lock        —
```

Two environment files and one schema. The ledger's `.env` holds what the machine shares; the
instance's `.env` — never committed — is written with only the keys nothing else holds yet.
Here that is one: the signing secret, minted by `install` itself. The addresses are read from
the ledger, as the `stratum` column says. A key you write into the instance's `.env` wins over
the ledger's for that instance — that is how a second instance gets its own ports. Defaults
reference each other with `${VAR}`, expanded on read, so every address derives from one origin
and moving to a real host is a single edit. A `SECRET_*` key is a secret wherever it is written.

`instance/doctor` afterwards: every key with its value and the stratum that won it, plus
`faults`, what the schematic refused (an address that is not a URL), and `dormant`,
hallucinators dropped because their key is blank. Put a provider key into `~/.viva/.env` and
the matching line leaves `dormant`.

**who gets in** is the lighthouse's `traits`, in `ledger.viva.json`:

| traits | `signup <name>` | `signup <name> <password>` | `signin <name>` |
| --- | --- | --- | --- |
| `JOINABLE` | asks for the password in a form | signs up | refused: needs the password |
| `AUTOSIGNUP` | signs up, no password | signs up, sets it | signs in a passwordless name |

Both commands print `status` and `user`; `--json` adds the tokens. A name that holds a password
is never entered by name alone.

## 5 — `viva instance/up` · `start`

**control**

```sh
viva instance/up [runtime | anima]       # attached: output on this terminal
viva instance/down
viva instance/start [runtime | anima]    # detached: logged under <ledger>/logs/<slug>/
viva instance/stop
viva instance/delete [slug] [--force]
```

Boots the instance's children as supervised processes and records them in the instance's one
lock, `<ledger>/locks/<slug>.lock`. Naming one child runs just that one. `delete` is the undo
of steps 3 and 4: the record, dead locks, logs, and every shell session that had selected it
go, and so does the directory when it sits under `<ledger>/instances/` — a directory you
tapped from elsewhere stays. It refuses while a child is running and asks before acting unless
`--force` is given.

**walkthrough**

```sh
$ viva instance/start
status      started
instance    hello-world
supervisor  1962
processes
  process  pid   serve                   status  exit
  runtime  2000  http://localhost:2501/  ALIVE   —
  anima    2001  http://localhost:1794/  ALIVE   —

logs        ~/.viva/logs/hello-world
next        viva instance/stop

$ curl -s localhost:2501/beacon/status
{"timestamp":"…","code":"RUNNING"}

$ ls ~/.viva/locks ~/.viva/logs/hello-world
~/.viva/locks:
hello-world.lock

~/.viva/logs/hello-world:
anima.out.log  runtime.out.log

$ viva instance/lighthouse/signup second changeme
status  SUCCESS
user
  id      01a218e0-73c0-703a-8c2d-321c2ad459ac
  slug    second

$ viva instance/lighthouse/signin second wrong
[ERROR] /instance/lighthouse/signin: Unauthorized — Invalid username or password
  @ /lighthouse/login

$ viva instance/stop
status      stopped
instance    hello-world
```

`ALIVE` in the table means the process is up; the runtime answers once `/beacon/status` says
`RUNNING`, some seconds later. For `hello-world` that is two processes:

| process   | what                    | where                   |
| --------- | ----------------------- | ----------------------- |
| `runtime` | daemons, entities, HTTP | `http://localhost:2501` |
| `anima`   | the browser client      | `http://localhost:1794` |

The runtime hosts everything as one path tree under one origin: itself under
`/runtime/<slug>` (`/runtime/runtime` by default), daemons under `/daemon/<slug>`, each
host's modes under `<host>/mode/<type>/<slug>`, attached services like `nlp-stanza` under
`/attached/process/…`, identity under `/lighthouse/…`.

Open **http://localhost:1794**, log in with the account from step 4, and you are inside:
the client attaches to the daemons and renders their modes.

On a server, the origins bind and the remote is what a browser reaches. In `~/.viva/.env`:

```sh
VIVA_RUNTIME_ORIGIN="http://0.0.0.0:2501"
VIVA_CLIENT_ANIMA_ORIGIN="http://0.0.0.0:1794"
PUBLIC_VIVA_RUNTIME_REMOTE="http://<the server's address>:2501/"
```

## 6 — or from the published images

Every push builds four images, tag `alpine` and the commit's short hash, pulled without a
login: `registry.vivalence.org/beef/viva/vivalence/{viva,runtime,anima,documentation}`. They
are `arm64` only. An instance folder can be a compose project over them: `runtime` with the
packages tapped at build, `anima` from its own image, the folder mounted read-only as the
instance. The `@droneaid` package ships one:

```sh
git clone https://github.com/vivalence/registry-droneaid.git
cd registry-droneaid/instances/droneaid
cp .env.example .env            # SECRET_VIVA_JWT (openssl rand -base64 24), a provider key
docker compose build runtime
docker compose up -d
curl -s localhost:2501/beacon/status
```

No `viva` on the host is needed. The runtime turns healthy in about 25 seconds, anima answers
after it on `:1794`. The database lives in the compose volume `mountpoint`.
