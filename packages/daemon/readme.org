* Comprehensive System Architecture and Module Documentation

** Overview
The system is built around a central daemon that manages multiple runtimes, each corresponding to a specific corpus (e.g., a language pair for translation). The architecture is highly modular, with clear separation between core system logic and runtime-specific modules. It uses Supabase for data persistence and real-time capabilities, and incorporates an event-driven design with scoped event buses for inter-module communication.

The system is primarily designed for language-related applications, featuring complex ontologies for linguistic concepts and interactive game modules for language learning.

** System Components

*** Daemon
The core process that orchestrates the entire system lifecycle.

Responsibilities:
- Manage the boot, activation, and runtime phases of the system
- Create and manage multiple runtimes
- Handle graceful system shutdown

*** Runtime
An isolated environment for a specific corpus and its associated components.

Components:
- Router (scoped)
- Event Bus (scoped)
- Supabase Client
- Corpus Module
- Ontology Module
- Game Modules
- Strategy Modules 

*** Router
Handles HTTP routing within a runtime, with each runtime having its own scoped router.

Responsibilities:
- Define and manage routes for the corpus and its components
- Handle incoming HTTP requests and direct them to appropriate handlers

*** Event Bus
Manages event-driven communication within a runtime, with each runtime having its own scoped event bus.

Responsibilities:
- Allow components to emit and listen to events within their scope
- Facilitate inter-module communication

*** Corpus Module
Represents a specific dataset or domain within the system (e.g., a language pair for translation).

Responsibilities:
- Define corpus-specific data structures and operations
- Provide API endpoints for corpus operations
- Set up event hooks for corpus-related events

*** Ontology Module
Defines the structure and relationships within a corpus, with a focus on linguistic concepts.

Responsibilities:
- Define schemas and relationships for linguistic data
- Provide methods for linguistic operations (e.g., autocomplete, prediction, validation)
- Set up API endpoints for ontology-related operations

*** Game Modules
Interactive components associated with a corpus, designed for language learning.

Types:
- Conjugations
- Flashcards
- Translations

Responsibilities:
- Provide interactive language learning experiences
- Define game-specific API endpoints
- Implement UI components for game interactions

*** Database (Supabase)
Provides data persistence and real-time capabilities.

Responsibilities:
- Store corpus, ontology, and game data
- Support real-time data synchronization
- Handle authentication and authorization

** Component Interactions

1. Daemon Initialization:
   - The daemon starts and begins the boot phase.

2. Server Initialization:
   - Core server components are set up, including middleware for auth, CORS, and local context.

3. Runtime Creation:
   - For each configured corpus:
     a. A new runtime is created with a scoped router and event bus.
     b. A Supabase admin client is initialized for the runtime.

4. Module Loading and Initialization:
   - Corpus and Ontology modules are dynamically loaded.
   - Each module is booted with access to the runtime's scoped resources.

5. Game Module Initialization:
   - Game modules are loaded and initialized within each runtime.

6. Activation Phase:
   - Loaded modules are activated, setting up necessary data structures and connections.

7. Runtime Phase:
   - The server starts listening for incoming requests.
   - Requests are routed to the appropriate runtime and handler based on the URL path.
   - Modules communicate via the scoped event bus as needed.

8. Shutdown:
   - On receiving a SIGINT signal, the daemon initiates a graceful shutdown of all components.

** Runtime Loading and Module Installation

1. Dynamic Module Discovery:
   - The system scans for available corpus modules using the viva/module-loader.js.

2. Runtime Initialization:
   - For each discovered corpus:
     a. A new runtime object is created.
     b. Scoped router and event bus are assigned to the runtime.
     c. A Supabase admin client is created for the runtime.

3. Module Loading:
   - The corresponding ontology module is loaded for each corpus.
   - Both corpus and ontology modules are booted with access to runtime resources.

4. Module Boot Process:
   - Each module's boot method is called, allowing it to:
     a. Set up necessary data structures.
     b. Install routes on the runtime's router.
     c. Set up event listeners on the scoped event bus.
     d. Perform any necessary database operations or migrations.

5. Game Module Integration:
   - Game modules associated with the corpus are loaded and initialized.
   - Each game sets up its own routes, API endpoints, and UI components.

6. Activation:
   - After all modules are loaded, an activation phase allows for any final setup or cross-module interactions.

This architecture allows for a highly extensible and customizable system, where new corpora, ontologies, and games can be added as modules without modifying the core system logic. The use of scoped routers and event buses for each runtime provides isolation and flexibility, while the modular structure facilitates easy maintenance and updates.
