#+TITLE: Cortex — Hallucinator Orchestration & Mode Hallucination Interface
#+AUTHOR: Vivalence
#+DATE: 2026-03-19

* Intent

The cortex is the daemon-level orchestrator for all generative AI/ML
interactions. Hallucinator services expose their faculties to the cortex.
The cortex resolves providers by tune, constructs harness Vectors per mode trait,
and compiles them to both callable objects and HTTP apertures.

Modes never touch hallucinators directly. Modes interact with a harness — a
Vector instance constructed by the cortex, carrying middleware, branches,
and effects for each available faculty. The harness compiles via shape.object for
server-side use, is attached to the Modes aperture for http exposure, and replicated on the
client-side for consumption in the Modes View.

This touches: typology (primitives, entities), registry (hallucinator services,
mode traits), runtime (cortex composition, trait system, daemon lifecycle),
and client (harness consumption, trait-specific UI).

* Vocabulary (Settled)

| Term | Definition |
|------+------------|
| cortex | Daemon-level orchestrator. Resolves providers, holds tunes, constructs harnesses. |
| faculty | What a hallucinator can do. A capability contract with type, channels, tune, and a via object. |
| channels | I/O contract on a faculty: ={in, out}=. Maps 1:1 to Part types. |
| via | Delivery object on a faculty: ={render?, stream?}=. Presence of method = support. Declares AND implements delivery. |
| harness | A Vector instance constructed by the cortex. Branches per faculty type, effects per delivery avenue. |
| thread | A head turn and its parent chain. Not an entity — a pointer into the turn graph. |
| turn | Persistence primitive. Has parent/children (DAG), role, parts, meta. |
| part | Typed content atom within a turn. Discriminated by type string (= channel name). |
| packet | Delta event in a stream: turn.open, part.open, part.delta, part.close, turn.close. |
| tune | Resolution vector: [cost, quality, speed], each 0-1. |
| tier | Named preset tune. frugal, balanced, capable, unleashed. |
| render | Delivery avenue. Returns sealed turn. |
| stream | Delivery avenue. Returns async iterable of packets. |
| accumulate | Stream→render bridge. Reduces packets into a sealed turn. |

* Design Decisions (Settled)

1. All AI interaction is turns and parts. Faculties, channels, streaming —
   all reduce to turns containing typed parts.

2. A faculty declares: type, channels {in, out}, tune, context limit,
   and a via object {render?, stream?} implementing delivery.

3. Hallucinator services expose arrays of faculties. The cortex composes
   them into a routing table indexed by faculty type and tune.

4. Model identity is implementation detail. The cortex never sees model
   names. It sees faculties. The hallucinator internally maps faculty
   to model.

5. Conversation and action are the same mechanism. The harness can have
   =turn= (one exchange) and =resolve= (auto-loop on tool_use) as
   patterns built in middleware. No separate action faculty.

6. The harness is a Vector. cortex.harness(types) builds the mechanical
   wiring: branch per faculty type, effect per via. Shape compilers
   produce server/client/tool interfaces. Traits decorate with middleware.

7. System prompt is a middleware concern, not structural. The harness
   prepends it at call time. It lives outside the turn graph unless
   explicitly persisted as a turn.

8. Traits determine what harness branches a mode gets:
   - CHAOSMONKEY: daemon has a cortex (base trait, already exists)
   - LANGUAGED: mode gets conversation harness with personality
   - AGENTIC: mode gets action harness with auto-resolve

9. Turn is the sole persistence primitive. Thread is not an entity —
   it's a head turn and its parent chain. The turn graph is general-purpose,
   not LLM-specific.

10. Tune resolution: filter available faculties by =!!faculty.via[v]=,
    then nearest-neighbor in 3-space. Tiers are named presets.

11. Stream is the fundamental delivery. Any stream can be accumulated into
    a render via the accumulator. Services should implement stream where
    possible; render can be derived by draining the stream.

12. One call to the cortex = one provider. If a mode needs text + audio +
    image, that's three calls. The mode composes results.

13. The cortex builds mechanical wiring (resolve + dispatch). Traits add
    the domain middleware (tune, system prompt, history). Branch-level
    middleware for conversation-specific concerns (history load/save).

* Primitives

** Turn (Persistence Entity)

#+begin_src javascript
Turn {
  id
  parent    → Turn (nullable)     // m:1
  children  → Turn[]              // 1:m, mappedBy parent
  role      string                // open, not limited to LLM roles
  parts     JSON                  // Part[]
  meta      JSON (nullable)       // usage, stop, latency — whatever the producer wants
  createdAt
}
#+end_src

Turn is the one primitive. The graph is a DAG via parent pointers.

A "thread" is a head turn and its ancestry — not an entity. Stored as
a reference on session, mode, or client state. Thread boundaries are
wherever the consumer draws them.

The turn graph does not know about LLMs, system prompts, or faculties.
It is a general-purpose content DAG. Roles are open strings.

** Part (Core Channels)

#+begin_src javascript
{ type: 'text', text }
{ type: 'image', data, media }
{ type: 'audio', data, media }
{ type: 'video', data, media }
{ type: 'document', data, media }
{ type: 'object', data, schema }
{ type: 'tool_use', id, name, input }
{ type: 'tool_result', id, output }
{ type: 'thinking', text }
#+end_src

Core channels defined in typology. Domain or service-specific channels
(e.g. prosody, expression) defined by hallucinator services or kernel.
The =type= discriminator is an open string mapping 1:1 to channel names.

MIME specifics (image/jpeg vs image/png) live on the part's =media=
field. Faculty declarations use broad channel types (=image=, =audio=).

* Streaming Ontology

** Packets

A stream delivers an async iterable of packets. Each packet is a
self-contained JSON object, SSE-framed for HTTP transport.

#+begin_src javascript
{ event: 'turn.open',  turn: { role: 'assistant' } }
{ event: 'part.open',  index: 0, part: { type: 'text', text: '' } }
{ event: 'part.delta', index: 0, delta: { text: 'Hello' } }
{ event: 'part.delta', index: 0, delta: { text: ' world' } }
{ event: 'part.close', index: 0 }
{ event: 'part.open',  index: 1, part: { type: 'tool_use', id: 't1', name: 'lookup' } }
{ event: 'part.delta', index: 1, delta: { input: '{"word":"' } }
{ event: 'part.delta', index: 1, delta: { input: 'casa"}' } }
{ event: 'part.close', index: 1 }
{ event: 'turn.close', meta: { usage: { input: 340, output: 89 }, stop: 'tool_use' } }
#+end_src

** Accumulation Rules

- =part.delta= string fields append to existing string fields on the part
- =part.delta= non-string fields replace
- =tool_use.input= streams as raw string chunks; parse JSON on =part.close=
- =turn.close= carries meta (usage, stop reason, latency)

** Accumulator

#+begin_src javascript
function accumulate(turn, packet) {
  switch (packet.event) {
    case 'turn.open':  return { ...packet.turn, parts: [] }
    case 'part.open':  turn.parts[packet.index] = { ...packet.part }; break
    case 'part.delta':
      const part = turn.parts[packet.index]
      for (const [k, v] of Object.entries(packet.delta)) {
        part[k] = typeof v === 'string' && typeof part[k] === 'string'
          ? part[k] + v : v
      }
      break
    case 'part.close': break
    case 'turn.close': turn.meta = packet.meta; break
  }
  return turn
}
#+end_src

** Streaming Characteristics Per Channel

- text, thinking: progressively useful (render/play each chunk)
- audio: progressively useful (play each chunk)
- tool_use: buffer until part.close (partial JSON is unusable)
- object: buffer until part.close (schema validity requires completeness)

Consumer-level concern, not cortex architecture.

* Faculty Contract

What a hallucinator service exposes to the cortex. An array of these:

#+begin_src javascript
{
  type: 'conversation',
  channels: {
    in: ['text', 'image', 'document', 'tool_result', 'thinking'],
    out: ['text', 'thinking', 'tool_use'],
  },
  tune: [0.3, 0.7, 0.8],
  context: 200000,
  via: {
    render: async (turns, config) => turn,
    stream: async (turns, config) => asyncIterableOfPackets,
  },
}
#+end_src

- =type=: faculty type. One of: conversation, object, speech, call.
- =channels.in=: inbound channels — Part types this faculty can receive.
- =channels.out=: outbound channels — Part types this faculty emits.
- =tune=: [cost, quality, speed] characterization.
- =context=: maximum input token capacity.
- =via=: delivery implementations. Presence of method = support.
  =render(turns, config) → Turn=. =stream(turns, config) → AsyncIterable<Packet>=.

The hallucinator service translates between the cortex's turn/part
format and its provider's native API. All normalization is internal
to the service.

** Faculty Types

|------+------------+-------------+-------------|
| conversation | text, image, document, tool_result, thinking | text, thinking, tool_use | render, stream |
| object | text | object | render |
| speech | text | audio | render, stream |
| call | audio, text, tool_result | audio, text, tool_use | stream |

* Delivery as Vector Effect

Delivery avenue (render/stream) is the effect-level destination on the
harness Vector. Faculty type is the branch. This gives each avenue a
distinct HTTP endpoint and unambiguous return type.

* Cortex Composition

#+begin_src javascript
function Cortex(faculties) {
  const table = new Map()
  for (const faculty of faculties) {
    if (!table.has(faculty.type)) table.set(faculty.type, [])
    table.get(faculty.type).push(faculty)
  }

  return {
    table,

    resolve(type, { tune, via } = {}) {
      const candidates = table.get(type) || []
      const eligible = candidates.filter(f => !via || f.via[via])
      return nearest(eligible, tune ?? [0.5, 0.5, 0.5])
    },

    harness(types) {
      const vector = new Vector()
      for (const type of types) {
        const branch = vector.branch(type)
        const vias = new Set()
        for (const faculty of this.table.get(type) || []) {
          for (const v of Object.keys(faculty.via)) vias.add(v)
        }
        for (const v of vias) {
          branch.open(v, async (input, ctx) => {
            const faculty = this.resolve(type, { tune: ctx.tune, via: v })
            return faculty.via[v](input.turns, ctx)
          })
        }
      }
      return vector
    },
  }
}
#+end_src

** Tune Resolution

#+begin_src javascript
const tiers = {
  frugal:    [0.1, 0.3, 0.9],
  balanced:  [0.4, 0.6, 0.6],
  capable:   [0.6, 0.8, 0.4],
  unleashed: [0.9, 1.0, 0.2],
}

function nearest(faculties, target) {
  if (typeof target === 'string') target = tiers[target] ?? [0.5, 0.5, 0.5]
  let best = null
  let bestDistance = Infinity
  for (const faculty of faculties) {
    const d = Math.sqrt(
      (faculty.tune[0] - target[0]) ** 2 +
      (faculty.tune[1] - target[1]) ** 2 +
      (faculty.tune[2] - target[2]) ** 2
    )
    if (d < bestDistance) { bestDistance = d; best = faculty }
  }
  return best
}
#+end_src

* Conversation Flow

Client sends ={parent, turn}= each time. =parent= is the turn ID to
attach to (null for first message). Server walks the parent chain,
builds history, calls faculty, persists both turns, returns new head.

#+begin_src
First message:
  Client → { parent: null, turn: { role: "user", parts: [...] } }
  Server:
    1. Create turn t1 { role: "user", parent: null }
    2. History: [] (no parents)
    3. Faculty: [system*, t1] → response
    4. Create turn t2 { role: "assistant", parent: t1 }
    5. Return t2

Second message:
  Client → { parent: "t2", turn: { role: "user", parts: [...] } }
  Server:
    1. Create turn t3 { role: "user", parent: t2 }
    2. History: walk t2 ← t1 → [t1, t2]
    3. Faculty: [system*, t1, t2, t3] → response
    4. Create turn t4 { role: "assistant", parent: t3 }
    5. Return t4

Graph: t1 ← t2 ← t3 ← t4
#+end_src

=system*= is injected by harness middleware, not in the graph.

Branch/retry: client sends a different parent. New path diverges.
Old turns remain in the graph, reachable from other heads.

#+begin_src
t1 ← t2 ← t3 ← t4        (original)
       ↑
       └── t5 ← t6         (branch from t2)
#+end_src

** LANGUAGED

#+begin_src javascript
export async function LANGUAGED(mode, daemon) {
  const harness = daemon.cortex.harness(['conversation', 'speech', 'object'])

  harness.use(async (ctx, next) => {
    ctx.tune = ctx.input.tune ?? mode.cake.tune ?? 'balanced'
    ctx.system = {
      role: 'system',
      parts: [{ type: 'text', text: mode.cake.personality }],
    }
    ctx.tools = mode.cake.tools
    await next()
  })

  harness.branch('conversation').use(async (ctx, next) => {
    const head = ctx.input.parent
      ? await daemon.entities.turn.findOne(ctx.input.parent)
      : null
    const history = head ? await walkParents(head) : []

    const userTurn = daemon.entities.turn.create({
      parent: head, role: 'user', parts: ctx.input.turn.parts,
    })

    ctx.input.turns = [ctx.system, ...history, userTurn]
    await next()

    const assistantTurn = daemon.entities.turn.create({
      parent: userTurn, role: 'assistant',
      parts: ctx.output.parts, meta: ctx.output.meta,
    })
    await daemon.entities.em.flush()

    ctx.output = { ...ctx.output, id: assistantTurn.id }
  })

  mode.hallucinate = shape.object(harness)
  mode.aperture.branch('/hallucinate').slurp(harness)
}

* Open Questions

** Where the head pointer lives

A thread is a head turn ID. Where is it stored? On the session?
Client-only? Both? The client must send =parent= with each message,
but long-lived conversations need a durable reference.

** Context window management — REQUIRED, MID PRIORITY

The CONVERSATIONAL trait loads ALL turns for a thread with no limit.
Long conversations will silently degrade (slow queries, context overflow
at the provider). Needs a windowing/budgeting/tracing system:

- History query must be bounded (sliding window or token budget)
- Budget-aware truncation: faculty.context informs how many turns to load
- Summarization strategy for dropped turns (or just drop oldest)
- This is middleware on the harness — Layer 2 of CONVERSATIONAL

** Call faculty (realtime)

Bidirectional audio. WebSocket-based. How call fits into the turn/part
ontology is unresolved. Requires investigation of existing realtime
implementations. Architecture TBD.

** Personality system — PARTIALLY RESOLVED

Context is a Vector the mode composes. Effects return ={turns?, config?}=.
The harness middleware traverses it and merges results into the faculty call.
Effects receive ambient state: ={mode, daemon, thread, tune, input}=.

Current implementation iterates =contextVector.effects= directly (not via
=steer.rollup=, which wraps in Context and breaks the arity contract).
When the context vector needs branches and middleware, a dedicated traversal
strategy (=steer.gather=?) will be needed.

** Stream history persistence — RESOLVED

=observe(stream, onSealed)= wraps an async iterable. Consumer iterates
normally. On drain, =onSealed= fires with the accumulated turn.
Branch middleware uses this to persist the assistant turn after the
consumer finishes reading the stream. One primitive, both paths.
