** The disease — inversion of control, backwards

A daemon should be a pure fold over its inputs. Instead =Die.populate/resolve=
reaches THROUGH the global =paladin= singleton into filesystem-scanned state.
Exhaustive grep of =paladin= in =systems/runtime/daemon= (excl. comments/bak/test)
returns EXACTLY two reach-ins:

#+BEGIN_SRC

application.js:10  import paladin → scope.repo →      // the ONLY trait that fetches mid-boot

#+END_SRC

There is no input to substitute, so every scenario hand-forges the OUTPUTS
(=die.register=, the bundler) — that IS =wireMode=/=buildDaemon=/=variant.js=.
The guard =if (!die.register.datamap)= was detecting whether a reach-in had fired.
Band-aids on a missing parameter.

** Multi-consumer — gaia is a paladin seam, not a runtime convenience
gaia serves ≥4 consumers, each folding the same source its own way. NOT speculative:
ghost ALREADY mounts the registry (=trajectories/system/doctor.js:132= + =instance/clone.js:75=).

| consumer       | bundler            | folds the loaded modes into |
|----------------+--------------------+-----------------------------|
| runtime-daemon | svelte             | traits + aperture mount     |
| ghost          | ∅ (none)           | tools / manifests           |
| kajuit         | vite / client-load | rendered views              |
| test-scenario  | identity (()=>[])  | assertions                  |

Producer split:
- =paladin.gaia()= → ={ registry: this.vip }= — the UNIVERSAL half (a Vip: resolver over the

- =bundler= is per-ENVIRONMENT (the view-materializer), CONSUMER-supplied. The svelte
  imports-map stays a runtime-server concern; kajuit's is vite; ghost has none.
