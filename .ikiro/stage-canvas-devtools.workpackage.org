* Intent

Provide rendering engine access as a drapes primitive. ECharts for
data visualization (charts, graphs, heatmaps, timelines), Three.js for
3D (deferred). No framework — a shim and a managed container.

The shim is =stage=. It follows the same pattern as =v= (schematics)
and =specimen= (testing): the sole consumer of the underlying library.
Mode authors import from =@vivalence/drapes=, never from =echarts= or
=three= directly.

The component is =Canvas=. A managed container that handles mount,
resize observation, and cleanup via an =init= callback. Engine-agnostic
— the mode's init function decides whether it's an ECharts instance, a
Three.js scene, a raw 2D canvas, or anything else.

First consumer: a =tool/dashboard= mode that visualizes the live
dataspace — literal topology, memory landscape, trace timeline.

* Design Decisions

1. *Primitive not framework.* =stage= re-exports library pieces. It
   does not wrap, abstract, or opinionify the underlying API. The mode
   speaks the library's native language (ECharts options objects,
   Three.js scene graph). =stage= provides access; the mode provides
   intent.

2. *Sole consumer boundary.* =drapes/stage/lib.js= is the only file
   that imports from =echarts/*= or =three=. If the underlying library
   changes, only lib.js changes. Modes never import from the library
   directly.

3. *Canvas owns lifecycle, nothing else.* Mount → init callback →
   ResizeObserver → cleanup. The init callback returns ={ resize,
   dispose }=. Canvas calls resize on container changes and dispose on
   unmount. Everything else is the mode's business.

4. *Explicit registration.* =stage.use()= wraps ECharts' registration.
   The mode registers only the chart types it needs. Tree-shaking
   removes unused types. No global "register everything" — the mode
   decides.

5. *Escape hatch.* =stage.echarts= exposes the raw echarts core.
   =stage.THREE= exposes the raw three.js namespace. If the shim
   doesn't re-export something, the mode reaches through. The shim
   grows by demand, not by anticipation.

6. *One component for all engines.* =Canvas= doesn't know what
   rendering engine it hosts. There is no =Chart.svelte= vs
   =Scene.svelte=. The distinction lives in the mode's init function.

7. *Dashboard is a tool mode, not a game mode.* Type =tool=, not
   =game=. Traits: =BUFFERED=, =DATASET=. No emitter, no intents, no
   signals, no memory evolution. SELFEVIDENT. The mode fetches its own
   data client-side from existing datamap endpoints.

builds the scene graph.

* Canvas Component

#+begin_src svelte
<script>
  let { init } = $props();
  let container = $state(null);

  $effect(() => {
    if (!container) return;
    let api;

    (async () => {
      api = await init(container);
    })();

    const observer = new ResizeObserver(() => api?.resize?.());
    observer.observe(container);

    return () => {
      observer.disconnect();
      api?.dispose?.();
    };
  });
</script>

<div bind:this={container} style="width:100%;height:100%;min-height:200px;"></div>
#+end_src

The init callback is async to support dynamic import of stage (which
lazy-loads echarts). Returns ={ resize?, dispose? }=. Both optional —
some engines handle resize internally, some have no cleanup.

** Views

*** Graph — Literal Topology

508 nodes, 550 edges. The map of the language.

Nodes: each literal. Size by ontology (sentence > conjugation > word).
Color by memory status (UNTOUCHED dark, UNKNOWN purple, LEARNING
gold, KNOWN green, GRADUATED blue).

Edges: =literal_uses= relations. Sentences cluster around their
constituent words. Conjugation paradigms cluster around inflected
forms. Hub words (=o.determiner=, =você.pronoun=) bridge clusters.

Force layout. Roam + drag. Click node → show literal detail (slug,
traits, translations, memory state, trace count).

Data source: =/entities/literal/find= with =populate: ["uses"]=.

*** Memory — Learning Landscape

Scatter: x = =lastAt=, y = =nextIn= (hours). Each dot is a practiced
literal. Bottom-left = weak (recent + due soon). Top-right = strong
(old + not due). Color by status.

Bar: status distribution across all memory records.

At 71 records this is sparse. Grows as the user practices.

Data source: =/userspace/entities/memory/find=.

*** Traces — Session Heartbeat

Timeline scatter: x = =created_at=, y = signal (MASTERY through
FAILURE). Color by signal. DataZoom slider for time range.

Live-appending via SSE: =/userspace/entities/trace/subscribe=.

Data source: =/userspace/entities/trace/find= (initial load) +
subscribe (live).

*** Taxonomy — Symbol Facets (stretch)

Treemap of symbol→literal counts. Rectangles sized by coverage.
Color by % practiced (has memory record / total in facet). The
overview of what's available vs what's been touched.

Data source: symbols + symbol_literals (would need a new endpoint
or client-side aggregation from literal symbols).

* Open Questions

1. *Where does echarts install?* drapes' =deno.jsonc=, or the html
   system's import map? drapes is a subsystem consumed by html — if
   drapes declares the dependency, html inherits it. But echarts is
   heavy. Should it be an optional/lazy dependency?

2. *Dashboard registration.* Tool modes don't exist yet — all current
   modes are =game= or =tactic= type. Does the daemon need to handle
   =tool= type modes? Or should dashboard just be =type: "game"= with
   no emitter?

3. *Populate on uses.* The graph view needs =populate: ["uses"]= on
   literal find. Does the current literal endpoint support this, or
   does it need a new route / populate option?

4. *Symbol data access.* The taxonomy view needs symbol→literal counts.
   There's no client-facing symbol endpoint currently. Either add one
   or aggregate client-side from literal trait/symbol data.
