How the kernel slot is read: `instance.mount()` in paladin folds the ledger recipe under the instance recipe, then walks each daemon declaration through a `daemon(label)` closure that hydrates the declaration against the record, so every thunk in the declaration fires with the environment already resolved. The kernel entries are then normalised through `reference(module.source)`, which turns a relative path into an absolute one rooted at the instance module, and any entry that is an object carrying a `module` key is additionally dressed so that its mountpoint is checked for absoluteness. After that the runtime's population step imports each kernel entry as a mode module and stagger installs its traits. The whole chain is order-sensitive because the record must be complete before a thunk fires, which is why the ledger fold happens first. So the shape of the kernel slot is decided at populate time, and the reference normalisation is what makes relative paths in the recipe work at all; the string vs array question is really about whether the normalisation step receives an iterable, since it maps over the entries it was given, and the downstream import expects one module per entry rather than a single path.
