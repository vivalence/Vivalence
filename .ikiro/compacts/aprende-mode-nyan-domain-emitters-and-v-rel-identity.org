* The v.rel fix — entities through `v` (typology core, the connoisseur's headline)
Clicking Activation 500'd: "Entity of type SymbolEntity expected for property LiteralEntity.symbols, Collection given." I first patched it by passing ids across the cross-mode boundary. Finn rejected the workaround: "we absolutely want to be able to send literals and other entities through v. figure this out! let the conosseur have a look." Root: =schematics/index.js= `v.rel = (schema) => v.union([scalars.ID, schema])` — the entity arm was the FULL structural schema, so `cast`'s `Value.Convert` (coerces by structure) descended into the entity body and mauled `symbols`/`uses` (MikroORM Collections, not plain arrays). The connoisseur read: *a relation is referenced by IDENTITY, not embedded by value; the schema conflated reference with inclusion.* But a blast found =v.test.js:349= asserts `v.rel(v.mode()).check({slug,type})` → true — rels accept any entity-shaped object, not just `{id}`. So the fix is *structural opacity*, not id-only:
#+BEGIN_SRC javascript
v.rel = (schema) => v.union([scalars.ID, v.object({}, { additionalProperties: true })]);
#+END_SRC
The non-id arm has no declared body → Convert has nothing to descend → entities pass through whole. Ground-truthed by probe: a real prototype-based Collection survives cast BY REFERENCE (`instanceof` intact) — typebox preserves class instances, only shallow-clones plain objects. (My first guardrail test used a plain-object fake and failed on ref-equality — corrected to a class.) Added the guardrail to =v.test.js=; full typology suite green (103 passed / 1062 steps; 1 env-only `whoami` fetch). Then reverted the emitters to pass entities again — entities-through-v, end to end.

* The thread-binding bug
After v.rel, clicking Activation generated no rendered buffer. Finn's DB row showed the tell: `"thread": null`. Chain: (1) `runAction` didn't pass `thread` → aprende's `ctx.thread` unset (=daemon/traits/emitter.js:19,47=). (2) After fixing that, aprende delegated to `nyan.emit.literals` WITHOUT forwarding `thread` → that call runs nyan's full emitter trait, which `flush`es the buffer with `thread=null` (emitter.js:54) before aprende ever re-binds → the re-bind hits an already-flushed/serialized buffer. Fix: forward `thread` through to nyan (+ carry it in the `/drill` and `/coach` input schemas) so nyan binds `buffer.thread` before its OWN flush. Verified live: emitted `buffer.thread` now the bound thread object (was null). Open cosmetic: aprende's trait re-binds + re-indexes the pooled buffer, so `thread.counter` advances twice per drill (an index gap) — harmless, left for later.
