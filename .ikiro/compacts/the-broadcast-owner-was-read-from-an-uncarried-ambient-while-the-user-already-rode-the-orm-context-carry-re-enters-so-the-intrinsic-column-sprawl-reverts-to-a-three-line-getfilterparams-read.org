* Arc (methodical, in order)

** turn 1 — "this feels herrendously hacky. is there some architectural assumption somewhere we're not grogging? or where we maybe just need a clever await?"
The =carry= re-entry (re-open the ORM context per stream =next()=) read as a patch. Traced the real assumption: MikroORM =RequestContext= is scoped to the SYNCHRONOUS handler lifetime — the shape assumes "the response is fully produced inside the context scope." True for buffered JSON; FALSE for a stream, whose body is a suspension the transport drains AFTER the middleware unwinds. So the context closes; the generator's =em.create= runs in the gap. No "clever await" dissolves it: the producer (generator) and consumer (transport) live in different async executions; a generator resumed from another context does not inherit its ALS. =inject='s re-wrap IS the correct bridge — it was just left half-built (=inject= referenced =datamap.shard.carry= that libsql never implemented). Not a hack; a designed mechanism with a hole.

** turn 2 — "or maybe just change attach to bind somewhere"
beef's instinct mapped EXACTLY: =RequestContext.create= (=ALS.run=, scoped, closes) vs =RequestContext.enter= (=ALS.enterWith=, persists) = the =attach= vs =bind= lever. But =enter= is MikroORM's documented footgun — =enterWith= never cleans up, so on the ONE multiplex socket handling many frames it can bleed one request's context into another's =setFilterParams= (cross-tenant). =carry= (run + re-enter, per-stream scoped) is leak-proof by construction. Chose =carry=. Landed it on the libsql shard, marked =// @beef hacky deep wire=, + a regression (=datamap.inject.test=: without carry the stream sees =[null,null,null]=, with it =[true,true,true]=).

* Lessons
- *The thing that FEELS hacky is not always the thing that IS hacky.* =carry= felt like the patch; the real defect was the broadcast reading its owner from a DIFFERENT, un-carried ALS than the one =carry= keeps alive. The half-built =carry= (a dangling reference to an unimplemented =shard.carry=) is what made a correct bridge read as a hack — completing a designed mechanism ≠ adding one.
- *A silent failure is a first-class defect, never a footnote.* =console.warn + drop= on a user-scoped write is exactly the smell beef hates most, and I ranked it below the interesting architecture. Rule (logged): any warn/log/swallow-and-continue on a data-losing path is reported as a TOP finding with a loud-fix; writes that can't complete their contract THROW.
- *When a fix sprawls, the axis is wrong.* Denormalizing an owner column touched schemas, migrations, every write site, and every scenario — for a fact (=thread.user=) the entity already reaches. "too sprawling" was the signal to stop denormalizing DATA and start reading the CONTEXT that was already threaded (and already carried).
- *The user was already on the context we carry.* =bind("user")= writes the filter param that scopes find; =carry= re-enters it. The owner routing and the read routing are the SAME context — reading them from two different places (filter-param for find, ambient for broadcast) was the whole bug. One source, one carry.
- *Verify the mechanism before reverting toward it.* The =inside/outside/carried= probe (=USER-123/null/USER-123=) proved =getFilterParams= survives =carry= BEFORE tearing out the sprawl — so the revert was a walk toward a proven target, not a leap.
- *"aperture" earned two meanings; the glob paid for it.* stripwire assumed every =*-aperture.snapshot.json= was a wire aperture; the corpus find-vantage snapshots squatted the suffix. Name-by-role means a register (a filename suffix) has ONE meaning — the collision, not my change, was the failure.
