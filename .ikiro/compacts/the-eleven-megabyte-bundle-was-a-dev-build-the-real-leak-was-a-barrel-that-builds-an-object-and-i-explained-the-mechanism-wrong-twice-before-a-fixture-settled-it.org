* three wrong mechanisms before the fixture

This is the part worth keeping. I explained the cause from theory twice and
was wrong twice, and the first wrong version went into =invariants.md=,
which auto-loads.

1. *"`export * as ns from` pins the barrel"* — WRONG. Measured 32 B, fully
   shakeable. On that false claim I had proposed deleting three lines from
   =typology/mod.client.js= that would have changed nothing.
2. *"the `.svelte` modules are side-effecting via `css:\"injected\"`"* —
   WRONG. Pure and side-effecting fixtures pin identically.
3. The fixture (4000 exports, one variable at a time) settled it:

#+begin_src text
export * from "./heavy.js"                        32 B    shakeable
export * as heavy from "./heavy.js"               32 B    shakeable
export const v = { check, object, heavy }         32 B    shakeable   ← identifiers only
export const v = { check: core.check, heavy }  214944 B   PINNED      ← property access
export const v = { ...core, heavy }            214876 B   PINNED      ← spread
export const v = { ...core, get heavy() {…} }  214917 B   PINNED      ← getters don't rescue
core.heavy = heavy; export const v = core      214863 B   PINNED      ← mutation
#+end_src

*ONE property access, spread, or call anywhere in the initializer marks the
whole statement impure and everything it references is retained.* Re-exports
are never the problem. Building an object is.

The lesson is not the rule, it is that I shipped two confident mechanisms
before running a 20-line fixture that took two minutes. Logged.

Then three good follow-ups, all answered with measurements:

- *why is typebox so large?* 46% of it is i18n — =build/system/locale=
  134 KB, 41 languages of error messages, plus a 25 KB runtime
  TypeScript-syntax parser (=Type.Script=). The validator itself is ~57 KB.
  It pins ITSELF the same way drapes did: =typebox/build/index.mjs= ends
  =export * as Type= + =import * as Type= + =export default Type=.
- *still a problem in the latest?* No change. 1.3.12 (published two days
  before this session) is byte-identical on =index.mjs= and
  =locale/index.mjs=; =_locale.mjs= went 41 → 40 modules because they
  de-duplicated a doubled =fr_CA=. Upgrading buys ~7 KB.
- *can esbuild be configured around it?* No. =onResolve= can return
  =sideEffects: false= and typebox declares none of its own, so it looked
  free — measured =553 KB → 553 KB=, zero change. Namespace materialization
  is a genuine REFERENCE, not a side effect.
- *would a PR make sense?* No: all three candidates (=export default Type=,
  =export * as Type=, =export * as Locale=) are documented public API and
  removing any breaks every consumer. The only non-breaking upstream change
  is =sideEffects: false=, measured not to help. And I still cannot name the
  locale carrier — nothing outside =locale/= references =Locale=, yet all 40
  are retained. *Do not PR a mechanism you cannot explain.*

Cheapest untested lead, recorded for next session: =v.js= touches exactly 15
=Type.*= members, and the =./type= subpath provably never reaches
=system/locale= (walked 120 modules, no hit) — named imports from
=typebox/type= may drop all 134 KB in one line, and take =Type.Script= with
them. Prove that first; if it works no upstream work is needed at all.
