* the firmware arc — v2, v3, v4

- *v2* (channel): =peerInfo.channel = 0= + never-pinned WiFi channel = the classic "works
  yesterday" ESP-NOW bug. Pin channel 6 + loud =esp_now_init= fail. beef: /"v2 is just the fix
  to get shit flowing again."/
- *v3* (eyes): /"thorough logging. i want to know every state transition and event."/ — LOG
  (always) vs TRACE (DEV-gated) macros, every line JSON, English; send callback with IDF≥5.3
  signature guard; TX-power hygiene trio. Mesh WENT GREEN on v3 — and the boot log convicted
  two more bugs from a single line: ="txPower":78= (setTxPower silently no-ops before WiFi is
  up — the CHANNEL was the real fix) and ="id":"0"= (=WiFi.macAddress()= returns zeros before
  radio start → =esp_read_mac=). The self-verifying log paid for itself immediately.
- *v4* (rebuild): schema settled in chat — 19B header, =(origin, seq)= identity random-seeded,
  variable per-kind payloads (ghost fields structurally dead — a live ping carrying the
  previous alarm's payload had confirmed the disease), =RANGE.peer= in band (the one-endpoint
  edge was THE schema hole: /"whats the issue?"/ → the type-2 reply couldn't name whose ping it
  measured), =epoch= u16 in band (the node TELLS you its clock frame), hub-only SYNC authority,
  RX callback = validate+enqueue only, per-origin dedup with age-out, blind alarm resends same
  seq, STATUS all roles, bootCount in NVS. Warts killed on /"can you fix the warts?"/: hub
  self-STATUS omits rssi (RSSI_SELF sentinel), counters u32. Compile-verified C3+S3 every step
  (arduino-cli + esp32 core 3.3.11 installed for it; struct sizes host-verified: frames
  23/19/24/27/41B). README written; role docs + DEV doc inline after /"thats not fucking
  inline is it??"/
- *the gate that ate the data*: live logs showed the laptop board printing rx traces but no
  data lines — flashed ROLE_SENSOR, and =printReception= was role-gated. beef, on being shown
  the gate: /"why would we ever drop data?!"/ → gate REMOVED, every role prints every
  reception; roles now differ only in radio behavior. The AskUserQuestion fork offered 4 drop
  candidates and the true referent was a 5th — ledgered.
