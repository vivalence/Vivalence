* The design arc — where to guarantee a phase is functional
Finn: "there is a point when we activate a phase where we must guarantee the integrity of our
data for that phase. where would that be?" My first answer (the stall's =phase.subscribe=) was
WRONG; the c-panel grounding corrected it. The arc, each step Finn sharpening:

1. *NOT in the stall.* The stall is a pure reactor (effect-over-model); validation is the
   DRIVER's job, and =e.svelte.phaseAvailable= already half-did it. But it lived in ONE driver
   while three (e-panel · f-panel · hub) write =thread.phase= → the rule was SMEARED, presence-
   checked (=includes("AIMED")=) in 3+ places. The convergence point is the thread.
2. *Phases as data.* Finn: "i like the idea of maybe encoding the phases in 1 name and 2
   functions: can apply, apply." Improved: =canApply= as a boolean is lossy; encode the
   constraint as DATA so the check is generic AND reports WHICH constraint failed (the =$errors=
   content).
3. *Composition, not presence.* Finn: "we dont only want to guard against presence of traits,
   we want to guard against correct compositions and implementations of traits. we want to
   update this continuously. we need a functional approach. ='name', ()=> is valid (), ()=>
   do()=" → validators are composed total predicates over the thread's LIVE wiring (is the
   mount resolvable, is =pull= wired, is depth ≥ 1), and validity is a reactive derivation, not
   a one-shot.
4. *Responsibilities split.* Finn: "responsibilities arent split yet. go through the roles,
   constraints and ownership models of app/dom, typology/entities, typology/stall." The map:
   entity OWNS composition (the trait modules already know the rules) · stall OWNS reaction
   (trusts the phase) · app OWNS display+gesture (should hold NO rules — but did). The rule
   must live with the behavior it guards.

* The trait-protocol problem (the two issues that reframed the whole layer)
Finn caught the timing flaw in my reactive-install sketch: "consider when this function is
called. its called once on instantiation. its not called every time the config changes. we
will change phases and configs a lot." Confirmed in =runner.js=: =applyTraits= loops the trait
set ONCE at resolve. Toggle AIMED later → =$traits= updates but =AIMED()= never re-runs → pull
never installs → continuous silently dead, =f.svelte='s =thread.pull()= throws.
Then the deeper cut: "there a lot of different roles and responsibilities of the traits. i like
the idea. validate whether we are overloading this term. or maybe, we are just to blunt in our
application of it. maybe applyTraits is a too agressive, one size fits all, hammer."
Verdict: the TERM "trait" is fine (a capability bundle); =applyTraits= is the overload —
five cadences (behavior-install · marker · lifecycle · validity) collapsed into one
=(entity)=>void= applied once. The proof it was too blunt: =CONVERSATIONAL= already ESCAPED it
(wired separately, =engage/release= user-driven). The exception WAS the evidence.
The decisive reframe — Finn: "this might be avoided if we are a little bit smarter with our
imports and exports. we dont HAVE to barrel exeport and we dont HAVE to automatically run EVERY
trait function every time. take away these assumptions and construct the system from that
perspective." And: "i dont think we WANT uniformity on trait level. we want propper exporting
and responsibilities."
