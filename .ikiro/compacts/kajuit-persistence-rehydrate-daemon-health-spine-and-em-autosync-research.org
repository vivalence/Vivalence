** "terminals loose their threads" on refresh

Finn: =when refreshing the client, the terminals loose their threads. in kajuit.=

Root cause: =stores/terminals.js= persisted to localStorage by subscribing only to =$entities= (the array). But a Terminal stores thread/buffer in inner atoms (=$thread=/=$buffer=); =terminal.thread = X= (navigation =resume()=) mutates the inner atom without changing the array reference → the persistence writer never fired → thread selection never written → on reload =rehydrate= skipped it (=typeof terminal.thread !== "string"=) → no thread. Earlier terminals only survived incidentally (creating a *later* terminal re-serialized the whole array).

Fix (systemic, per [[feedback_no_hotfix_architecture]]): the persistence must observe the actual reactive state, not array identity. The constructor now watches each terminal's =$thread=/=$buffer= atoms and **re-arms** those inner subscriptions whenever =$entities= changes:
#+begin_src js
let innerSubscriptions = [];
this.$entities.subscribe((entities) => {
  innerSubscriptions.forEach((unsubscribe) => unsubscribe());
  innerSubscriptions = entities.flatMap((terminal) => [
    terminal.$thread.subscribe(write),
    terminal.$buffer.subscribe(write),
  ]);
  write();
});
#+end_src
The trap worth remembering: an =atom= holding objects that themselves hold atoms — the outer atom only fires on array-ref change; mutating an inner atom is invisible to outer subscribers.

** "next.mount is not a function" — intermittent on reload

Finn: =sometimes i get this error on page reload. not always=. Stack: =boot → verify → gate ready → Frame.activate → next.mount is not a function=.

=Buffer= (=entities/buffer.js=) has =mount()/render()/release()/destroy()=; a raw id-string does not. Two compounding causes: (1) the terminals-persistence fix above now reliably wrote =buffer= as an id-string; (2) =rehydrate= restored =thread= but **never =buffer=**, and there's an async window where terminals construct from localStorage *before* rehydrate runs. So =$buffer= was a string → =Frame.activate(string)=.

Fix A — =rehydrate= now resolves **both** thread and buffer to a live entity or =null= (never a dangling string), via a generalized =restore(entityName, id, options)= helper that searches daemons' repos.
Fix B — =drapes/panels/Frame.svelte= guards the effect boundary: =if (typeof next.mount !== "function") return;= after the null check, so =live=/=teardown= never see a non-Buffer (=teardown= calls =live.release()= which would also crash on a string).

** Research: automatic vs manual server-sync of relation assignments

Finn pointed at =remote-repository.js=, =thread/dossier.js=, =entity-manager.js=, =Aprende.svelte= and the stubbed =// thread.$mode.subscribe()=. He wants =terminal.thread.mode = X= to auto-PATCH the server. Two approaches named: (1) **manual** — dossier wires =thread.$mode.subscribe → updateOne=; (2) **automatic** — entity-manager-level relationship wiring so every relation set triggers an update. Finn: =i would like you to research the automatic approach first. read through the testing of remote repo and entity map, study the related components, hypothesise if this is possible. judge if its reasonable.=

Verdict delivered (research only, no code): **possible in theory, not reasonable here.**
- The =RemoteEntityManager= already has the unit-of-work the automatic approach would ride: =persist(entity)= → =changes()= (diff of =toJSON= vs =snapshot=) → =flush()= (batched =/updateOne=); =Entity.toJSON= already collapses =m:1 → {id}=; =cast()= already installs =defineProperty= accessors for 1:m collections.
- **Decisive blocker:** kajuit entities keep mutable state in **nanostores atoms**, not plain fields. =Thread.mode= is a getter/setter over =$mode= (=set mode(v){ this.$mode.set(v) }=). =Entity.toJSON= iterates own enumerable props = the =$mode= *atom* (the =mode= getter lives on the prototype, never enumerated); the atom is either skipped (non-plain) or makes =structuredClone= throw → **the EM diff never sees =mode=**. Proven by the =entity-manager.test.js= "snapshot resilience" test: non-cloneable entity → =changes()= returns =null= (graceful no-op). Thread carries =daemon=, =socket=, =conversation=, =streams=, atoms — exactly that case. So the automatic path would *silently* not fire.
- Secondary: hydration write-back storms (=merge=/=cast= assign fields on every read → would self-trigger), relation-diffing is untested (only scalars), the unit-of-work is currently dormant in kajuit (app uses =repo.updateOne= directly), and it bolts a 2nd reactivity system on top of the atoms that already drive the UI and already fire on =thread.mode = X=.
- Recommendation: the atom IS the signal — manual =thread.$mode.subscribe(...)= (already stubbed), or, for a generic feel without the EM, an **atom-layer** wiring that loops the schema's =m:1= relations and subscribes to each =$field= atom (skip the hydration echo by comparing incoming id to last-synced). Offered to spec either; awaiting Finn's choice.
