* the FK gotcha, recurring exactly as predicted

Mid-run beef restarted runtime + client. Mikro migrated the italian DB — created =Retention=, dropped =Engram=, renamed =Trace.engram= → =Trace.retention=. And sqlite's =rename column= left the constraint naming the dropped table:

#+begin_example
constraint `Trace_engram_foreign` foreign key("retention") references `Engram`(`id`)
#+end_example

→ =SQLITE_ERROR: no such table: main.Engram= on every Trace insert, surfacing as a red in =integration.test.js= that had been green at baseline. The drop cascaded both tables to 0 (23 retentions, 83 traces). Priced as beef priced it in advance — *"we can pretty much ignore that"* — no recovery ceremony this time. One table rebuild with the right FK, =pragma foreign_key_check= clean, suite back to 38.

*This is the second consecutive rename where the same sqlite semantics bit.* Mikro writes the migration (never author one, never patch a =.snapshot-*.json=) but its rename path does NOT rewrite dependent FK constraints — a table rebuild of the referencing table is the standing follow-up, not an incident.
