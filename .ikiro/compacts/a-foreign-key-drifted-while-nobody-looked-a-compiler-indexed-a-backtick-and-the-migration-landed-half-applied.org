* the question was a false dichotomy

beef's read — *"rewrote traits rename or remove"* — assumed the defect was in the =traits=
column, and the *"again"* pointed at a family of past renames. Neither half held. Nothing
was renamed and nothing was removed. The migration failed on a line that mentions =traits=
only because =traits= was the innocent bystander standing where the damage was written:

#+begin_src sql
alter table `Buffer` add column `traits` json not null default '[]'
  constraint `Buffer_thread_foreign` references `Thread` (`id`) on update cascade on delete cascade;
-- SQLITE_ERROR: Cannot add a REFERENCES column with non-NULL default value
#+end_src

A foreign key for =thread= welded onto the =traits= column. Two independent causes had to
meet for that statement to exist.

** cause one — a foreign key rule that drifted where no differ could see it

=BufferEntity.thread= carries =deleteRule: "cascade"=, and has since ~09-07. The italian
db was born 09-01 with =on delete set null=. Every db born after the entity change has the
right rule; every db born before has the wrong one and has never been told.

| db | Buffer.thread rule | born |
|---|---|---|
| =vcompany= · =hello= | =cascade= | after the entity change |
| =italian= · all 5 =language-learning= | =set null= | before |

The drift is invisible by construction: =checkMigrationNeeded()= and =createMigration()=
diff against =.snapshot-*.json=, **never against the live database**. The snapshot said
=set null= too, so for ten days there was nothing to report. The entity change alone was
inert. It only became a diff when a second change to the same table arrived.

** cause two — mikro's sqlite compiler indexes a string as if it were an array

=@mikro-orm/knex/dialects/sqlite/SqliteTableCompiler.js:22=, verbatim:

#+begin_src js
const column = this.formatter.columnize(foreignInfo.column);
const addColumnQuery = this.sequence.find((query) => query.sql.includes(`add column ${column[0]}`));
// no need for temp tables if we just add a column
if (addColumnQuery) {
  addColumnQuery.sql += ` constraint ${keyName} references ${inTable} (${references})${onUpdate}${onDelete}`;
  return;
}
#+end_src

=columnize= returns a **string** — =`thread`= — so =column[0]= is a single backtick. The
search for /"the add-column statement for this FK's own column"/ degrades into /"any
statement containing =add column `="/, which is every added column on the table. The FK
finds the first one and glues itself on. The optimisation's own comment states the
precondition it then fails to check.

Pinned upstream at =v6.6.16= — byte-identical logic, so this is not a stale pin. 7.x
dropped knex entirely, which is a rewrite and not a fix to take.

** the collision, stated once

A sqlite table cannot receive **a changed FK rule and an added column in the same mikro
diff**. Separately each is fine: the FK change alone routes through =getAlterTable= and its
=__temp_alter= rebuild; the column alone is a clean =add column=. Together, the FK's
temp-table path is skipped by an optimisation that then attaches the constraint to the
wrong column. Every db still holding an old FK rule is armed, and fires on the next
unrelated column added to that table.

* the second wound — no transaction, so the failure is not atomic

=commons/datamaps/libsql/libsql.viva.js= configures =migrations: { transactional: false }=.
The migration that threw had already run every statement before the Buffer line. Measured
on the live db before repair:

| table | state after the "failed" migration |
|---|---|
| =Mode= | rebuilt via =__temp_alter=, done |
| =Literal= · =Symbol= | =mode_id= column + index + unique index, done |
| =Thread= | =parent= column + index, done |
| =Buffer= | untouched — the crash |
| =_mikro_migrations= | **two rows**, the 09-11 migration absent |

So the db was in a state no migration describes: most of the work applied, nothing
recorded, and the =.ts= file still on disk waiting to re-run from the top. A second boot
would not have retried the Buffer line — it would have died earlier, on =drop index
`Literal_slug_unique`=, an index the first pass had already dropped.

** a third defect, found by reading the generated SQL rather than trusting it

#+begin_src sql
this.addSql(`pragma foreign_keys = on;drop index `Literal_slug_unique`;`);
#+end_src

Two statements in one =addSql=. The sqlite driver executes the first and discards the rest,
so the pragma ran and the =drop index= silently did not. The index survived the migration
that claims to remove it. This is why the repair script drops it by hand.

* the repair, and why it was a table rebuild and not a migration

The memory =feedback_mikro_owns_the_db= is unambiguous: never author a migration. It is equally
unambiguous about the exception — a drifted dev db is repaired by **one table rebuild**,
which is not a migration and does not compete with the differ. That is the path taken.

Dry run first, on a copy, with the full entity assembly reproduced from
=daemon/lifecycle/population.js= including the education domain tier:

1. reproduce — the differ minted the corrupt =ALTER= byte-for-byte against the copy
2. repair — rebuild =Buffer= to the entity's DDL using mikro's own =__temp_alter= recipe
3. re-diff — =checkMigrationNeeded(): false=, nothing minted
4. read back — the ORM returned the surviving buffer with =traits: []=, =trait: {}=, thread bound

Then the same on the real db, after confirming zero holders on the file and free ports. The
**snapshot was kept**, not reverted: it already describes the target state, so keeping it is
what makes the differ go quiet. The failed =.ts= was deleted (captured to scratch first).

* the claim-guard caught the word "verified"

The stop hook fired on *"Fix applied, verified"* — assume-dont-verify, family n=16, five
failures, largest on the board. The complaint was exact: the turn asserted a completion and
the measurement backing it lived in an **earlier** turn. The envelope above was then taken
fresh, in the asserting turn, and pasted.

Worth keeping, because the failure mode is subtle: the measurement had genuinely been made,
and making it again changed nothing about the world. What it changed is whether the reader
can tell a measured claim from a remembered one. The hook does not doubt the fact, it
doubts the tense.

* what is still armed

The five =language-learning= dbs all carry =Buffer.thread on delete set null=, brazilian
with 273 buffers. Their snapshots have **not** advanced, so they fire the same collision at
their next boot. A FK-only repair script is written and NOT applied — it flips the rule and
adds no columns, leaving mikro to mint =traits= / =trait= itself.

Not applied because the instance may simply be dead. That is beef's call, not mine.
