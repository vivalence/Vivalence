* THE BIG ARC — object generation as a derived cortex capability

** The break
=hallucination.object.render(schema)= (my first cut) is invalid on every axis: =Hallucination= (=prototypes/hallucination.js=) is a DATA HOLDER (add/absorb/tool/tune/configure — no execution); execution lives on the cortex (=renderLeaf/streamLeaf/executeTools=); the anthropic provider registers ONLY =dialogue= faculties (=FACULTY_TYPES = dialogue/speech/verbatim=). No object faculty existed; =mode.harness.dialogue.*= is turn-bound. The object faculty CONTRACT was already latent in the tests: =cortex.test.js= / =hallucination.test.js= define =type:"object", channels:{in:["text"],out:["object"]}, via:{render:(turns,config)=>{parts:[{type:"object", data, schema: config.schema}]}}=. So =config.schema= is the codebase's naming, not mine.

** Is a dedicated provider slot logical?
Finn: "is there a reason to have a dedicated slot for the provider to facilitate object generation? outside anthropics preference. logically? do we want that?" Reasoned: a native provider object slot is justified ONLY where a provider has a NATIVE structured mode distinct from tool-calling (OpenAI json_schema, Gemini responseSchema) — constrained decoding, own tune. For Anthropic, structured output IS a tool call → a dedicated slot buys nothing. And object-WITH-tools can never be a native slot (native modes don't interleave tool calls) — it's inherently dialogue + a terminal structured tool. Finn endorsed the framing VERBATIM and praised it: "perfect! i want this." — Keep =object= in the faculty CONTRACT as an optional native fast-path; don't give Anthropic one; cortex SYNTHESIZES object from dialogue + a respond-tool (the universal path, and the only one that supports tools).

** 3 approaches to object-with-tools (Finn: "fix q1 and q2 ... research then ideate 3 approaches")
- A — provider-owned object faculty with an internal tool loop. ✗ provider has no tool HANDLERS (they live in =hallucination.tools=); running them leaks orchestration into the stateless provider.
- B — cortex-orchestrated object over dialogue with a terminal =respond= tool: =tool_choice:"any"= over [real tools, respond]; =executeTools= runs review/search; terminate + extract when the model calls =respond=. ✓ provider stays thin (just forward =tool_choice=, disable thinking when forced).
- C — two-phase (dialogue+tools research, then one-shot structured). ✗ splits reasoning, 2× calls, no interleave.
Chosen: B.

** Elegance correction — how to INSTALL/facilitate the faculty
My first B wiring special-cased =if (type === "object")= inside =shard.faculties=. Finn: "this isnt elegant at all. look how you break the pattern. reason about 3 ways to implement this and propose the most fitting one. the question is: how to get the faculty installed and facilitated?!" Three ways: (1) eagerly install a synthetic faculty into the table — stateful, mutation-timing; (2) special-case the wiring loop — the wart; (3) DERIVED FACULTY surfaced through =has=/=resolve= — a declarative =DERIVATIONS= map, =has(type)= = native OR derivable, =resolve(type)= returns native else derives on demand (bound to the requested tune), and =shard.faculties= stays 100% generic. Chose (3): object isn't installed, it's FACILITATED BY RESOLUTION — derivation belongs in the cortex's own resolve/has, not in the wiring loop or table mutation.
