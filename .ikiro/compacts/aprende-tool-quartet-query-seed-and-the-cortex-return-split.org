* the two mechanics that shaped the code

**The cortex tool-return split.** =executeTools=
(~subsystems/typology/prototypes/cortex.js:39~) treats any return carrying a
=message= / =entities= / =object= key as lexicon-native and splits it: only =message=
reaches the model; =entities=/=object= ride the part app-side. Consequence, load-bearing
for query: a read tool MUST return bare data (={ results }=, no reserved keys) or its
rows never reach the model. Buffer tools keep the ={ message, entities }= receipt shape
— screen delivery rides the emit broadcast, the model gets one line of receipt.

**Tool handlers get a real Context.** =TOOLED=
(~systems/runtime/daemon/traits/tooled.js~) prepends =shard.context.bind= middleware for
daemon + mode before slurping =mode.module.tools=; =shape.agentic= compiles through
=steer.rollup(vector, steer.guarded)=, and =guarded= casts/validates input against the
descriptor schema then runs the carry chain. So handlers see =ctx.daemon= /
=ctx.mode= / =ctx.input= (with =thread= injected by the cortex loop) even though the
cortex calls =execute(input)= — the binding rides the chain, not the call site.
