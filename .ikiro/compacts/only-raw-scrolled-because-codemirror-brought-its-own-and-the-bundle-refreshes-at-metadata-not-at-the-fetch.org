=.cm-scroller=; =read= and =edit= were flex children of an =overflow: hidden= column carrying nothing but

he reasoned out loud toward a reaper, killed his own design mid-sentence, and told me to file it.

** what the bundler actually does (75)

The chain, measured rather than recalled:

#+begin_example
boot → stagger(APPLICATION) → deferred
  └─ paladin.bundler(store).bundle({ kind:"svelte", entry })
       source === null → SKIPS the disk probe → always compile
       hash = digest(OUTPUT text) → write <store>/bundle/<hash16>.svelte.mjs

per hit  /attached/bundle/<mode.mount>/<hash16>.svelte.mjs
  └─ bundler.serve() → read.text(disk) + crypto.digest   ← disk read + sha256 EVERY request, no compile

client   Bundle.load() → module-level `verified` Map keyed by integrity
  └─ after the first import: no fetch either
#+end_example

=belt/bundler.js= probes the cache only on the =source= branch. It cannot probe on the =entry= branch: the hash
is of the OUTPUT, so it has to compile to learn the key. Source-based views (GENERATIVE) hash the input and do
hit the cache; every mode buffer is entry-based and recompiles each boot.

Measured, so the proposal carried numbers rather than adjectives:

#+begin_example
Vdex.svelte  →  858ms cold · 426ms warm · 6385 kb out (inline sourcemap, dev)
~/.viva      →  757 *.svelte.mjs, nothing ever unlinked
                stucatch/dashboard/watch/bundle/ alone holds 15 generations
                office/vdocs + office/corpo hold the SAME hash — one module, two mountings, two stores
#+end_example

=--watch= does not help either: it follows the module graph, and =.svelte= files never enter it — esbuild reads
them off disk. Mode =.js= changes restart the watcher; buffer views do not.

** the seam he guessed at, and why it cannot take it (76)

He guessed runtime attachments. It is the intuitive place and it is the one place that cannot work, for three
independent reasons that all reduce to content addressing:

- =serve()= looks up by the requested stem. A fresh compile writes a DIFFERENT stem, so the request still reads
  the stale file.
- Serve the new bytes under the old path anyway and the client throws =integrity sha256 X is not Y= —
  =entry.integrity= came from metadata.
- Worst: *the route is never hit twice.* =Bundle.load()= memoizes in a module-level =verified= Map keyed by
  integrity, and =Frame.identity()= is =record.hash=. Same hash → the =$effect= early-returns, no fetch at all.
  Recompiling at a route nobody re-requests is a no-op.

It *can* be made to work there — stable dev path, =integrity: null=, recompile in =serve()=; =load()= skips both
memo branches when integrity is null. But it buys the refresh by turning content addressing off in dev, so dev
and prod take different paths through =bundle()=, =View= and =Bundle.load()=. That is the class of bug you
cannot reproduce, and it was worth saying out loud rather than just picking the other option.

** the landing (77)

=/metadata/app= is a *lazy closure evaluated per request*, and the only place the hash crosses to the client.
Recompile there and the existing reactive chain does the rest untouched:

#+begin_example
GET /mode/office/vdex/metadata/app   (dev)
  → recompile → new hash + integrity → mode.app.view replaced
  → client APPLICATION sets mode.app store
  → a.svelte `view` re-derives          ($app is a store, chain() is live)
  → Frame identity(view) changed → teardown → load() → new path, verified MISS → fresh import
#+end_example

=systems/runtime/daemon/traits/application.js= — the compile lifted to a callable:

#+begin_src js
  let compiling = null;
  mode.app.compile = () => {
    compiling ??= (async () => {
      const store = `${daemon.mountpoint.absolute}/bundles/${mode.manifest.type}/${mode.manifest.slug}`;
      mode.app.view = await paladin.bundler(store).bundle(
        mode.app.source
          ? { kind: "svelte", source: mode.app.source }
          : { kind: "svelte", entry: entry.absolute },
      );
      return mode.app.view;
    })().finally(() => (compiling = null));
    return compiling;
  };

  return () => mode.app.compile();
#+end_src

The guard is not decoration. =/metadata/app= is now hit by every client mode boot, so two terminals opening
together would compile the same entry twice and race on =mode.app.view=. Promise memo, set synchronously before
the first await, cleared in =finally= — the =lighthouse.populate= shape.

=systems/runtime/daemon/aperture/metadata.js=:

#+begin_src js
     if (mode.implements("APPLICATION"))
       meta.open("/app", async () => {
         if (paladin.is.dev) await mode.app.compile();
         return {
           url: die.good.attach.branch("/bundle").branch(mode.mount.absolute).absolute,
           view: mode.app.view.json,
           schema: mode.app.schema ?? null,
         };
       });
#+end_src

=paladin.is.dev= is live and was verified rather than assumed: =paladin.mode= = =env.get("VIVA_SYSTEM_MODE")=,
and =~/.viva/.env:1= claims =DEVELOPMENT= at the lowest (ledger) stratum, =populate.js:89=. Nothing else sets
it, so it holds locally and is absent in a container.

Cadence stated plainly rather than sold: the client calls =/metadata/app= once per mode boot, so /"every hit"/
lands as *every page reload*, not every artifact fetch. The artifact fetch is by definition the thing that must
not change.

** T3, marked not built (77)

He talked himself out of his own design inside one turn, and the reason is the keeper. Filed whole at
=known-issues.org= → =* bundle-store-never-prunes=, his words quoted:

#+begin_quote
we want a cleanup process in the runtime. runtime goes through the waste and cleans up anything older than xyz
or something. no that would force the runtime to regularly re-compile. stupid. hmmm. no clue.
#+end_quote

He is right, and the entry says why in one line: *the only pointer to the live artifact is =mode.app.view.mount=,
held in the runtime's memory* — not on disk, not in the ledger. Sweep by age and you either delete what a
running daemon is still serving, or you have to ask the runtime what is live, at which point age was never the
key.

The key that IS available: *supersession, not age.* =compile()= holds both hashes, the one it replaces and the
one it just minted; everything else under that mode's =bundle/= is dead the instant they differ. One
=Deno.remove=, no inference, no reaper. It only prunes forward — the standing 757 need a one-shot, and that one
CAN be age-keyed because nothing serves them.

Four things a go would still have to decide, all in the entry: whose verb (=paladin.bundler= mints and serves
but only the trait knows what is live; runtime lifecycle is his first instinct and a real third option); whether
prod wants it at all (prod compiles once per deploy, and deleting costs the rollback); what happens to a store
two daemons share; and whether the store should key on MODULE identity rather than mounting — which collapses
=vdocs=/=corpo= from two byte-identical artifacts to one and shrinks the problem before anyone prunes it.
