* The one finding that SURVIVES the rejection — tool loop is a STRATEGY, not a middleware

beef's inline doubt: "strategy might be one place to facilitate the tool use loop?! a middleware would also be adequate." The connoisseur resolved it on a HARD mechanic, not taste:

*koa-compose forbids calling =next()= twice* ("next() called multiple times"). A tool loop IS re-invoking the avenue N times. So a loop-middleware cannot drive the repeat through =next()= — it would have to call the avenue directly and ignore the effect, rendering every effect vestigial (a strategy in a middleware costume, worse). The strategy owns the ONION TERMINAL — it loops freely while compile-in / parse-out wrap exactly once. ⇒ =shape.object(vector, hallucinate)=, a new steer-family member beside =echo/guarded=.

Two more reusable notes from that pass:
- *the three historical versions ARE three answers to "where does the loop live":* jj-committed 26679a3d = loop in cortex =renderLeaf/streamLeaf/deriveObjectFallback=; working-copy = loop on the request as =render(type)/stream(type)= methods (executeTools exported, cortex imports it — the backward dep); quest pass-4/5 = loop as =execution.render/.stream= strategies. So approaches A/B/C = registry-owns / request-owns-via-toolbox / strategy-owns.
- *streaming-elegance seam:* the parse-out middleware wraps an UNCONSUMED generator — for a stream, =next()= returns the instant the terminal CREATES the generator; parse-out returns a wrapping generator that folds =soma.pour= over the packet flow (tool_use → entities, single pass, no buffering); the leaf =yield*='s it. Render and stream share the onion; keep them as TWO twins (turn grammar vs packet grammar) — do not force-collapse.
