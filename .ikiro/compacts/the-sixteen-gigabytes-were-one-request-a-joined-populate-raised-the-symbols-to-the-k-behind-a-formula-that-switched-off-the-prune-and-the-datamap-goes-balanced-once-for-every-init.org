* what the sixteen gigabytes were

Not sqlite, not a pile-up, not the client. One =/resolve= for an =all= clause with k chips in
ALL: =picks.all= → =repository.find(where, {limit, orderBy: {rank}, populate: ["retentions"]})=.
MikroORM 6.6.7, default =loadStrategy: "joined"= (=core/utils/Configuration.js:50=): a joined
to-many populate + =limit= sets =PAGINATE=; =wrapPaginateSubQuery= moves the where into a
subquery (=… where s2.slug = … and s4.slug = … group by l0.id order by min(rank) limit 20=)
and would delete the outer joins it no longer needs — but it returns before that when any
selected field is a =RawQueryFragment=. =Retention.lastSignal= is a formula selected with the
populate. So the outer query keeps =left join symbol_literals s3 … left join Symbol s2 …= three
times over, unconstrained: per literal =symbols^k= rows, each carrying =l0.*= (the trait JSON),
all hydrated on the main thread. =/count= never populates → 36 ms. The fixture suites were green
because fixture literals carry two symbols. =0 of 1938 counted= from compact 44 was the same
request dying and =catch → rows = []=.

* the category and its three levels

The category is not "retentions" and not "the formula" — it is **a to-many relation loaded by
JOIN**: every multiplication found (=symbols^k= behind paginate; =uses×symbols= and
=literals×symbols= without it) needs that primitive. So:

- =strategy: "select-in"= on =retentions= — kills the dojo/stream shape only. Kept, explicit at the relation.
- =lastSignal: lazy= — kills only this trigger, re-arms on the next formula, and BREAKS eleven readers of =retention.is.failed=. beef: /"no lazy on last signal"/.
- =loadStrategy: "balanced"= — to-one JOINED (one row), to-many SELECT-IN (root query + one =where fk in (ids)= per relation per level, additive). Kills the primitive; the upstream early-return becomes unreachable. Declared ONCE in =config()= so no =MikroORM.init= — daemon or test — can drift back to JOINED unnoticed.
