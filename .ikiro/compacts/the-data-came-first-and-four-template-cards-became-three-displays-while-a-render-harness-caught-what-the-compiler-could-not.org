* the data came first

The order was explicit about sequence, and the sequence changed the result. Three probes, run against the
shelf instance through `deno eval` at the workspace root — the entry file must live inside the Deno
workspace or `@vivalence/paladin` will not resolve, which cost two attempts from the scratchpad.

| display | source | what came back |
|---------+--------+----------------|
| daemon | `paladin.instance.daemons` matched on MOUNTPOINT + `ctx.daemon` (the die) | 1 mode, 3 routes, 6 traits, 4 entities, 1 hallucinator attached + 1 dormant, 2 faculties |
| ledger | `paladin.ledger.instances` + `scope` + `env.get` | 4 instances, 1 service, 1 client, 12 env vars, 1 unset slot |
| registry | `paladin.vip.pensieve` after `supply()` | 61 modules · 4 owners · 21 types |

The daemon is identified by matching `daemon.mount.absolute` against `ctx.daemon.mountpoint.absolute`,
not by taking the only entry — hello-world has one daemon today and that is not a fact to encode.

*** The secret discipline held by construction.*** A hydrated mask carries `secrets.key` in CLEAR, so the
payload emits SLOT NAMES only — `secrets key`, `secrets jwt`. `paladin.env.vars` carries no `SECRET_`
keys at all (env and secret are separate `Env`s), so resolving the whole environment is safe. Scanned the
finished payload for `sk-` patterns and `SECRET_`-with-a-value: none.

* the render harness

Compile the component for the server, seed its `$state` from a global on a SCRATCH copy, render it with
the real probed payload, strip the tags and read it back as prose.

#+begin_example
  compile(src, { generate: "server" })                       # npm:svelte@5/compiler
  src.replace("let report = $state(null);",                  # on a copy in scratchpad, never the real file
              "let report = $state(globalThis.__REPORT__ ?? null);")
  render(mod.default, { props })                             # npm:svelte@5/server
#+end_example

`report` is local `$state`, not a prop, so props alone render 2668 bytes of empty page — the seed is what
makes the harness work. With it: 17996 bytes, and every one of the three displays legible as text. It
caught the `via` bug, it caught that my ctx shim was masking the `docs` fallback, and it is the first
verification in this whole hello-world arc that actually looks at the rendered result rather than at a
compile plus a grep.

* three callouts

*** A compiler warning is not an audit, and neither is a compile.

Last fold the lesson was that `css_unused_selector` cannot see a rule that is gone. This fold it went a
step further: a clean compile says nothing about what the template PRINTS. `Object.keys` on an array is
valid JavaScript, valid Svelte, and wrong. The check that finds it is rendering the thing and reading it.

*** A sequencing instruction is an instruction.

/"fist get the data for each"/ was not scene-setting. Obeying it produced the resolved-vs-raw env finding,
the `via` shape mismatch, and the registry's real cardinality — three things that would have been guessed
wrong, and one of which (the env templates) beef had already photographed as a defect.

*** Do not name a helper after a browser global.

`const window = (context) => …` inside a Svelte component shadows `window` for the whole module. Caught
before landing and renamed `contextWindow`. No abbreviation, no shadow — the rule is that a local name
must not collide with an ambient one, and "it reads well" is not a defence.
