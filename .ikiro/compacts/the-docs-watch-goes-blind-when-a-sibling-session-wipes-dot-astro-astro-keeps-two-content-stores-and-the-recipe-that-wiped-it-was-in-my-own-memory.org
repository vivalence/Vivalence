The log named a configuration file; no configuration file had moved. The trace went to the astro source under =node_modules= and to the sibling transcripts on disk, and both agreed: the "docs survey" session had run =rm -rf .astro && astro build= inside =documentation/= while beef's =deno task documentation/watch= was live. Astro keeps its content store in two places — the dev server's under =.astro/=, a build's under =node_modules/.astro/= — and the dev runtime reads its store from disk on every invalidation, so a deleted file is an empty site. Nothing regenerates it: the restart path never re-syncs content, and the in-memory store still holds every entry with its dirty flag down, so even a manual sync declines to write. The =rm= was not the sibling's invention — it was the stale-cache recipe in my own =project_documentation_site= memory, unqualified. The memory now carries the two-stores law and =--force= as the sanctioned clear; the =public/= junk found beside the bug went to =known-issues.org=; the dev server is still dead until beef restarts it, because his foreground process is his. Then =ikiro compact=, with =/clear= queued behind it.

* arc

** the log named a configuration file; the source named an unlink (row 1)

=Configuration file removed= is what astro prints for ANY unlink that =shouldRestartContainer= accepts, and the only candidate under =.astro/= is =settings.json=, the preferences file the update-check writes at boot. So the message meant "something deleted =.astro/= wholesale", and the failed =content-assets.mjs= import was a request caught mid-deletion. What made the site stay dead was the part no log line says: the dev runtime does not serve from the content layer's memory, it serves from the =astro:data-layer-content= virtual module, which re-reads =.astro/data-store.json= from disk each time it is invalidated. Delete that one file and every =getCollection= sees an empty map while the process still holds all nine entries. The restart does not help — =restartContainerInPlace= rebuilds vite and nothing else — and the =s= shortcut cannot help either, because the glob loader skips entries whose digest matches and the store only writes when something called =set=. The =.astro/= directory looked regenerated at 16:34:37 (=content-modules.mjs=, =content.d.ts=, schemas), which is the trap: those were the sibling BUILD's sync writing what it writes when files are missing; a build's store lives elsewhere, so =data-store.json= alone never came back.

** the weapon was a recipe in my own memory (rows 1, 3)

The sibling did not improvise =rm -rf .astro=. My =project_documentation_site= memory carried, since the home-rework era, /"Gotcha: stale =.astro/= content-layer cache after moving collection files → UnknownContentCollectionError; =rm -rf .astro=."/ — a correct remedy for a dead dev server, stated without the condition that makes it safe. A memory recipe reads as canon to every session that loads it, and this one loaded into a session that had no way to know a watch was up in another terminal. Same family as a codemap claim that rots unread: derived canon asserting an action without its precondition. The line now says =--force= (which clears only the store of the command that runs it, =clearContentLayerCache= keyed on =isDev=) and names the two-stores law at the end of the body; MEMORY.md's hook says the same in one clause, because the hook is what a sibling skims. No callout: beef did not name it, and the recipe was mine, not a beef correction.

** the control that made the claim measurable (row 1)

Two builds ran that minute. The first, from session =8d4bdf08= at 16:34:01, had no =rm=; it wrote the build store at 16:34:03 and the watch served =/50.01_slowstart= 200 at 16:34:32. The second had the =rm=. One variable between them. That is why the memory now says a concurrent plain =astro build= is SAFE — the sanctioned "MDX check without capture" stays as written — and why the ban is on the =rm= alone, not on building beside a watch.

** the tree beside the bug (rows 1, 3)

=dist/= carried =.astro/=, an empty =dist/=, and =node_modules/.vite/deps/= — not build output but =public/= copied verbatim, and =public/= has held those three since the day the site was born (an astro run rooted one directory too deep). They ship into the nginx image. Beef's tree, one =rm=, so a known-issue, not a deletion.
