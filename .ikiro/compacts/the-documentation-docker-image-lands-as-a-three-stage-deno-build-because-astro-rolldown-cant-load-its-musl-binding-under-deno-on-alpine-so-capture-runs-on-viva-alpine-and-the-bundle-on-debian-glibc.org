#+title: the documentation docker image lands as a three-stage deno build — because astro's rolldown can't load its musl binding under deno on alpine, capture runs on viva:alpine and the bundle on debian glibc
#+filetags: :documentation:docker:deno:astro:rolldown:build:integration:

Ship the docs site as a docker image, wired into the build/publish machinery like kajuit and runtime. Small surface on paper; one hard incompatibility underneath, and a long thrash before I stopped routing around it and diagnosed the real cause. Pins [[project_documentation_site]]; the process lesson → [[feedback_reproduce_before_proposing_infra_fixes]].

* the task — mirror kajuit

beef: build and deploy the docs in docker; read how the system handles docker first, then build + integrate.

The stack is a three-image tier, all built from repo root, pushed to =registry.vivalence.org/beef/viva=: root =Dockerfile= → =vivalence/viva:alpine= (base: deno:alpine + tools + the whole workspace `deno install`ed) · =systems/runtime/Dockerfile= (the daemon) · =systems/kajuit/Dockerfile= (the exemplar: `FROM vivalence/viva:alpine AS build`, `deno task kajuit/bundle`, then `nginx:alpine` serving the static build). Wired through root =deno.jsonc= tasks (`*/build|tag|push` + aggregates), =.gitlab-ci.yml=, and the multiplayer =docker-compose.yml=. The obvious first move: make =documentation/Dockerfile= a kajuit-mirror.

* the wall — rolldown can't load under deno on alpine

The kajuit-mirror failed at `deno task documentation/bundle`:
#+begin_quote
Error: Cannot find native binding.
  cause: TypeError: libc.so: cannot open shared object file: No such file or directory
    Cannot find module './rolldown-binding.linux-arm64-musl.node'
#+end_quote
Astro 7 bundles with *Rolldown* (a Rust bundler, per-platform native `.node`, NO JS fallback). On the musl viva:alpine base, deno does not link rolldown's musl binding; the `.node` it does reach is glibc-linked and Alpine has no `libc.so`. Capture (`content/docs/capture.js`, imports `@vivalence/typology`) ran fine — only the *bundle* died. The bundler was the whole problem.

* the thrash — five routes, each rejected

I proposed fix after fix without first nailing the mechanism. beef's escalating cost signal is the spine of this compact:

1. =NAPI_RS_NATIVE_LIBRARY_PATH= env pointing rolldown at the binding.
#+begin_quote
this seems like an ultra weird hack. why is this required?!?!?!?
#+end_quote
2. A debian split with an echoed import-map config.
#+begin_quote
not happy with this still. why this hack? why not just integrate properly?
#+end_quote
3. "Proper integration" — bake `documentation` into the base image so a *full clean* `deno install` would place the musl binding. beef rebuilt; it FAILED identically → my incremental-install hypothesis was *disproved*, not confirmed. (It did establish documentation belongs beside kajuit as a workspace citizen — briefly kept, later reverted.)
4. =gcompat= (Alpine's glibc shim) to load the glibc binding. It BROKE deno itself — `Error relocating /bin/deno: __res_init: symbol not found` — the shim collides with deno's own musl linkage (the base already had to `rm libgcc_s.so.1` once for the same reason). Conclusive: *you cannot have both a musl deno and a loadable glibc rolldown binding in one image.*
5. A node/npm stage (npm resolves musl bindings correctly where deno doesn't). It built *past* rolldown, then died on `Editor.astro`'s `import "codemirror"` — because a `package.json` must re-declare every client dep `import_map` already carries.
#+begin_quote
i dont want to go the way throug a pakcage.json
its antipattern
#+end_quote
Directive that reframed the goal:
#+begin_quote
plan implementing this back within deno without node fallback.
#+end_quote

* the pivot — a fast harness, empirical rungs

Instead of another repo edit + "please rebuild", I built a seconds-fast reproduction: mount `documentation/` + `import_map.json` into a throwaway `deno run npm:astro build` container, tweak, rerun. This turned guessing into measurement.
- rung 1 (pin `@rolldown/binding-linux-arm64-musl` in the import map) → FAILED (deno still won't link it).
- deno on *debian* (glibc) → CLEAN GREEN, 13 pages + pagefind. rolldown's gnu binding loads natively.
The moment I measured, the answer was unambiguous: deno-only requires glibc for the bundler; alpine is a dead end.

* the shape that landed — three stages, zero config gymnastics

A first collapse to two stages forced the workspace onto the bundler stage (capture needs `@vivalence/typology` via the deno workspace; `import_map` has no `@vivalence/*` entries), which meant an inline redeclared-workspace `deno.jsonc`:
#+begin_quote
COPY <<'DENO' ./deno.jsonc … "workspace": [ … ]
WHYY???
ugly
#+end_quote
The fork was real and beef's to pick — capture needs the workspace, astro needs glibc, nginx serves; collapsing any two creates a wart. He chose *three stages, zero config*:
- *capture* — `FROM vivalence/viva:alpine` — the real workspace, NO config, `deno task --cwd documentation capture` → snapshots.
- *build* — `FROM denoland/deno:debian` — glibc; copy documentation (from capture) + `import_map.json` + a one-line `{ nodeModulesDir, importMap }` deno.jsonc (load-bearing: without it in `deno.jsonc`, the `--import-map` *flag* doesn't reach astro's client-dep resolution and codemirror 404s); `astro build` + `pagefind`.
- *serve* — `FROM nginx:alpine` — copy `dist`, listen `:2020`.
Deno-only. No node, no `package.json`, no env hack, no shim, no workspace redeclaration. Built + smoke-tested green end-to-end (root/subpage/pagefind 200, 404→404). Integration: root =deno.jsonc= `documentation/{bundle,build,tag,push}` folded into the aggregates, compose `documentation` service `:2020`, CI lines live. beef was
#+begin_quote
i am ok with building the documentation image standalone!
#+end_quote
so the image stands on its own Dockerfile (its capture stage reuses viva:alpine, as runtime/kajuit reuse the base).

* the root cause — beef's own question closes it

#+begin_quote
why is it that we need to do these import aerobics in documentation but not in kajuit?
#+end_quote
The bundler generation. kajuit pins `deno run -A npm:vite@6 build` → *Rollup 4* (`rollup@4.55.1`), which links its musl binding under deno (or JS-fallbacks) → builds on the musl base, three-line Dockerfile. Documentation is Astro 7 → its own *Vite 8* → *Rolldown* (`rolldown@1.1.5`, Rust-only, no JS fallback) → deno can't load its musl binding on alpine → glibc → off the viva base → hence the import-map re-supply + the capture split. kajuit's `vite@6` pin *is* the "stay on Rollup, avoid Rolldown" move; the day it bumps to vite 7+/rolldown it hits the same wall. Not docs being awkward — docs run a newer, Rust-only bundler that musl+deno can't load.

* the cleanup — my own residue

The abandoned route 3 left drift: the local `vivalence/viva:alpine` image still carried documentation + astro deps (from beef's rebuild) though I'd reverted the base =Dockerfile= to lean.
#+begin_quote
WHAT?
#+end_quote
Owned it, re-leaned the base (verified docs gone, typology intact), rebuilt + re-smoked the docs image against the clean base. `package.json` deleted, scratch harnesses removed, tree tidy. Nothing committed (VCS read-only).

* reflection — measure the mechanism before proposing the fix

Five fixes reached the user before I built the ten-second harness that would have picked the winner on attempt one. Each "why this hack" / "ugly" / "WHAT" was the toll for handing over unverified guesses instead of a reproduced, measured cause. **The rule folded out: for a failing build/infra problem, stand up a fast reproduction and test candidate fixes in it BEFORE editing the repo or asking the human to rebuild — routing around a symptom is how a hack chain starts.** [[feedback_reproduce_before_proposing_infra_fixes]], adjacent to [[feedback_no_hotfix_architecture]] and [[feedback_no_dithering]].
