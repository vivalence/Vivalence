* email per provider, calendar a mode

Asked as a design question, answered with the reasoning the house asks for: mail has one wire
(IMAP/SMTP — Gmail, Outlook, Proton-through-Bridge all speak it), LLM vendors differ on the wire,
so the LLM analogy argued for ONE =service/mail= with vendors as statics presets and per-vendor
services only where a vendor API adds a faculty (Graph for outlook calendar/contacts, Gmail REST
for labels/push). He ruled the other way, and the reason is the faculty: /"calendar as a mode.
email per provider for this reason."/ — the calendar mode needs the vendor API, so the vendor IS
the service (=@commons/service/{gmail,outlook,proton}=), and /"maybe some internal shared smtp
tooling?!"/ — the IMAP/SMTP client is a belt the vendor services compose. The ontology stays ONE
=message.channel.email=; the vendor is what the daemon consumes, at most a =MAIL.account= field.
T2 rows re-cut; =office/calendar= moves from CALL to a mode to design.
