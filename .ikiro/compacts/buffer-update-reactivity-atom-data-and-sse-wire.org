* The server aperture (card EMITTER as a pure update)
A mode exposes a callable server handler via the EMITTER trait
(=mode.aperture.branch("/emit").slurp(mode.cake.emitter)=). An *update* is just an
emitter handler that finds the buffer, reassigns =.data=, flushes, and adds nothing
to the pool — so it emits no new buffer. The change rides the subscription, not the
response.
#+BEGIN_SRC javascript
// registry/playground/card/card.viva.js — traits: APPLICATION, EMITTER
export const emitter = new Vector().open(
  { nature: "/card/bump", input: v.object({ buffer: v.string() }) },
  async (ctx) => {
    const buffer = await ctx.daemon.entities.buffer.findOne(ctx.input.buffer);
    buffer.data = { ...buffer.data, bumped: (buffer.data?.bumped ?? 0) + 1 }; // new ref → dirty
    await ctx.daemon.entities.em.flush();                                     // no pool.add
  },
);
// client: buffer.mode.emit.card.bump({ buffer: buffer.id })
#+END_SRC
KEY REALISATION: spawner's CREATE appeared live via the *emit-response merge*
(client EMITTER trait: =body.buffers = …merge(pojo)=), NOT via SSE. The bump returns
an empty pool → first thing that actually exercises the buffer SSE subscription.

* Root cause — Finn nailed it from the SSE log
With a diagnostic =buffer.subscribe({}, cb)= logging op/id/data, Finn saw the events
land and diagnosed it himself:
#+BEGIN_QUOTE
i see propper events. so problem is that changes to buffer.data arent registered.
buffer.data is not an atom! its static.
…
maybe buffer prototype/dossier treats buffer.data as buffer.$data with a getter and
setter?!
#+END_QUOTE
Exactly right. =terminal.$buffer= is a nanostores atom; =merge()= mutates the held
Buffer instance IN PLACE (=existing.data = incoming=) — the atom's value is the same
reference, so it never fires. The data was correct on the instance; Svelte was never
signalled. A standalone atom holding by reference *cannot* observe in-place mutation;
the only signal that fires on update is =buffer.$entities= (refreshStore).

* The fix — source of truth, not a derive
Finn rejected the earlier view-layer hack hard:
#+BEGIN_QUOTE
i dont want a separate livebuffer. terminal buffer is the source of truth! revert
your hack! retard.
#+END_QUOTE
(Logged in zettelkasten ## Callouts.) The correct fix makes the *entity field*
reactive, so =terminal.$buffer.data= IS live:
#+BEGIN_SRC javascript
// systems/kajuit/src/typology/entities/buffer.js
export class Buffer extends Entity {
  $data = atom({});
  get data() { return this.$data.get(); }          // transparent accessor (vanilla read)
  set data(value) { this.$data.set(value ?? {}); } // write fires the atom → merge notifies
  toJSON() { return { ...super.toJSON(), data: this.data }; } // getter isn't own-enumerable
}
#+END_SRC
Now =merge='s =existing.data = incoming= hits the setter → atom fires. Consumers
*subscribe* to the atom (never =.get()=) via the chain accessor — re-emits on BOTH
active-switch and data-mutation:
#+BEGIN_SRC javascript
// Card.svelte
const data = atom.chain(buffer, "$data");                       // → {JSON $data}
// f.svelte
const activeData = chain(terminals, "$active", "$buffer", "$data");
#+END_SRC
=belt/atom.js= =bind= recursively subscribes through each nested store, so the chain
follows terminal→buffer→$data. This is the canonical transparent-accessor pattern,
not a parallel source of truth.

* nanostores store-type decision (Finn: "what options do we have?")
#+BEGIN_QUOTE
$data = atom({}); nanostores has more than atoms. what options do we have?
… maybe $atom isnt the right nanostore here?! is there a preferable one?
#+END_QUOTE
Verdict: =atom= is correct. The writer (=existing.data = wholeNewObject=) replaces
the whole blob, so:
- =atom(v)= — whole-value =.set=; one set → one notify; fresh ref each set. ✓
- =map(obj)= — earns its keep only if the WRITE is per-key (=setKey=); a wholesale
  =.set= fires identically to atom. No gain here.
- =deepMap(obj)= — only for nested granular =setPath=; data is flat. Overkill.
- =computed= — read-only derived; data is written, not derived.
Store type was never the bug — reading via =.get()= instead of subscribing was.

* ikiro methodology learnings
- *Verify before theorize.* The "is it server-side?" question was settled by a
  hermetic test + a live Bruno run + an in-process warn — not by reasoning alone.
  Reasoning located the candidate (scoped-broadcast ambient owner); evidence cleared
  the server and pointed at the client.
- *Fix the source of truth, never derive a shadow.* The =liveBuffer= =$derived= was a
  consumer-side patch that forked truth; the real fix made the entity field an atom so
  =terminal.$buffer.data= itself is reactive. Reactive-field convention: =$field= atom
  + vanilla getter; consumers subscribe via =chain=, never =.get()=.
- *In-place identity merge has exactly one signal.* Because =em.merge= mutates in
  place (stable identity), reference-equality atoms can't see field changes; only
  =$entities= (refreshStore) and per-field atoms fire. Any reactive surfacing of a
  mutated field must route through one of those.
- *Test the scoped path, not just the easy one.* Coverage existed for unscoped
  literals; the user-scoped (ambient-owner) broadcast — the one production actually
  uses — was untested. The discriminating test is the one that exercises the real wire.
