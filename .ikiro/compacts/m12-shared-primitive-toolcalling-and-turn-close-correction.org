* the correction — turn/close was never the bottleneck

Beef, verbatim, rejecting step 3 outright: /"false. why would it be an issue
to drain into turn close? where do we construct the environment that does
the tool calling? i need a conoisseur asessment here on architecture level.
what should we want? is there another way to get mid-stream buffers out? a
more elegant way?"/

Traced the actual cadence instead of assuming:
- =soma.drain= (=belt/soma.js:28=) synthesizes a FULL turn envelope
  (=/turn/open= → =/part/*= → =/turn/close=) for the SYNTHETIC tool-result
  turn, once per ROUND — not once per whole exchange.
- =harnessed.js='s dialogue branch persists a Turn entity AND forwards the
  packet to the client on EVERY =/turn/close=, not just the final one. A
  10-round tool-calling loop already streams up to 20 turn-closes live.
- =executeTools= (=cortex.js:19=) never stringifies tool output —
  =results.push({ type: "tool_result", id, output })=, =output= raw.
- =soma.drain= never forces a string either — non-string part values pass
  straight through to =delta[key]= whole (=soma.js:34-41=).

Conclusion: a tool handler returning a raw =Yield= already survives
untouched into a =/part/delta= packet, same round, same tick. The delivery
mechanism was never missing — step 3 invented transport that already
exists. Retracted. =Packet.Any= doesn't grow. The real gap re-scoped to:
Pool-awareness inside =executeTools= (classify via the SAME shape table
=Pool.add()= already has, thread-bind + flush buffer-shaped output like
=EMITTER= trait does) + =renderLeaf= (=cortex.js:64=) currently discarding
every mid-round tool result, only returning the final turn — case 1's actual
blocker, not a transport gap.

Where the tool-calling environment lives, precisely: ONE =executeTools=
(=cortex.js:19=), shared by =streamLeaf:41= and =renderLeaf:64= — not
duplicated per leaf, don't build two.
