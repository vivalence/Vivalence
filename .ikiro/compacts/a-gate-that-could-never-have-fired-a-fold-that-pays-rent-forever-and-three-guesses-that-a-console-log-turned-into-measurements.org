* Arc

** the harness had three lines, and one of them was a wish

Beef asked whether the harness already receives what =doctor()= pulls. It did not. The whole
of it was =system.hello=, three sentences, the third reading /"Anything about this machine
comes from viva_doctor"/ — the mode asking the model, in prose, to spend a round on a fact it
could have been handed. Prose is the weakest instrument available and this is the third time
this quest has caught itself reaching for it.

=doctor()= is not promptable as-is: it returns =ledger.environment= (every variable's VALUE),
=registry.modules= and =ledger.instances=, and it =await=s two =paladin.ledger.*.list()=
filesystem walks. Put that in the harness and every turn pays two walks.

So M0 is a PROJECTION, not a paste. =standing(ctx)= reads state already in memory —
synchronous, no walk — and =machine()= renders it as four kinds of line. 429 characters, inside
the cache-marked prefix, free after the first write.

** the gate beef struck was also a gate that could never have fired

The first draft let =viva_doctor= ARM the full fold: the tool returns a receipt, the harness
sees the call in the thread's history and installs =system.diagnostics= from the next turn on.
Beef: /"why only on turns we want doctor??! either this belongs into the correct harness path
or this is a stupid gate. i'd rather attach this as a tool called on demand."/

He was right on the shape, and the reasons are worse than the one he gave. It pinned the
harness to a tool NAME as a magic string; it inferred intent from transcript archaeology; it
was sticky with no way off; and it was CIRCULAR — it read history to learn the model had
asked, while that same history already held the answer the tool could have returned.

**Then the probe showed it was broken too.** =armed(ctx.hallucination.turns)= reads a value
the mode harness does not have: the probe printed =turns: []= on a request where four user
turns already sat in the db on that thread, and again on a fresh thread, and again after a
restart. Three measurements, one verdict — =P-order= is FALSE.

The reasoning that produced it: =/dialogue= sets =ctx.hallucination.turns= at
=harnessed.js:97-108=, =mode.module.harness= is slurped at =:157=, AFTER it, therefore the mode
harness sees a populated =turns=. Registration order is real. It is not execution order. A
root-level =use= runs before every branch-level =use= on the same path no matter when it was
registered, because dispatch walks the trie root-first.

So the feature would have compiled, type-checked, passed review and silently done nothing
forever. Beef killed it for being ugly; it was also dead.

** the environment: two audiences collapsed into one projection

=ledger.environment= was =Object.fromEntries(keys.map((key) => [key, paladin.env.get(key)]))=.
No secret is in there — =Paladin.split()= files every =SECRET_*= into a different =Env= — but
it is the machine's whole environment written into a turn row for the life of a thread and
shipped to a provider.

Beef, twice. First: /"the mode can read paladin. why not just pull from there? thats what he
is for."/ I answered with a two-audience split — the fold keeps values for =App.svelte=, the
tool projects. Then: /"we can standardize really. no need for two."/

One projection wins. =variables(env = paladin.env)= returns ={key, set}=, the FOLD itself takes
it, and no consumer can leak a value because no consumer is handed one. The App's band loses
nothing that mattered: it already prints /"N resolved, M unset"/ and the =requirements= list
under it already names every unset slot.
