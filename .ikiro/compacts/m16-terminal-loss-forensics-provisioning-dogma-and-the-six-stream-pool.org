* the reversal — no server bug, a six-stream pool

beef: /"on chrome i cant click on the mode name. not a problem in
firefox?!?!?!"/ Drove the app live in Chrome: healthy daemon answered
EVERY suspect query shape in <100ms (populate variants, absent-id
findOne, 6-way concurrent, /batch) — while a fresh tab's =auth/verify=
sat pending forever next to beef's open tab. Root: 3 daemons × 2 SSE
subscribes = exactly 6 live streams to :2501 (HTTP/1.1) = Chrome's
per-host pool, shared across the whole profile → every later fetch
queues forever. Boot's own finds run BEFORE subscribes open, hence the
partial-wedge illusion. Firefox "worked" only where a stream happened
to be dead. Every hang of the day — original findOne, thread/find,
thread/create, cross-tab verify — one mechanism. Quest fork 6 RESOLVED
(the esbuild/write-lock hypothesis was wrong; superseded).
