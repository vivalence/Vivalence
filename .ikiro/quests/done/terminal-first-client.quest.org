* Intent

The client is an incoherent mess. Lighthouse setup half-baked, client setup half-baked, fake multi-lighthouse pretense, scattered =await import("$client")= gymnastics, boot sequence leaked into SvelteKit routes. No design philosophy.

Terminal-first: the terminal is the primary client entity. Like iTerm processes, emacs buffers, browser tabs. Everything is a terminal. Login is a command. The lobby is a command. Settings are a terminal. The REPL is the shell.

** Desired End State

User opens vivalence.com/. One URL. Sees a REPL prompt. Types commands. =login <url>= connects a lighthouse (inline form if no saved session, instant reconnect if hydrated). =list= shows available modes. =open flashcard vocabulary= spawns a game terminal. Switch between terminals via modeline or keyboard. The REPL is always terminal 0.

No login page. No lobby page. No SvelteKit route tree. No loader gate. No discover gate. No TLA. =new Client()= is synchronous. All async work happens through REPL commands.

** Key Design Decisions

- *Terminal is the primary entity.* Not daemon, not lighthouse, not buffer. Terminal.
- *Multiple lighthouses, for real.* =client.lighthouses= is a Map. You can connect to N lighthouses. No hardcoded single-lighthouse pretense.
- *REPL is a terminal phase.* Terminal has phases: REPL (command line), STREAM (game buffers), etc. REPL is the default.
- *Commands return strings or components.* The command vector's effects return plain strings (rendered as text) or ={component, props}= objects (rendered via =<svelte:component>=). Login returns an inline form component. List returns a daemon listing component.
- *Command vector is assembled, not declared.* Base commands (help, clear) are always present. Client commands (login, list, switch) added at boot. Daemon commands (open) added when daemons load. Mode commands (submit, skip) added when a session starts. Same pattern as daemon aperture growing from mode traits.
- *Everything at root.* =vivalence.com/=. No routing. SvelteKit routes moved out of src/.
- *No TLA.* =export const client = new Client()=. Synchronous. The client exists immediately. Commands do the async work.
- *Auto-exec from env.* If =PUBLIC_VIVA_LIGHTHOUSE_REMOTE= exists, the REPL evaluates =login <url>= as its first command on mount.
- *Invocation pattern.* Signal from input, steer.invoke, steer.minimal. Commands nest naturally because Vector branches.

** Architecture

*** Client

Root singleton. Holds the collections.

#+begin_src
Client
  .lighthouses     Map<url, Lighthouse>
  .terminals       Map<id, Terminal>
  .active          terminal id (null = repl / terminal 0)
#+end_src

*** Terminal

The primary entity. Owns a command vector and phases.

#+begin_src
Terminal
  .commands        Vector (the command tree)
  .phase           "REPL" | "STREAM" | ...
  .history         [{command, output}]  (REPL entries)
  .stall           Stall (buffer queue, for STREAM phase)
  .daemon          current daemon (when in session)
  .mode            current mode
  .thread          current thread
  .intent          current intent
#+end_src

*** Command Vector

Flat or nested. Resolved via Signal + steer.invoke.

#+begin_src
commands.open("/login", async (die) => { ... })
commands.open("/list", async (die) => { ... })
commands.open("/help", async (die) => { ... })
commands.branch("/open").open("/:mode", async (die) => { ... })
commands.branch("/open").open("/:mode/:intent", async (die) => { ... })
#+end_src

User types =open flashcard vocabulary=. Input becomes Signal. Vector matches =/open/flashcard/vocabulary=. Effect spawns terminal with that mode+intent.

*** REPL Loop

Read: input field at bottom of screen.
Eval: =new Signal(input)= → =steer.invoke(commands, signal, steer.minimal)= → =cast({signal})=.
Print: push ={command, output}= to history. Output is string or ={component, props}=.
Loop: clear input, focus.
