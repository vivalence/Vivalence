#+TITLE: Client Typology Reorganization
#+AUTHOR: Vivalence
#+DATE: 2026-04-05
#+STATUS: ACTIVE

* Intent

The client's typology evolved ad hoc. Lighthouse treated as entity. Prototypes mixed concerns. Entities were enriched POJOs, not schema-aware. Dual init paths (client.js + client.wafer.js). Dataspace was two loose RemoteRepositories. Now: design what evolved.

** Desired End State

Client architecture mirrors daemon's entity model. RemoteEntityManager (EM) sits below RemoteRepository — owns identity map, unit of work, snapshots. Repos delegate identity to EM. Dataspace (≈ MikroORM.init) births EM + repos from daemon's /datamap schema. Terminal is the user-centric universe. Thread is the URL primitive. Lighthouse is a network topology node (not "auth/"). Vectors all the way down — no imperative client.js.

** Key Architectural Decisions

- *EM below repos, not above.* MikroORM architecture: EntityManager owns IdentityMap + UnitOfWork. Repositories are thin delegates receiving the EM in constructor. NOT the inverse.
- *Auth is a connection concern.* Lighthouse provides authorized connections to daemons. Scoping flows through auth middleware on the connection, not through where-clause injection. No ScopedRepository.
- *RemoteRepository exclusively managed.* No unmanaged/standalone code path. Every repo on the client is registered with an EM via repo.manage(). Old put() commented out.
- *Approach A for MikroORM.* EM-shaped API over RemoteRepository. No actual MikroORM import (core has hard Node deps: fs-extra, globby, esprima, node:util). Identity map + dirty tracking + batched flush built into EM.
- *Schema from wire, not hardcoded.* Entity classes are just constructors with defaults. Relationship metadata comes from daemon's /datamap (via strip()) and gets wired at runtime.
- *RemoteEntityManager + RemoteRepository in typology.* Both are generic primitives, not client-specific. Tested as a unit in typology.

** Terminology

| Term      | What                                                        |
|-----------+-------------------------------------------------------------|

* Architecture

** RemoteEntityManager ↔ RemoteRepository

#+begin_src
RemoteEntityManager (owns identity map, UoW, snapshots)
  ├── em.register("mode", repo)  → repo.manage(em, "mode")
  ├── em.merge(name, raw, kind)  → canonical entity reference
  ├── em.cast(name, raw, kind)   → hydrate relationships, then merge
  ├── em.identity(name, ref)     → resolve from identity map
  ├── em.drop(name, id)          → remove from map + store
  ├── em.persist(entity) / em.remove(entity) / em.flush()
  └── em.fork()                  → fresh EM, same connection + schema
        RemoteRepository (thin delegate)
          ├── repo.find() → connection.call → em.cast() → entities
          ├── repo.merge(raw) → em.merge()
          ├── repo.cast(raw) → em.cast()
          ├── repo.drop(id) → em.drop()
          ├── repo.$entities → em.stores[name] (reactive atom)
          └── repo.findOneLocal() → $entities query
#+end_src

*** Key learnings

- ScopedRepository was wrong. Auth is connection-level (lighthouse pattern), not query-level.
- MikroORM core can't be imported in browser (fs-extra, globby, esprima, node:util at top level).
- strip() skips abstract entities. Concrete schemas (LiteralDomain, SymbolConcrete, BufferConcrete) appear fine.
- RemoteRepository persist test was pre-existing failure (nanostores/persistent test engine issue), not caused by changes.

*** Design

client.wafer.new.js defines the full client lifecycle as a Vector:
- /birth: creates Connection + Lighthouse from variant.lighthouseUrl
- /hydrate: restores auth from localStorage
- /idle: exit point — lighthouse exists, may or may not be authorized
- /discover: if authorized, casts lighthouse wafer (which discovers daemons + births Dataspaces)
- /ready: exit point — fully populated

client.new.js casts to /idle at module scope via TLA. Layout decides whether to discover.
Named .new.js to coexist non-destructively with current client.js/client.wafer.js.

* Decisions

- Approach A (EM-shaped API, no MikroORM import). Migration path to B (real MikroORM with custom driver) or C (client-side SQLite) preserved — the EM interface is identical.
- RemoteEntityManager + RemoteRepository in typology, not client. They're generic primitives.
- RemoteRepository exclusively managed — no unmanaged code path on the client.
- Entity classes are just constructors with defaults. No schema declarations — schemas come from daemon's /datamap via strip()/wire().
- URL shape: /viva/:daemonSlug/:threadHash/...
- Thread is the primary URL primitive. Terminal mounts a thread.
- Modline is the primary control/navigation primitive.
- Lobby contract with thread/intent still murky — parked.
- Lighthouse daemons as Map (keyed by slug) — enables O(1) lookup for URL routing.
- client.js is TLA cast to /idle — layout handles discover. Same two-step pattern as before, just vectorized.
- .new.js naming for non-destructive coexistence during migration.

* Gaps

- flush() not tested against actual /batch endpoint (scenario doesn't wire batch)
- persist() (localStorage) interaction with managed EM not tested
- subscribe() (SSE) interaction with managed EM not tested
- Literal/symbol repos not in entity registry (abstract base — concrete per daemon)
- Fork doesn't carry registered repos — caller must re-register. Intentional? Or should fork replicate repo registration?
- Thread resolve hook not tested (needs auth context — deferred to M5 browser verification)
