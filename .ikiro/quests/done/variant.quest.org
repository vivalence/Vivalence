#+TITLE: Variant — Root Manifest for a Vivalence Deployment
#+AUTHOR: Vivalence
#+DATE: 2026-05-18
#+STATUS: ACTIVE

* Intent

Collapse the manifest taxonomy. Drop =type: "circuit"= as a deployment-layer
artifact. Promote =type: "variant"= as the single root manifest that declares
a vivalence deployment in full: runtime + clients + services + daemons +
environment + mountpoint.

A variant is one self-contained deployment description. Paladin reads one
file at the variant root and resolves everything either inline or via
references (registry slugs / filesystem paths / env vars).

** Desired End State

- One manifest type: =variant=. (=type: "daemon"=, =type: "service"=, etc.
  remain as inner-config types — they describe pieces inside the variant.)
- A variant can be expressed inline (whole deployment in one file) or
  hybrid (variant points at registry slugs / paths / env vars).
- =paladin.variant= ends up the same shape regardless of how it was declared.
- =viva install variant <slug>= materializes the variant into a destination
  declared by the variant module (or overridden by path arg / env).
- =viva start <variant>= spawns the runtime against that materialized variant.

** What's wrong with =circuit=

The =circuit= manifest type sits between =variant= and =daemon= as a
filesystem-grouping artifact (a "file in =circuitry/=") rather than a
semantic one. testament/variant/circuitry/test-system.viva.js declares
runtime+clients but is typed =circuit=. That's a naming accident — the file
is variant-level, not circuit-level. Eliminating =circuit= removes the
ambiguity.

* Compiled End-State — =paladin.variant=

Single source of truth after paladin resolution. Identical shape regardless
of how it was declared.

#+begin_src javascript

* Manifest Shape — =type: "variant"=

Each field has TWO valid forms: *inline* (literal config object) or
*referenced* (string slug → vip.accio; or path → filesystem load).
Paladin normalizes to inline in =paladin.variant=.

** Required

#+begin_src javascript
export const manifest = {
  owner: "@vivalence",
  type: "variant",
  slug: "<slug>",
  version: "<semver>",
};
#+end_src

** Optional install-time

=path= — where ghost materializes this variant. Expanded:
- absolute path → literal
- =~/...= → =HOME/...=
- =$VAR/...= → =Deno.env.get(VAR)/...=
- omitted → fall back to ghost arg, then =$VIVA_VARIANTS_ROOT/<slug>=

** Optional runtime declarations

| field | inline | referenced |
|-------+--------+------------|
| =runtime= | =Object= literal | =String= slug (vip.accio + extract =.runtime=) |
| =clients= | =Object= keyed by slug | =Object= mapping slug → string ref |
| =services= | =Array= of inline objects | =Array= of bare slug strings or objects |
| =daemons= | =Array= of inline daemon configs | =Array= of bare slug strings, or local path strings |

When omitted entirely: =runtime=, =clients=, =services=, =daemons= → empty.

** Environment + mountpoint are NOT variant-file concerns

A variant file =import paladin from "@vivalence/paladin"= at top, then reads
=paladin.env.get(...)= / =paladin.secret.get(...)= in its body. By the time the
variant is imported, paladin has *already* loaded env from:

- system =Deno.env=
- =<variant>/environment/*.jsonc= (via =populate.environment=)
- repo =.env= fallback (for citizen mode)

Letting the variant *declare* its environment creates a chicken-and-egg
problem: the variant file is imported once, evaluated top-to-bottom, and
=paladin.env.get= calls inside it would resolve against whatever was loaded
BEFORE the file ran — not anything declared by the file itself.

So: variant files do not export =environment= or =mountpoint=. The variant
*directory* still contains =environment/*.jsonc= + =mountpoint/= as
sibling subdirs. Install copies them verbatim from registry source. Paladin
populates from them as today.

* Paladin Resolution Flow

Environment populates first (today's behavior, unchanged). Variant marker
loads against an already-populated paladin.env.

#+begin_src
paladin.ikiro
  populate.env               EXISTING: system Deno.env → paladin.env / .secret
  populate.scopes            EXISTING
  populate.environment       EXISTING: <variant>/environment/*.jsonc → paladin.env / .secret
  populate.vip               EXISTING
  resolve.variantManifest    NEW: find <variant>/*.viva.js with manifest.type === "variant"; import; assign to paladin.variant.module
  resolve.compose            NEW: normalize each declaration into paladin.variant.{runtime,clients,services,daemons}
                              for refs (string slugs):  paladin.vip.accio({type, slug}) + extract relevant export
                              for refs (local paths):   dynamic import relative to variant root
                              for inline objects:       use as-is
  resolve.consumables        EXISTING
  integrate.statements / .publish / .questions   EXISTING
#+end_src

Mountpoint stays as a paladin scope (=paladin.scope.mountpoint=) — resolved
from env vars or =<variant>/mountpoint/= today, no change.

** Backwards compat

If no variant-typed file at root, paladin falls back to today's circuitry-
scanning behavior (reading every =<variant>/circuitry/*.viva.js= and folding
their =runtime/clients/services/daemons= exports). This lets old
=testament/variant/= deployments keep working until migrated.

A legacy circuit file's =manifest.type = "circuit"= will be re-classified
to =variant= during migration; in the interim, fallback handles them.

* Install Flow

#+begin_src
viva install variant <slug> [path]
  1 cake = paladin.vip.accio({owner, type:"variant", slug})
  2 destination = ctx.argv[1] || expand(cake.path) || $VIVA_VARIANTS_ROOT/<slug>
  3 source = dirname(cake.mount.absolute)        ← whole variant dir, including environment/ + mountpoint/
  4 copy source tree → destination               (verbatim: marker + colocated daemon files + environment/ + mountpoint/)
  5 return materialization manifest              (lists files copied)
#+end_src

Environment + mountpoint live as filesystem subdirs of the source variant.
No special install-time materialization — just copy. The variant author
maintains =environment/{variant,services,secrets}.jsonc= templates in the
registry source.

* Start / Stop / Status

Unchanged in spec from earlier ghost work. The variant resolver (=lib/variant.js=)
calls =paladin.vip.accio({type:"variant", slug})= and reads =cake.path= for the
installed location.

* Migration Path

   existing =resolve.circuitry= + =resolve.variant=).
2. Promote =testament/variant/circuitry/test-system.viva.js= → root
   =testament/variant/test.viva.js= with =manifest.type = "variant"= and merged

3. Once all live variants have a root variant file, deprecate
   =resolve.circuitry= + =resolve.variant=.
4. Drop =manifest.type === "circuit"= as a deployment artifact (still valid for
   in-process structural use if any).

* Vocabulary

| Term | Definition |
|------+------------|
| variant | Root deployment manifest. Single file per deployment. =manifest.type = "variant"=. |
| variant root | Directory holding the variant file + materialized =environment/= + =mountpoint/=. |
| inline | A declaration expressed as a literal object/array inside the variant file. |
| referenced | A declaration expressed as a slug string (→ vip.accio) or path (→ filesystem). |
| materialized variant | The variant tree on disk after =viva install variant=. |
| variant marker | The =<slug>.viva.js= file at variant root with =manifest.type = "variant"=. |
