* the contract

*ONE rule: an effect returns ={condition, output}=. =output= is one bag whose keys are
payload words (=message=, =object=) or entity type names (=buffer=, =literal=, =symbol=, …).*

  output: {                   // the payload — ONE bag, sparsely filled

** why =condition= stays OUTSIDE =output=

It reports *whether there is an output*. =EXHAUSTED= means the bag is empty — the verdict
must be readable without reading the bag. Structurally: =Pool.drain()='s three-way
discriminator and =is.yieldish='s sniff both need a top-level probe point, and a status
cannot live inside the thing whose existence it reports.

This is the one place the design does not take *"just an input and an output"* literally.
=condition= is the ENVELOPE; =output= is the PAYLOAD.

** the governing distinction — a RECORD is not a BAG

*=output= is a BAG. =Request= is a RECORD.* They must NOT be made symmetric.

- production is OPEN — you cannot know what a tool yields, so =output= is sparsely filled,
  open-keyed, and SNIFFED.
- the provider contract is CLOSED — every key has one known role and one provider mapping,
  so =Request= is fixed, exhaustive, and AUTHORED.

Making =Request= bag-shaped would import sniffing into the one place the shape is already
known. So the answer to *"maybe request and response are different in nature"* is: yes,
deliberately, and that difference is the design. But =system= still gets promoted — for a
different reason, below.

** (a) =cache= is NOT =settings=

Different natures. =settings= is PARAMETRIC — it maps ~1:1 onto provider params (=maxTokens=
→ =max_tokens=, =temperature= → =temperature=). =cache.marks= is STRUCTURAL — it maps onto no
param at all; it instructs the TRANSLATOR where to place =cache_control= inside content
blocks (=anthropic/provider/translate.js=: =if (marks.has("context") && system.length)
system.at(-1).cache_control = {type:"ephemeral"}=). Folding it into =settings= would make
=settings= mean two things — the exact disease this quest treats.

Deeper: =cache.marks: ["context","tools"]= naming SEGMENTS BY STRING is a workaround for
segments not being addressable objects. Once =system= is a real array of sections (below),
a mark belongs ON the section and top-level =cache= may dissolve entirely. Folding it into
=settings= now would cement the workaround. *Keep it separate; expect it to migrate.*

** (b) two different things are both called =tools=

| where | what | crosses the wire |
|-------+------+------------------|
| =Request.tools= | the CATALOG — =[{name, valence, input}]= from =declarations()= | YES |
| =requestConfig.tools= | the invocable =Vector= — what =dispatch()= calls | NEVER |

Both are passed to the same function, in two adjacent objects:
=session(faculty, avenue, hallucinationRequest, requestConfig)=. Same word, two meanings,
one seam apart. A sibling of the four-=output= disease.

*Fix, minimal and register-free:* hoist the Vector to its own parameter rather than rename
either — =session(faculty, avenue, request, policy, tools)= and =render(faculty, request,
policy, tools)=. =Request.tools= keeps the provider-facing wire name it has earned; =policy=
goes back to being only =rounds/backoff/span=. No new vocabulary.

*Should the catalog live in =turns=? No — and the provider evidence inverts the intuition.*
A turn is a TRANSCRIPT EVENT WITH AN AUTHOR (role + parts, positioned). Tools are AMBIENT
CAPABILITY, available across all turns, authored by no one at no position. Empirically:
anthropic · openai · openrouter · gemini ALL take tools as a top-level array and NONE
accepts them inline in messages. Providers *disagree about system and agree about tools* —
so =system= is the one that could be positional, and =tools= is the one that cannot.

** (c) =system= gets promoted to a Request key — but not for symmetry

Today the system content makes a round trip that every provider then undoes:

#+begin_example
context.system(…)  →  compile() mints [{role:"system", parts:[…]}]  →  prepended to turns
                   →  provider translate PULLS IT BACK OUT into the top-level system array
#+end_example

That trip is pure loss. =compile()= joins every section into ONE text part (a turn has parts,
and there is no per-section identity left), which is precisely why a cache mark cannot
land on the stable persona block while volatile state changes behind it. The
representation cannot hold what system needs.

#+begin_src js
Request = { system?, turns, tools?, settings?, output?: { schema? }, cache? }
#+end_src

=system= = an array of SECTIONS that keep their identity. Fork A (multi-part compile) then
falls out free rather than being a separate fight, and =translateTurns= stops hoisting.
NOTE: this is an INPUT-half change and does not have to land in the same bracket as the
output contract — but the two forks stop being independent once =Request= is opened, so
decide the order before starting.

** merge rules (the snowball semantics)

| key | at a PART | at the RESPONSE envelope |

| =object= | that tool's structured return | last non-null wins |

*=condition= does NOT roll up.* Envelope =condition= is the RESPONSE's verdict (did the run

** the projection frame (the thread side of the same law)

The Request is a PROJECTION of the thread; the caller (harness) is the projector. Three
channels, never mixed:

| channel | carrier | discipline |
|---------+---------+------------|
| HISTORY — what happened | =turns= | append-only, replayed, compaction later |
| STATE — what is | =system= sections | keyed, re-derived per invocation, byte-stable unless data changed |
| ACTION — what can be done | =tools= | the ONLY write path |

Rulings that fall out (settled with beef over the multi-turn blob):

1. realtime db data: STATE section if it shapes every utterance (memory strengths), TOOL if
   on-demand. Litmus: think-before vs ask-when-needed.
2. buffers in context (email composer, game state): READ = projected section, WRITE = a
   =buffer.update= tool (plain mikro update — beef confirmed) — the file model, in JSON land
   (beef: /"they live in Python land, I live in JSON land"/). SELECTION FLIPPED on beef's
   own insight: *default = the thread's live buffers project* — buffers FK the thread, so
   agent-generated buffers stay in context and re-derive with fresh data every request; the
   thread IS the selection. Section key = =buffer:${id}=, content = =buffer.data= JSON raw —
   byte-identical unless data changed, unchanged buffers cost zero cache. Mode refines by
   overwriting the section KEY in its middleware — no new declarative surface.
3. output entities re-entering context: HAPPENED rides the replayed transcript's tool_result
   parts; IS projects as a state section. Never re-inject bags.
4. turn↔buffer SQL relation: NO — part-level provenance (m26) already records it; both FK
   the thread, that is the shared spine.
5. long-running agents: compaction = fold old turns INTO a state section (history → state);
   the turn-repository =fold(tract, judge)= design is that slot. DEFERRED, slot named.
6. branching/delegation: a tool whose execute spawns a hallucination on a child thread; the
   child Response returns as the tool's yield. Already composes — nothing to invent.

Industry-proofing: the frame maps 1:1 onto the provider convergence (messages=history,
system=instructions+state, tools=actions, MCP resources=readable state); dialects stay in
