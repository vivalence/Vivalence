** Candidate state (carried from M11 fork 6) — SUPERSEDED by Design below

- =module= — OUT (beef named the conflict: shadows the real JS/ES module
  concept in a system full of them). REOPENED: the conflict objection was
  against naming a registry TYPE "module"; naming the READ RESULT module
  aligns with what it literally is (=read.viva= does =await import(path)= —
  the cake IS a JS module namespace + manifest + mount).
- =crate= — Cargo's word for "a compiled unit", on-brand for the
  package-manager vocabulary, no collision found.
- =parcel= — plain English "a bundled thing", no collision, weak thematic tie.
- =declaration= — already used locally in =vip.js= for the package-cake read
  specifically; reusing for EVERY read blurs that distinction.
- =pkg= — the "taken" objection is MOOT post M11 fork 7 (those bindings died
  unborn), but naming the READ RESULT after the package type repeats the
  mode/module-type naming mistake fork 7 corrected.

** Design (beef dictation, loaded — name still unpinned between two layouts)

beef (verbatim, voice): *"the cake term we drop completely in the
[daemon], we move everything that's [mode] into kernel. We still have
[daemon].modes.type.slug, but it's computed from the array of kernel
modes. Then in the declarations where we define the... that's where we
use the modules in the variant, for example. There, what we called
module, I would rename to mode. And then the thing that we named cake
... the [live] instance of a thing, I would name that module. Or
another way to semantically lay this out would be to name the live
instance the mode, and the reference the module. I'm not sure, but
that's the general idea."*

Structural change (both layouts agree):

- =cake= dies completely in the daemon.
- viva.js daemon declaration: =modes: []= array MERGES into =kernel: []= —
  one array of references (domain/ontology/corpus/game/tactic/... all in).
- =daemon.modes.<type>.<slug>= SURVIVES as a COMPUTED index over the kernel
  array; today's special =daemon.kernel = {domain, corpus, ontology}= subset
  dissolves into that index.

** Settled ontology (pinned over four exchanges)

TWO principles, non-overlapping:

1. *Residence disambiguates; one noun per concept across the wire.*
   Declaration residence = everything is a reference; live residence =
   everything is an instance. (Caught by beef when a first draft split
   kernel(declaration)/modes(live) as if residence justified it: *"the
   principle is inconsistent ... Not a fan"*.)
2. *Mask keys are SEMANTIC (role); lookup surfaces are LEXICAL (type).*
   (beef: *"When we define a datamap mode or a hallucinator mode, we use a
   semantic, not a lexical name for the property. But if we would use
   modes in the [daemon] mask, that would be a lexical name."*) This is
   what reactivates =kernel= — it names the ROLE of the array
   (constitution), not the type of its contents. =kernel= vs =modes= is
   NOT residence-polymorphism: constitution vs directory are two concepts.

| term   | meaning                                                          |
|--------+------------------------------------------------------------------|
| mask   | declaration — "turn this into an instance": {module, statics…}   |
| module | loadable/loaded unit — mask.module ref → accio → loaded module   |
| mode   | live citizen                                                     |
| kernel | the constitutive array — SEMANTIC mask key in variant/daemon     |
| modes  | =daemon.modes.<type>.<slug>= — LEXICAL lookup index, derived     |
| kinds  | type→prototype registry (was daemon/kernel.js =modes= export)    |
| cake   | DEAD                                                             |

- Mask key grammar, all semantic: =datamap= (storage) · =lighthouse=
  (presence) · =hallucinators= (AI providers) · =services= (sidecars) ·
  =kernel= (constitution). =modes:= as mask key would be the lone lexical
  key — rejected on principle 2.
- Array entries are MASKS; bare string = shorthand for ={module: string}=
  (beef: *"what we reference here as single strings, we could also
  reference as objects with further configuration ... what is now the mode
  string ... would be inside of a module key. So that's the general
  structure of the mask."*).
- =mask.js= never dropped the key: =prototypes/mask.js:3=
  =// {manifest, kernel, modes, services, ...}=, =this.kernel = []=.
