** The doctrine amendment (the decision trail)

*** one grammar (=shard.context=), two time-characters
The server composes =ctx= per request — a transient middleware onion, built and
torn down each call. The client holds the SAME spine (daemon→thread→buffer) as
a STANDING reactive structure. The server UNFOLDS ctx (ana, per request); the
client HOLDS the folded ctx as a live cursor. Same grammar, opposite time.

The proof the client already speaks this grammar
(=systems/kajuit/src/typology/prototypes/dataspace.js:22=):

  .use(shard.context.attach("dossier", dossier))
  .use(shard.context.attach("repository", repository))

#+end_src
plus =entities/daemon/dossier.js:23= — =vector.use(shard.context.bind("daemon", daemon))=.
The client's ENTITY-resolution layer is pure server-grammar middleware. beef's
*"the client doesnt [have middleware]"* is true only of the DOM/render layer —
and that layer SHOULD stay middleware-free.

*** the two laws, named by their server duals
| server              | character                          | client dual        | carries                         |
|---------------------+------------------------------------+--------------------+---------------------------------|

- =attach= ⟷ =setContext= : a capability provided once, stable for the scope's
  life. On the client: =LIGHTHOUSE= (auth+daemons) · =BRIDGE= (layout) · =BOX=
  (audio) · =TERMINALS= (the collection). The world the client may touch.
- =bind= ⟷ =chain= : a capability re-resolved on each use — the server per call,

  =chain(terminals, "$active", "$thread", "$buffers")=. You do not provide a
  moving target down a static tree; you subscribe to it.

*** the three DOM laws (M17's correction to M16's "contexts narrow")
beef corrected the first draft (which made props primary): *"i think the props
for buffers/apps are a fallback. the real source of all these props ought be
contexts."* Correct — and it maps straight onto the stolen canon: =getContext=
walks the component OWNER TREE, which IS Solid's =context= field (provide-at-
scope, read-at-leaf). Context is the source; props are the escape hatch for
leaves that left the tree.

1. *Context is the source — within the host bundle.* =setContext= at each
   spatial boundary that exists as a DOM subtree: =+layout= (the DECKS — the
   world) · the active-cursor scope (=TERMINAL= — the active terminal, consumed
   by every host-side surface: Frame, Dock, Phase, D/E/F). A host-side leaf
   =getContext=-s what it needs; nothing re-reads =$active=.
2. *Props are the BOUNDARY TRANSPORT — across the buffer-bundle line.* A =.url=
   mode-app is NOT a Svelte child of Frame: =application.js:20= esbuilds it into
   a SEPARATE bundle (own importmap {typology, schematics, shared, drapes,
   kajuit-typology}, own Svelte runtime, typology-only — NOT =client.js=). So
   =getContext= cannot cross that line (separate Svelte instance; two
   =Symbol("buffer")= never match). Frame reads =getContext(TERMINAL)= + its
   =terminal.$buffer=, then hands =({terminal, buffer})= as PROPS across to
   =module.default(dom, {…})= (=Frame.svelte:36=). Props are the CTX HANDOFF at
   the client's handler boundary — the dual of the server handing =ctx= to a
   handler, and of =strip=/=messenger= across the network. The value ORIGINATES
   in context; it rides a prop only because the app is a separate compilation.
   (A =.Component= app, if ever host-bundled, reads context directly — latent
   path; every live registry app is =.url=.)
3. *Entities narrow by DERIVATION (the DATA axis, orthogonal to §1/§2).*
   Mode→Thread→Buffer→Turn is computed filters over daemon-wide atoms, never
   nested providers: =thread.$buffers = computed(daemon.entities.buffer.$entities, by thread.id)=
   (=thread/dossier.js:25=). The DOM is FLAT (=+page.svelte= — panels A–H are
   absolutely-positioned siblings; D/E/F never nest under a thread node), so no
   NEW provider nesting can be harvested for THREAD/DAEMON/MODE/BUFFER — they
   stay ATTRIBUTES read off =TERMINAL= (=terminal.thread=, =terminal.daemon=,
   =terminal.$buffer=, =buffer.mode=). The derivation runs on typology atoms, so
   it crosses the bundle line for free.

So the honest grammar is THREE layers, not a narrowing tree:
- *decks* (attach-dual, host bundle) — the world, at =+layout=.
- *TERMINAL* (attach-dual, host bundle) — the active cursor, at its scope,
  consumed by every host-side surface; sourced from =TERMINALS.$active= + =chain=.
- *the bundle handoff* (props) — Frame → the isolated =.url= app; ctx sourced
  from context, transported as props because the app is a separate compilation.
Only ONE new symbol falls out: =TERMINAL=. =BUFFER= is dropped — its sole
consumer is the cross-bundle app (props), and host-side it is just
=terminal.$buffer=.

*** the throughline (connoisseur)
One structure — =shard.context=. One law made visible — *the client is the
server's per-request ctx made standing.* =attach/bind= and =setContext/chain=
are the same two laws in two runtimes; the client already runs both and never

request, the DOM holds the folded ctx as the fixpoint cursor. The quest names

an addition-free resolution.

** The five questions, answered

1. *What is the client's ctx-equivalent?* The TERMINAL — the standing cursor
   {daemon, thread, buffer, stall}, sourced from context host-side and handed to
   the buffer app as a prop across the bundle line, together with its
   =terminal.$buffer=. It is the server's per-request ctx made standing.
2. *Deck contexts vs entity contexts — new per-entity symbols?* ONE: =TERMINAL=,
   at the active-cursor scope, consumed by host-side surfaces (Frame/Dock/Phase/
   D-E-F). NOT =BUFFER= (only consumer is the cross-bundle app → prop; host-side
   it is =terminal.$buffer=), NOT THREAD/DAEMON/MODE (attributes; no subtree; a
   =MODE= symbol re-opens the two-mode desync). beef corrected the first-draft
   "no symbols" — context IS the source; the bundle pass then found only TERMINAL
   earns a symbol. (Fork 1, twice-revised.)
3. *terminal.mode vs terminal.thread.mode — is MODE derivable from THREAD?*
   Neither derivable nor a single context. There are TWO modes: render-mode
   =buffer.mode= (what app is on screen) and session-mode =thread.$mode= (the
   conversation). They legitimately diverge via cross-mode emission
   (=EMITTER.js:47= — an emitted buffer carries the emitting mode, lands in a
   thread of another mode). Each rides its entity; NO =MODE= symbol; never a
   free-floating =mode= prop that can desync. LIVE PROOF (found this pass):
   =stores/inspector.js:48= reaches for a unified =terminal?.mode?.slug= — but
   =terminal.js= has NO =.mode= getter (only thread/buffer/daemon/stall), so the
   inspector's "active mode" row silently renders "—" forever. The first consumer
   that wanted one terminal-mode and discovered there isn't one. (Name-the-pair,
   not a bug to unify — the fix is to show BOTH.)
4. *Middleware absence — compose step or provide-down?* The client HAS the
   compose step — at the dataspace (entity resolution), the exact dual of the
   server composing ctx at the aperture. VERIFIED: re-frame is the ONLY surveyed
   architecture with a genuine compose step (its coeffect interceptor vector,
   docstring: "analogous to request and response"); every other (Solid/Elm/XState)
   is provide-down. So the client's compose lives where re-frame puts it — the
   effect/resolution boundary (=dataspace.js= =shard.context.attach/bind=) — NOT
   the DOM. The DOM does provide-down (decks + TERMINAL) only. =effects.mount= is
   the teardown-owner (Solid owner-node dual), not the middleware dual.
5. *What do mode apps receive today vs what they SHOULD?* Props
   =({terminal, buffer})= — CORRECT and mandatory (bundle boundary). Only the
   INTERNAL walk is wrong, and only in ONE app: aprende (=Aprende.svelte:46=)
   walks =terminal.daemon.modes.homepage.aprende.call=. Riddler makes no call
   (pure =buffer.data= render); ORACLE already uses =buffer.mode.call= +
   =buffer.mode.harness.object.render= + =buffer.mode.daemon= — the reference,
   and live proof =buffer.mode= carries full capability across the bundle line.
   SHOULD: aprende adopts oracle's =buffer.mode.call=. Props stay; the walk dies.

** The stolen canon (great artists steal — VERIFIED: 22/25 confirmed, 3 refuted)

Deep-research, source-level, adversarially verified (3-vote panels). Two
structural answers dominate, and they compose into M17's exact shape.

- *SolidJS Owner node* (=solid/src/reactive/signal.ts=) — 3-0 CONFIRMED. The
  north star: ONE node =({ owned, cleanups, owner, context })= unifies effect
  ownership · recursive teardown · context-narrowing on the SAME tree. =createRoot=
  is a disposable scope; =onCleanup= pushes teardown AS DATA; =cleanNode= disposes
  children-before-self recursively (automatic, no bookkeeping); context inherits
  parent-at-creation, provide-DOWN, no compose. Svelte's component tree IS this
  Owner tree: =setContext=/=getContext= narrows down, =$effect= returns a
  teardown, =onDestroy= fires recursively bottom-up. → M17's SPINE: TERMINAL at
  =+page=, effects at their provider, teardown by the destroy cascade.
- *re-frame coeffects* (=day8/re-frame/cofx.cljc=, =interceptor.cljc=) — 3-0
  CONFIRMED, and the KEY steal: the ONLY surveyed architecture with a genuine
  COMPOSE step. =inject-cofx= composes an interceptor into the event's vector;
  its docstring calls =:coeffects=/=:effects= "analogous to request and response."
  This is the direct dual of the server's "capabilities down a middleware vector
  via ctx" — and the client ALREADY HAS IT, at the dataspace
  (=dataspace.js= =shard.context.attach/bind=). So the compose step is not
  missing; it lives at entity-resolution, exactly where re-frame puts it (the
  effect boundary), NOT at the DOM. Effects-as-data (=do-fx= single interpreter)
  also confirmed 3-0; steal the discipline, reject the flat global registry.
- *Elm Cmd/Sub* (=elm/core=) — 3-0 CONFIRMED. Effects are opaque VALUES
  (=type Cmd msg = Cmd=, no constructor); the runtime is the sole IO seam;
  managers are a process/actor tree with effect-RETURNED teardown (the binding
  carries its own =__kill=). "Effects always return teardown" is literal here.
  Managers are home-keyed (provide-down), not a narrowing tree.
- *TCA =store.scope(state:action:)=* (=pointfreeco/…/Store.swift=) — a child
  store is a LENS-projection of the parent, not a fresh store. Our
  =thread.$buffers = computed(daemon.buffers, by thread.id)= IS
  =scope(buffer, by: thread.id)=. Narrowing = derivation. Confirms law 3.
- *XState v5 invoke* (=statelyai/xstate/createActor.ts=) — 3-0 CONFIRMED, with a
  load-bearing CAVEAT (an over-claim was REFUTED 0-3): only INVOKED/owned effects
  auto-teardown on scope exit; SPAWNED / manually-created subscriptions need
  EXPLICIT teardown (=stopChild=/=onDestroy=). → directly validates M17.3: the
  conversational =wire()= teardown that =thread/dossier.js:54= DISCARDS is exactly
  this hazard — a manual subscription with no owner. It must be mounted as an
  owned effect or explicitly torn down.

The 3 REFUTATIONS (what is NOT true): re-frame does NOT thread a bare single
context map (it's queue/stack surgery); coeffects/effects are NOT purely plain
data (handlers are fns); XState teardown is NOT fully manual (invoked actors DO
auto-stop). None weaken M17.

SYNTHESIS (the verified punchline): adopt the Solid/XState ownership-tree
provide-down as the SPINE (Svelte's tree already is one), and reserve a
re-frame-style coeffect vector for the places you want the server's compose
symmetry — which the client already spends at the dataspace. M17 is this exact
composition: decks + TERMINAL (Solid provide-down) · dataspace ctx-onion
(re-frame coeffects) · props across the bundle line (the handler boundary) ·
derivation for data narrowing (TCA scope).
