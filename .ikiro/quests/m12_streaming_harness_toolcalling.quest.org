#+DATE: 2026-07-02

* Intent

Two cases on the aprende homepage, both need buffers to emerge from a
conversation with the tutor, not just from a direct emitter call:

1. *Helpdesk* — single-shot ask ("give me a quiz") through a non-streaming
   harness render. Today: =Aprende.svelte:303= =askTutor= is a stub
   (=console.log; return null=).
2. *Aprende via conversation* — the full streamed chat. Tool calls happen
   mid-stream; a tool can internally call the SAME emitters case 1 would use.

Buffer DELIVERY to the client is not a new problem — it's already solved,
caller-agnostic, by the reactive entity broadcast (=shard/datamap.js:152-182=
=twitch.open("/buffer/create/after")= → =Broadcaster.push=, the SAME feed
=thread.$buffers= already subscribes through for the homepage Action tiles,
=Aprende.svelte:292=). M12 is not building a new transport. It's routing
TOOL CALLS through the emitter machinery that already triggers that
broadcast, for both the render path (case 1) and the stream path (case 2).

* Pool/Yield stays untouched — the false binary, found and dissolved this session

Mid-session, chased a redesign of =Pool=/=Yield= (=prototypes/pool.js=) into
a =type=-discriminated envelope — motivated by a real found bug (Pool's
shape-classifier catch-all would silently treat ANY unrecognized tool
output as a raw buffer; riddler's commented-out =literal_review=/
=literal_search= tools are a live example of a plain-data tool that would
get miscategorized). Went as far as a full census (3 parallel Explore
agents) + a Plan agent's blast-bracket implementation plan.

Beef killed it, two objections:
- *"the pool doesn't reach into yield internals afaik?!"* — right. Pool's
  =classify=/=resolve= never branches on type; making =Pool= carry
  =this.type= + a registry lookup in =drain()= was inventing coupling Pool
  never needed, just to have somewhere to stamp a label.
- *"maybe buffer generation [should be] a special type of tool output,
  entirely separate from the dataspace handling of the buffer"* — the
  actual axis was never PAYLOAD-TYPE (buffer vs log vs artifact). It was
  AUDIENCE-CHANNEL (what the model reads vs what the app reads). Two
  different axes were conflated into one "does Yield need a type enum"
  question — a false binary (connoisseur.md:247, "settle how many objects
  there are before choosing between them"). Split the axes and the whole
  Pool/Yield redesign evaporates.

External research, both converge on the same split:
- *MCP* (=modelcontextprotocol.io/specification/2025-06-18/server/tools=):
  tool results carry =content= (model-facing, token-efficient) separately
  from =structuredContent= (machine-facing, schema-validated) + a
  =resource_link= content type (a URI pointer instead of inlining a payload).
- *LangChain* (=@tool(response_format="content_and_artifact")=): a tool
  returns =(content, artifact)=. =content= goes to the model. =artifact= is
  explicitly "not meant to be sent to the model," stays attached for the
  app layer — their own example: content references text, artifact carries
  document identifiers an application uses to render a page.

=Pool=/=Yield= are UNCHANGED by M12. No =type= field, no constructor param,
no registry. The split lives one layer up, in the tool-result part.

* buffer delivery — already solved, verified this session

=shard/datamap.js:152-182= =reactive(repo, twitch, {scope})=: every entity
create/update/delete fires =twitch.open("/{name}/{op}/after")=, caller-
agnostic — the ORM hook doesn't know or care whether the write came from a
direct =/emit= aperture call or from inside a tool handler mid-harness-
render. =Broadcaster.push= fans it out to any =/subscribe= SSE client
matching the filter. This is the EXACT mechanism =thread.$buffers= already
rides for the homepage Action tiles today. A tool calling
=ctx.mode.emit.drill(...)= triggers the identical =BufferEntity= create →
identical broadcast → identical client-side merge, zero new code, for BOTH
case 1 (render) and case 2 (stream).

Consequence: nothing in the render/stream loop needs to POOL or FORWARD
buffer data at all. No =Pool= import in =cortex.js=. No merge logic on the
client. The harness response only ever needs to carry the tutor's TEXT
reply — buffers arrive on their own, independently, usually before the
text reply even finishes.

*SUPERSEDED — the yield lexicon.* The split's AXIS (model-facing vs
app-facing) stands, but the field spelling below is dead: tool returns
are now lexicon-native ={message, entities, object}= and =executeTools=
puts =message= in =output= with siblings riding the part app-side —
LANDED in =subsystems/typology/prototypes/cortex.js= +
=subsystems/typology/gestalten/fromm/yield.js=, along with milestone
12.0's cortex edits (thread-forward + the split). See compact
[[yield-lexicon-four-channels-fromm-yield-and-the-emission-respelling]].
Remaining 12.0/12.1 work (aprende tools, server proof, askTutor) builds
on the lexicon spelling, not =.yield=.

Field named =.yield=, not =.artifact= (beef: "why keeping content/artifact
but not using .buffer?"). =.artifact= was borrowing MCP/LangChain's label
for the AXIS along with the axis itself — but what concretely rides here is
exactly a =Yield= (=Pool.drain()=/=ctx.mode.emit.X()='s return shape).
=buffer=/=buffers= undersells it (not just buffers — the whole
condition-tagged envelope, could be =EXHAUSTED=). =yield= joins the
existing in-repo register (=Yield=/=Pool=/=drain=) instead of a new,
ungrounded word for something already precisely named. The SPLIT itself
(model-facing vs app-facing) stays the borrowed, externally-validated
insight — only the field name changed.

=executeTools= (=cortex.js:19=) today: =results.push({ type: "tool_result",
id: part.id, output })=, =output= = whatever the handler returned, raw.
=translate.js:48-53= (=partToAnthropic=) reads =part.output= ONLY —
=JSON.stringify=s it if non-string, sends as the wire =content=. It does
NOT spread unknown keys, so a sibling =.yield= field is automatically
excluded from what reaches the model — zero changes needed in =translate.js=.

Note: =yield= is a strict-mode reserved word as a BARE destructuring
binding (ES modules are always strict — confirmed empirically:
=const \{ yield \} = obj= throws =Unexpected strict mode reserved word=).
Fine as an object key (=\{ yield: emission \}=) and fine via dot-access
(=result.yield=); a destructure must rename:

#+BEGIN_SRC javascript
async function executeTools(tools, parts, thread) {
  const results = [];
  for (const part of parts) {
    if (part.type !== "tool_use") continue;
    const tool = tools[part.name];
    const handler = typeof tool === "function" ? tool : tool?.execute;
    if (!handler) {
      results.push({ type: "tool_result", id: part.id, output: { error: `unknown tool: ${part.name}` } });
      continue;
    }
    const input = typeof part.input === "string" ? (part.input ? JSON.parse(part.input) : {}) : (part.input ?? {});
    const returned = await handler(thread ? { ...input, thread } : input);
    const { content, yield: emission } = returned?.content !== undefined ? returned : { content: returned };
    results.push({ type: "tool_result", id: part.id, output: content, yield: emission });
  }
  return results;
}
#+END_SRC

A buffer-producing tool:
#+BEGIN_SRC javascript
tools.open(
  { nature: "drill", valence: "Start a review drill.", input: v.object({ count: v.integer().optional() }) },
  async (ctx) => {
    const emission = await ctx.mode.emit.drill({ ...ctx.input, thread: ctx.input.thread });
    return { content: `Started a drill, ${emission.buffers.length} exercises.`, yield: emission };
  },
);
#+END_SRC

=.yield='s ONLY job: keep =content= (what the LLM reads back) short instead
of dumping a raw Yield/entity blob into the model's context. Nothing
downstream reads =.yield= — not =renderLeaf=, not the client, not a test. It
is thrown away once the round loop's synthetic =tool_result= turn
is consumed. Plain-data tools (riddler's =literal_review=) never populate
it, never look Yield-shaped, never risk being misclassified by anything —
there's no classifier to misclassify them anymore.
