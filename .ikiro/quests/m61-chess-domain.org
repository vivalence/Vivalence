* the law

#+BEGIN_EXAMPLE
four ontologies, one aperture. game · position · opening · puzzle are TOPOLOGICAL symbols —
one per literal, carried as the TOPOGRAPHICAL trait, and the subscriber throws if a literal
carries two. the ontology's vocabulary ships as a topology (symbols only); a body of chess
ships as a topography (literals + freight).

the position corpus has ONE owner. Literal is unique on (slug, mode), so a position reached
by two mounts is two rows unless a single mount owns every position. the position mount is
that owner, and every write goes through one repository verb. a position literal with a NULL
mode is a duplicate factory — sqlite counts NULLs distinct.

the move tree is PGN. it already carries variations, comments, NAGs, %clk and %eval; chessops
parses and prints it. there is no recursive `v` schema and none is needed — the tree is text
in the buffer, a parsed value in memory, and the SAME text in `game.RECORDED`.

UCI on the wire, SAN for eyes, FEN for a position, PGN for a game. no rules are written here:
chessops is the rules engine, chessground is the board.

engines are consumed, not declared. `consume: { engine: { module: "@games/service/stockfish" } }`
on the daemon; `ctx.daemon.services.engine` at the call site; a missing service is a sentence
the tool says, not a throw.

the live match is a buffer on the board mode's App. the sealed game is a literal in the corpus.
mutable vs corpus-able is the whole distinction.

what a mount COMPUTES it owns; what the ontology DECLARES is shared.
#+END_EXAMPLE

* the dossier, measured

Seven corrections. Each names the file that settles it. Nothing here is a preference.

** 1. the four ontologies are TOPOLOGIES, not topographies

The dossier: /"Everything below is a topography"/ (openings · puzzles · evals · elite · classics · syzygy) and, separately, four literal "ontologies".

Measured — the module types are pinned and crossed: topography = the surveyed terrain (the empirical body), topology = the invariant relational structure (the ontology's vocabulary). `@education` ships both, and they are different modules:

#+BEGIN_EXAMPLE
~/.viva/registry/education/topologies/word/word.viva.js
  manifest { type: "topology", slug: "word", traits: ["DATASET"] }
  dataset  = new Dataset({ symbol: "dataset/symbols" })          ← SYMBOLS ONLY
  dataset/symbols/ontological.js:
    { slug: "word", traits: ["ONTOLOGICAL","LABELED","TOPOGRAPHICAL"], … }

~/.viva/registry/education/topographies/english-to-italian/italian.viva.js
  manifest { type: "topography", slug: "english-to-italian", traits: ["DATASET","FRAUGHT","DATASINK"] }
  freight  = new Freight("freight/audio")
  dataset  = new Dataset({ symbol: "dataset/symbols", literal: "dataset/literals" })  ← LITERALS
#+END_EXAMPLE

So: `game` · `position` · `opening` · `puzzle` are four TOPOLOGIES, each a symbols-only dataset whose root symbol carries `TOPOGRAPHICAL`. The seven databases are TOPOGRAPHIES. `@games/tablebase/syzygy-345` in the dossier invents an eighth module type; it is a freight-only topography (`traits: ["FRAUGHT"]`, no dataset), exactly the shape `english-to-italian` already uses for audio.

** 2. `literal.ontology` is DERIVED from the one TOPOGRAPHICAL symbol

`systems/runtime/daemon/entities/kernel/Literal.ts:139-151` — the subscriber computes `ontology` at create and update, and throws when a literal carries more than one topographical symbol:

#+BEGIN_SRC ts
if (topographical.length > 1)
  throw new Error(`Literal "${entity.slug}" must have exactly one TOPOGRAPHICAL symbol, found ${topographical.length}`);
#+END_SRC

Consequence for chess: a literal is a game *or* a position *or* an opening *or* a puzzle. Never two. A puzzle generated out of a position is a SECOND literal that `uses` the position — not the position re-tagged.

** 3. the match buffer belongs to the mode's `App`, not to the domain

The dossier declares `v.buffer({...})` under "Userspace" in the domain. Measured — a buffer schema is the first-class argument of an `App`, and `App` is a MODE export:

#+BEGIN_SRC js
// ~/.viva/registry/education/modes/games/dojo/dojo.viva.js
export const app = new App("buffer/Dojo.svelte", v.buffer({ data: {…}, literals: …, symbols: … }).desc(`…`));
// ~/.viva/registry/education/modes/games/dojo/emitter/buffer.js
return ctx.mode.app.buffer({ data: {…}, symbols: …, literals: … });
#+END_SRC

The domain's `entities/userspace/Buffer.ts` is an empty subclass of `@vivalence/runtime`'s buffer — it exists so the daemon's datamap has a concrete table, and declares no fields. So the match buffer's schema lives in `modes/board`, and `/match/*` is an aperture over `ctx.mode.app.buffer` — which also means the arena and the trainer get their own buffer schemas rather than sharing one god-buffer.

** 4. `v.node()` does not exist — and the tree does not need it

`subsystems/typology/schematics/index.js` attaches exactly: `scalars slug url primitives environment entities prototypes rel literal symbol buffer bundle mode intent thread user`. `v.js:125-165` constructs exactly: `string number boolean integer object array union intersect const enum record any unknown null $ref`. There is no `node`, and no recursive constructor at all.

Ruling: the move tree is **PGN text**. PGN already carries variations, comments, NAGs, `%clk` and `%eval`; chessops' `parsePgn`/`makePgn` is the codec both directions. `game.RECORDED.pgn` is the record, the buffer holds the same text while a game is live, and the parsed tree is a derived in-memory value nobody persists. This is the dossier's own decision 1 (chessops for its PGN tree) taken one step further — and it deletes the redundancy the dossier flagged as an open question (`fen` on every node vs reconstruction cost): the node carries no `fen` because there are no persisted nodes.

** 5. there is no `MULTIPLAYER` trait, and the lighthouse cannot relay a move today

Daemon traits, whole list — `systems/runtime/daemon/traits/`: `agentic · application · booted · dataset · datasink · emitter · generative · harnessed · intented · tooled`. No multiplayer.

The lighthouse is a module (`commons/lighthouses/multiplayer/multiplayer.viva.js`, `type: "lighthouse"`), and its server is four files: `auth.js · entities.js · identity.js · index.js`. It serves identity and `/entities/{daemon,identity}`. There is no room, no ordering, no relay. On top of that, m60 is live and rewriting exactly those gates, and the client's remote-entity dataspace is DESIGNED-NOT-BUILT.

Ruling: remote seats are DEFERRED behind m60 (see `* deferred`). Everything else — user, hallucinator and engine seats — is local and lands in M3. The `Occupant` union keeps its `remote` arm so the seam is honest, and `/match/move` rejects it with a sentence until the relay exists.

** 6. `v.literal("user")` names the Literal ENTITY

The dossier's `Occupant`:

#+BEGIN_SRC js
v.union([ v.object({ kind: v.literal("user"), user: v.string() }), … ])
#+END_SRC

In vivalence `v.literal` is `entityFactory(entities.LiteralDescriptor, …)` — calling it with a string returns an entity schema narrowed by garbage, silently. The const constructor is `v.const`. This is a zod-ism of exactly the family Finn caught before (`.passthrough()` across 20+ sites).

Corrected below in `* the design ** occupant`.

** 7. a service is a module with a `provider`, consumed by name

The dossier: /"`ENGINE` — a service trait the domain declares and adapters implement"/. Measured, a service is a module:

#+BEGIN_SRC js
// commons/services/reader/service.viva.js
const manifest = { type: "service", slug: "reader", … };
function provider() { return { open: async (url, options) => ({ … }) }; }
export { manifest, provider };
// commons/instances/hello-world/instance.viva.js — the daemon consumes it
consume: { reader: { module: "@commons/service/reader" } }
// commons/instances/hello-world/tools/web.js:72 — the call site
const reader = ctx.daemon.services?.reader;
if (!reader) return { condition: "ERROR", output: { message: "web_read is not available on this daemon — …" } };
const page = await reader.open(ctx.input.url);
#+END_SRC

`provider(service)` reads `service.statics` and `service.secrets` (`commons/services/nlp/provider/index.js:4-5`) and returns a plain object of methods. So `ENGINE` and `TABLEBASE` are two **contracts** the domain documents and calls; `@games/service/stockfish`, `@games/service/fathom` and `@games/service/lichess-tablebase` are three modules that satisfy them. The domain declares nothing; the instance recipe wires them. A daemon with no engine still plays, imports, exports and classifies openings — only `/position/eval` and `/analysis/*` answer with the missing-service sentence.

** and one that is not a correction but a law

`(slug, mode)` is the unique key on Literal (`Literal.ts:81`), `Literal.mode` is m:1 nullable, and sqlite counts NULLs distinct — so an unowned literal has no uniqueness at all. "One position, deduplicated across every game" is therefore not a property of using the Zobrist key as a slug; it is a law about ownership. See `** the position corpus` below.

| trait | shape |

** the position corpus — the one law with teeth

`Literal` is unique on `(slug, mode)`; `mode` is nullable; sqlite counts NULLs distinct. So:

- every position literal is owned by ONE mount — the `position` topology's mode row — regardless of which mode reached it;
- the only writer is `PositionRepository.reach(fen)`, which computes the Zobrist key, upserts on `{ slug: key, mode: <position mount> }`, and returns the row;
- no aperture verb ever creates a position literal directly, and no position is written with a null owner.

#+BEGIN_SRC js
// ~/.viva/registry/games/chess/domain/entities/kernel/Literal.ts — the verbs, sketched
export class PositionRepository extends base.repository {
  async reach(fen) { … }                       // upsert by zobrist under the position mount
  async evaluated(position, { engine, depth }) { … }   // cache read — the ONLY /position/eval fast path
  async record(position, entry) { … }          // append an EVALUATED entry, newest first, capped
  async booked(position) { … }                 // the BOOKED fold, or null
}
#+END_SRC

Everything that looks like a cache in the dossier is one of these four verbs. `/position/eval` is: `reach` → `evaluated` → (miss) `ctx.daemon.services.engine.analyse` → `record`.

** services — two contracts

#+BEGIN_SRC js
// ENGINE — what a module must return from provider(service)
{
  analyse: ({ fen, depth, movetime, multipv, variant }) => AsyncIterable<{ depth, multipv: [{ cp, mate, pv }] }>,
  play:    ({ fen, elo, depth, movetime, variant })     => Promise<{ uci, ponder? }>,
  stop:    () => void,
}
// TABLEBASE
{
  probe: ({ fen }) => Promise<{ category, wdl, dtz, dtm?, checkmate, stalemate, moves: [{ uci, san, category, wdl, dtz, zeroing }] }>,
  limit: () => number,
}
#+END_SRC

`wdl` is Syzygy's five-valued result from the side to move: `2` win · `1` cursed win · `0` draw · `−1` blessed loss · `−2` loss; `category` says the same as a word. `dtz` is distance to the next zeroing move — what a fifty-move-correct conversion needs. `limit()` reports the highest piece count the adapter answers, so callers know when to ask.

Three adapters, preferred in order: **stockfish** (the process already running, `SyzygyPath` set, `Syzygy50MoveRule` honoured) · **fathom** (the standalone MIT prober over stdio, for probing without a search) · **lichess-tablebase** (`tablebase.lichess.ovh`, 7-piece, HTTP, the only 7-piece source — never called from an air-gapped instance).

`analyse` returning an AsyncIterable is not decoration: an async generator IS SSE on this transport, and SSE is the only escape from the 8000ms daemon-call ceiling. A depth-30 search does not fit under it.

Integration, all automatic once a `TABLEBASE` key is consumed:

- `/position/tablebase` probes, caches as `TABLEBASED`, stamps `endgame.pieces.*` and `endgame.material.*`;
- `/position/eval` short-circuits at or under `limit()` — the answer is the tablebase, `source: "syzygy"`, no search;
- `/analysis/game` judges endgame moves by CATEGORY change, not centipawn loss: win→draw or draw→loss is a blunder whatever a shallow search says; slow conversion is noted, not punished;
- hallucinator seats get the verdict in their prompt at or under the limit — a model should not calculate what is already known;
- `/analysis/explain` names the ending (`KRPvKR`) and states the theoretical result before it narrates;
- a position with exactly one winning move by DTZ is a tactics puzzle for free.

** analysis

`/analysis/game` walks the main line, calls `/position/eval` per node (cache hits are free), and classifies by centipawn loss on WIN PERCENTAGE rather than raw centipawns, so a late-game loss weighs correctly:

#+BEGIN_EXAMPLE
win%     = 50 + 50 · (2 / (1 + e^(−0.00368208 · cp)) − 1)
accuracy = 103.1668 · e^(−0.04354 · (win%before − win%after)) − 3.1669
inaccuracy ≥ 10 win% lost · mistake ≥ 20 · blunder ≥ 30
#+END_EXAMPLE

Both formulas live in `analysis/winrate.js` as pure functions with a unit suite — they are the only numbers in the domain a reader cannot check by eye. Judgements land as PGN comments and NAGs on the tree, summarised in `game.ANALYSED`. `/analysis/explain` hands one node, its eval lines and its judgement to a hallucinator. The engine judges; the model narrates.

** rating

`Rating` is per `(user, variant, timecontrol)`, unique on that triple, driver `GLICKO2` holding `{ r, rd, sigma }` or `ELO` holding `{ r, k }`. The driver contract is copied verbatim from the retention family; the entity is chess's own (D13). The signal is a finished game against an opponent state:

#+BEGIN_SRC js
// ~/.viva/registry/games/chess/domain/rating/glicko2.js
export default {
  type: "GLICKO2",
  encode,                    // (signal) -> { state, status }
  evolve,                    // (signal, rating) -> { state, status }  signal: { opponent: { r, rd }, score: 1 | 0.5 | 0 }
  assess,                    // ({ state }) -> { status }              PROVISIONAL until rd < 110, then ESTABLISHED
  sql: { rating: (table) => `json_extract(${table}.state, '$.r')` },
};
#+END_SRC

`sql.rating` is spliced into a formula column exactly the way `sql.strength` is on `Retention` — so a leaderboard is `orderBy: { rating: "DESC" }` with nothing persisted twice. Each sealed rated match writes a `Trace`.

** study, puzzles

`Study` is a user-scoped literal, ontology `study`, trait `OVERLAID { game, nodes: { "<path>": { nags, comments, children } } }` keyed by node path (`"12"`, `"12.1.3"`). Own games annotate in place; games you do not own get a layer. `/game/annotate` picks which by ownership, and the caller never says.

Puzzle training is spaced repetition over positions: chess's own `Retention` + `Trace` on the puzzle literal, driver `BAYESIAN` copied from education (D14), signal `MASTERY…FAILURE`.

* forks

Six, all beef's, all before M1.

- **F1 — the package.** `@games` holding `chess/` (mine, D15), or `@chess` as its own tap? The dossier's specifier says `@games/domain/chess`; I read that as settled and am flagging it only because the directory names are permanent in the ledger.
- **F2 — the tree's storage.** PGN text (mine, D10) vs a JSON node tree in `RECORDED.tree`. PGN buys import/export, `%eval`/`%clk`/NAG/variation support and no recursive schema; JSON buys direct field access without a parse. I recommend PGN and note the cost: every read of a deep node parses the whole game.
- **F3 — where a runtime-discovered position is written.** Every reached position into the corpus under the position mount (simple, and the eval cache pays for itself), or only positions someone actually analysed (smaller corpus, a second code path)? I lean write-on-analyse; the dossier implies write-on-reach.
- **F4 — the engine service's shape.** One Stockfish process per daemon (the dossier), or one per match? Per-daemon is cheaper and matches the nlp service's shape; per-match is what a real arena of model-vs-model games needs. I lean per-daemon with a queue, and note the queue is not free.
- **F5 — where a shared match's authority lives** when multiplayer reopens: the match aperture on one runtime (server-authoritative, the clock ticks there), or the lighthouse (relay-authoritative)? Not needed for M0–M7; naming it now stops M3 from baking an assumption in.
- **F6 — the rating default.** `GLICKO2` (the dossier) or `ELO` for a first landing? Glicko-2 is right and has a reference implementation to test against; Elo is 20 lines. I lean Glicko-2 — the test is the paper's worked example, so the harder one is the cheaper one to trust.
