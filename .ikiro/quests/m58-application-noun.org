** M1 — =app= → =application= (kernel export · module · mode)

*** mechanism — why one rename is three

#+begin_src js
// subsystems/typology/prototypes/mode.js:12

#+end_src

The kernel's named exports ARE the mode's properties. =export const app = new App(…)= lands as
=mode.module.app= (the module namespace) and, through the assign, as =mode.app= — the same object,
=mode.app === mode.module.app= (pinned by =tests/scenarios/{daemon,mode}.js= comments). Rename the
export and both properties follow, in every kernel. The runtime trait then decorates that object in
place (=buffer= · =fill= · =compile= · =view= · =source=), and the client mints its own =mode.app= from
=/metadata/app= — a DIFFERENT object with the same name, the wire seam.

The class =App= stays. Not asked; the class is the descriptor's type, the property is the mode's slot.

*** mechanism — one string, two lookups

No assign trick this time; the trait name is a STRING and two places resolve it:

for (const trait of mode.manifest.traits) {

#+end_src

The manifest string indexes the traits map, which is =export *= of =traits/*.js= — the export NAME is
the trait name. A kernel saying ="TOOLING"= against an export still named =TOOLED= logs the no-op and

=implements("TOOLED")=), and a TOOLED service stops transporting its tools (=population.js:128=). So the
export, the three string checks, and every manifest flip in ONE pass — that is the flag day.

The second lookup is the db: =ModeTraitsEnum= (=Mode.ts:25=) is the =traits= column's =enumItems= in
every instance's schema snapshot (text column, =checks: []= — no CHECK constraint). Renaming the
member diffs the column; the libsql datamap mints the migration at each instance's next boot
([[feedback_mikro_owns_the_db]] — measured in step 5, never authored).
