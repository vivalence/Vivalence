* Intent
Close the first end-to-end game loop — *Activation* — on top of a formalized
terminal rendering substrate. Activation is the Neon typer run through an
emitter. Two entry points reach it: an LLM tool fired on an assistant message,
and a games-row UI element. The substrate underneath (terminal-owned =Stall=
with explicit rendering phases) is shared by all three games — Activation,
Drill, Riddler — and is the riskier, foundational half of the work.

This quest is the technical engine for the launch WBS (=private/logs/2026.06.23.org=),
specifically the mode/buffer orchestration (A7) and the interactive modes.

** Desired End State
- Terminal renders buffers through a single always-on =Stall= with a declared
  *phase* (static / continuous / manual). Phase, not ad-hoc code, decides what
  happens when the active buffer or the buffer list changes.
- Clicking *Activation* in the games row (or the assistant calling the
  activation tool) writes config onto the thread, fires the emitter, and the
  returned exercise buffers render in the moat and self-delete on completion.
- No entity knows anything about the terminal.

* Build sequence (today's time-plan)
Ordered. Each item gates roughly on the prior. First three are substrate; the
rest is Activation, then Drill, then Riddler.

Original design notes (kept):
Elevate =Stall= from queue-only (=thread.queue=) to the terminal's core
buffer-rendering/management structure. The =Terminal= entity already reserves
=terminal.stall= (currently =null=).
- *Source of truth:* =Stall.$source= ← =thread.$buffers= (the thread's buffer
  list, taken directly from the thread, NOT a client-side lookup map).
  =Stall.$active= ← =terminal.$buffer=.
- *Always-on:* booted with the terminal. With no threshold and no face it just
  sits idle — does nothing — which is fine.
- *Lifecycle (nuke, don't mutate):* effect on =terminal.$thread=. On thread
  change → =stall.deactivate()= + drop it, then construct a fresh =Stall= with
  the new thread's =$buffers= atom and =terminal.$buffer=. Do NOT swap
  =$source= on a live stall.
- *Three phases:*
  - =static= — buffer resolves, no further action. Threshold 0, no pull.
  - =continuous= — validate thread composition (a standalone boat, or
    aimed + queuing); regenerate on resolve. This is the existing =Stall= pull
    behavior. (Standalone-regenerate may want an animation — edge case.)
  - =manual= — the *application* controls buffer rendering directly. Root face.
    The app gets thorough control over the terminal's rendering phase.
- *Refactor:* once phases land, collapse =Stall= from a class back to a single
  constructor function. The class has outgrown its weight.

* Decisions locked
- =Stall= = terminal-level core buffer rendering + management; one per terminal,
  lifecycled per thread (nuke + recreate, never mutate =$source=).
- Phases: =static= / =continuous= / =manual=; =manual= = root face, hands
  rendering control to the application.
- Multi-buffer emission handled as a single response unit.
- Activation emitter awaited → cheap model.
- Build order: substrate (1–3) → aprende + conversation scaffold (4–6) →
  Activation (7) → Drill (8) → Riddler (9).

* Open questions

  responsible for rendering/triggering the deletion? (Lean: app controls it.)

  can't parse them, so manual insert. "Manage it with the phases." Reluctant but
  accepted.

- *Idle stall with a face:* always-on but face set + no threshold = "metastatic"?
  Define the degenerate state.
- *Continuous standalone regenerate* may need an animation to not feel abrupt.
