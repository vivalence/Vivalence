* the design — one rig, the real vector

The recast made every lifecycle a `(die, next)` over a bag. The daemon's bag is `{ controller, mask, daemon }` (`entities/Process.ts:30`), and the ONLY thing `population.core` asks of the outside world is `paladin.ledger.registry.wire(mask)` — which already accepts INLINE citizens: `accio(query)` returns `{ ...query, module: query, identifier: null }` for an object without `module` (`subsystems/paladin/prototypes/ledger/registry.js:209`), and `wire` seats every kernel entry under `mask.reference` (`:231`). ** the design — one scenario, the same seam, once

A recipe's thunks close over the paladin they were authored against (`import paladin from "@vivalence/paladin"` in production, `(paladin) => ({ … })` in a test), so a fresh paladin CANNOT read a recipe from disk: the module must be in memory, and the one seam it enters through is the reader (`paladin.find.type`). That double is right; writing it four ways is not. Proven on the scratchpad copy — the four `mount` helpers replaced by one module, the four suites ported, same envelope both sides:

#+BEGIN_SRC js
// subsystems/paladin/tests/scenarios/index.js — proven 10-05
export function fresh({ env = {}, secrets = {}, ledger = null, home = HOME, mountpoint = MOUNTPOINT } = {}) {
  const paladin = new Paladin();
  paladin.scopes([["ledger", () => true, () => LEDGER], ["instance", () => true, () => home], ["mountpoint", () => true, () => mountpoint]]);
  for (const [key, value] of Object.entries(env)) paladin.env.set(key, value, "flag");
  for (const [key, value] of Object.entries(secrets)) paladin.secret.set(key, value, "flag");
  const declaration = is.fn(ledger) ? ledger(paladin) : ledger;
  paladin.find.viva = async () => (declaration ? [RECIPE] : []);
  paladin.read.module = async () => declaration;
  return paladin;
}

export function mount(declare, options = {}) {              // the REAL pipeline over an in-memory recipe
  const paladin = fresh(options);
  const declared = is.fn(declare) ? declare(paladin) : declare;
  const module = { manifest: PROBE, source: options.home ?? HOME, ...declared };
  paladin.find.type = async () => [module];
  return lifecycle.mount(lifecycle.populate.instance(paladin));
}

export async function homed({ env = {} } = {}) {           // a temp ledger, scopes by the real populate — the disk verbs
  const root = await Deno.makeTempDir({ prefix: "paladin-scenario-" });
  …
  await lifecycle.populate.scopes(paladin);
  return { paladin, root };
}

* the law

- a scenario boots what production boots: the vector, whole; a test never composes a subset of beats, never calls a trait by hand (the 9 files that do today migrate or justify in a comment-free way: the trait tests `mode/{agentic,generative,tooling}.test.js` test the trait as a function — they stay).
- a double is a citizen: it enters through the mask slot the real thing enters through (`lighthouse · datamap · hallucinators · consume`, a domain's `traits`), never by assignment onto a booted daemon.
- a fixture is rows: `rows(em)` writes into whatever datamap it is handed; it mints no mode and no intent — those are the vector's.
- every write rides a request scope; the bag carries no global `em`.
- `close()` is SIGTERM: the test proves the unwind every time it tears down.
- one word per thing: `scenario` is the bag, `rig` is a registry package's own (chess · assembly keep theirs), `fixtures` is data.
