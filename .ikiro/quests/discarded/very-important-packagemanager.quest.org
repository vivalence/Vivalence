#+TITLE: Very Important Package Manager — Registry as Discovery Scopes
#+AUTHOR: Vivalence
#+DATE: 2026-03-19

* Intent

The registry evolves from a single scanned directory into a system of
composable, jj-driven packages. Packages are the unit of distribution.
Modules (.viva.js manifests) remain the unit of identity within the
Pensieve. The Pensieve and VIP.mount primitives stay exactly as they
are — what changes is what feeds them.

The analogy is Homebrew. A package is a tap — a jj repository
containing .viva.js modules. Circuitry references modules by manifest
identity (@vivalence/game/flashcard). VIP resolves them from the
Pensieve, which was populated by mounting packages. Circuitry doesn't
know which package provides a module — it just asks by name.

A package might contain a single mode. A package might contain an
entire daemon's worth of modules plus circuitry plus corpus data.
The package doesn't constrain what's inside — it's a discovery scope.
VIP walks it and registers whatever .viva.js manifests it finds.

* Vocabulary

| Term | Definition |
|------+------------|
| package | A jj repository containing .viva.js modules. Unit of distribution. Identity is repo. |
| discovery scope | What a package provides — a filesystem subtree that VIP walks for .viva.js manifests. |

* Design Decisions (Settled)

1. Module identity lives in the manifest, not the filesystem. Pensieve
   indexes by manifest fields only. Packages are invisible to the
   Pensieve.

2. Package identity is repo.

3. VIP.mount stays exactly as it is. It walks a path and registers
   what it finds. The package layer sits above VIP, deciding which
   paths to feed it.

4. Pensieve stays exactly as it is. Flat pool indexed by
   owner/type/slug/version.

5. Version is jj state — working copy revision, bookmarks, op log.
   Packages don't declare their own version.

* Layers

** User Level — Declaration

"I want these packages." Identified by repo. Does not say WHERE
on disk (that's machine-level) or WHAT VERSION (that's jj).

Where this declaration lives is open. Candidates:
- Variant environment (packages.jsonc alongside services.jsonc)
- A paladin scope

Must be available before circuitry resolution, because circuitry
references modules that live in packages.

** Machine Level — Materialization

A directory containing cloned jj repos. Paladin knows the path via
scope. jj manages each repo's revision state.

** Paladin — Loading and Coordination

Reads the declaration, finds the repos at the machine-level path,
mounts each into VIP. Happens during paladin.ikiro, before circuitry
resolution:

#+begin_src
paladin.ikiro
  resolve.packages()    ← discover and mount packages
  resolve.circuitry()
  resolve.variant()
#+end_src

** Runtime — Consumption

Doesn't change. Calls accio(). Doesn't know packages exist.

The current populate.registry() in runtime (which mounts registry/
kernels, modes, services into VIP) should eventually move into
paladin. Paladin owns VIP, paladin should own all mounting.

* Open Questions

** Does a package know it's a package?

The declaration (user level) says "repo X is a package." But does the
repo itself need a package.viva.js with type: "package"?

Arguments for self-awareness:
- Metadata (author, license, description)
- VIP could distinguish package roots from arbitrary directories
- A package could declare things about itself

Arguments against:
- VIP already doesn't care — it walks whatever path you give it
- Identity lives in the declaration, not the package
- A package is just a jj repo with .viva.js files
- Brew taps don't know they're taps

In production, packages are baked into the image. No jj. Paladin
