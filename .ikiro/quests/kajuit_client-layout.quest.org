#+TITLE: Client Layout — Mobile-First Viewport & Keyboard Management
#+AUTHOR: Vivalence
#+DATE: 2026-03-29
#+STATUS: ACTIVE

* Intent

Principled layout system for the vivalence client that works on
mobile Safari, handles iOS virtual keyboard, and provides a clean
component contract for game modes.

The problem: iOS Safari does not resize CSS viewport units (dvh, vh)
when the soft keyboard opens. No CSS-only solution exists. The web
platform answer is the visualViewport API.

The solution is a two-level layout pattern (app + mode) using three
CSS primitives, a viewport management component, and deterministic
opt-in per mode.

* Architecture

** Layout Pattern

The same pattern is used at two levels:

#+begin_example
container (fills available height)
  surface   (flex: 1, scrolls if needed, fills otherwise)
  controls  (pinned to bottom, never scrolls)
#+end_example

App level:
- Container: =.viva-root= in +layout.svelte (position: fixed, height: var(--viva-h, 100dvh))
- Surface: buffer mount area
- Controls: modeline (44px mobile, 32px desktop)

Mode level (inside each buffer):
- Container: =.viva-frame= (height: 100%)
- Surface: prompt, content, feedback
- Controls: input row, buttons

** CSS Primitives (client.css)

Three classes. Nothing else.

| Class | Role |
|-------+------|
| =.viva-frame= | Flex column container, overflow hidden |
| =.viva-surface= | flex: 1 1 0, min-height: 0, overflow-y: auto |
| =.viva-controls= | flex-shrink: 0 |

** ViewportLock Component (drapes/controls/ViewportLock.svelte)

Svelte component. No DOM output. Lifecycle-managed.

On mount: listens to =visualViewport= resize + scroll events. Sets
=--viva-h= (viewport height) and =--viva-t= (viewport scroll offset)
as CSS custom properties on =document.documentElement=. Updates batched
via requestAnimationFrame.

On destroy: removes listeners, removes CSS properties. Layout falls
back to =100dvh= and =0px=.

** Layout Root (+layout.svelte)

#+begin_example
.viva-root {
  position: fixed;
  top: var(--viva-t, 0px);
  left: 0;
  width: 100%;
  height: var(--viva-h, 100dvh);
  overflow: hidden;
}
#+end_example

=position: fixed= is relative to the layout viewport on iOS Safari.
When the keyboard opens, iOS scrolls the visual viewport (offsetTop
increases). =--viva-t= counteracts this scroll, keeping the container
aligned with the visible area. =--viva-h= sizes it to the visual
viewport height (above the keyboard).

When no ViewportLock is mounted, both vars are absent. CSS falls back:
=100dvh= for height, =0px= for top. Normal behavior. No jitter.

** Mode Contracts

Modes are split by keyboard need:

| Category | Modes | ViewportLock | Keyboard component |
|----------+-------+--------------+--------------------|
| Text input | Write, Shadow, Listen, Cloze | YES | Shadow only (show-phase focus anchor) |
| Button only | Pick, Match, Judge, Flashcard, Exhibit | NO | NO |

Button-only modes use =onmousedown={(e) => e.preventDefault()}= on
action buttons to prevent focus steal. No hidden inputs, no viewport
correction, no layout shifts.

Text-input modes mount =<ViewportLock />= which activates viewport
correction for the buffer's lifetime. When the buffer releases, the
component unmounts and the correction clears.

** Keyboard Persistence

Text-input modes keep the keyboard open across state transitions
(Check -> Next -> next item):

1. Inputs are never =disabled=. Use CSS dimming (=.field-locked=) +
   JS input guard instead.
2. Action buttons use =onmousedown={(e) => e.preventDefault()}= to
   prevent focus steal from the input.
3. Focus =$effect= re-focuses the input on state changes.
4. Shadow uses the =Keyboard= component (hidden input) to keep the
   keyboard alive during the show phase, then transfers focus to the
   visible input on recall phase.

* Design Decisions

1. *Component opt-in, not global detection.* ViewportLock is a
   component that modes mount explicitly. No global event listeners,
   no heuristics, no threshold detection. The mode knows whether it
   needs keyboard support.

2. *visualViewport is the only JS.* One API, one component, one
   concern. Not a hack — it's the W3C standard for this exact
   problem. Shipped in all browsers since 2019.

3. *Button-only modes are pure CSS.* No JS viewport management, no
   hidden inputs, no Keyboard component. =100dvh= handles everything
   including Safari URL bar collapse. Zero layout shifts.

4. *Same pattern at both levels.* App and mode use identical layout
   structure (frame/surface/controls). Nesting works because the
   inner frame inherits height from the outer surface.

5. *requestAnimationFrame batching.* Viewport events fire rapidly
   during keyboard animation. RAF coalesces into one update per
   frame, preventing jitter.

6. *position: fixed + offsetTop counter-scroll.* On iOS Safari,
   fixed positioning is relative to the layout viewport, not the
   visual viewport. When iOS scrolls the page to reveal a focused
   input, =--viva-t= (visualViewport.offsetTop) pushes the container
   back into alignment with the visible area.
