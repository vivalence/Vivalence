*** Walker primitive: align with =shape.mcp=

=shape.mcp= already does Vector → tool-catalog. Uses

*** Function form

#+begin_src javascript
// subsystems/typology/gestalten/shape/agentic.js
import { steer } from "@vivalence/typology";

export function agentic(vector, separator = "_") {
  const entries = steer.rollup(vector, steer.guarded);

  const tools = {};
  const lines = ["### Tools"];

  for (const { pattern, steps, fn } of entries) {
    const name = steps.map((s) => s.nature).join(separator);

    lines.push(`"${name}":`);
    if (pattern.valence) lines.push(`  ${pattern.valence}`);
    if (pattern.input)   lines.push(`  - input: ${JSON.stringify(pattern.input)}`);
    if (pattern.output)  lines.push(`  - output: ${JSON.stringify(pattern.output)}`);

    tools[name] = {
      valence: pattern.valence ?? "",
      input:   pattern.input,
      output:  pattern.output,
      execute: fn,
    };
  }

  return { tools, llmstxt: "\n" + lines.join("\n") + "\n" };
}
#+end_src

22 LoC. No state, no class, no methods. Symmetric with shape.mcp:

| | =shape.mcp= | =shape.agentic= |
|---+-------------+-----------------|
| Walker | =steer.rollup(v, steer.guarded)= | =steer.rollup(v, steer.guarded)= |
| Tool catalog shape | array of ={name, description, inputSchema, outputSchema}= (MCP wire) | map of name → ={valence, input, output, execute}= (Hallucination native) |
| Executor | =handlers.get(name)(args)= | =tools[name].execute(input)= |
| Extra | JSON-RPC =handle()= | =llmstxt= prompt block |
| Consumer | MCP stdio bridge | =ctx.hallucination= |

Two compilers, one Vector, no shared adapter — each speaks its consumer's
idiom.

*** Hallucination consumer alignment: =absorb({llmstxt, tools})=

shape.agentic's bundle output ={tools, llmstxt}= is the consumable.
Hallucination absorbs the bundle in one call:

#+begin_src diff
 export class Hallucination {
   // ... existing add / tool / tune / configure ...

+  absorb({ llmstxt, tools } = {}) {
+    if (llmstxt) this.add(llmstxt);
+    if (tools)   Object.assign(this.tools, tools);
+    return this;
+  }
 }
#+end_src

Naming: =absorb= reads "soak in the bundle" — semantic match for
"compiler-output → consumer". Doesn't collide with field names. Doesn't
overload =add()= (which is for turn content). Alternatives considered and
rejected: =equip= (single-purpose, doesn't carry llmstxt), =consume=
(active voice; absorb is passive — the consumer doesn't alter the bundle),
=load= (generic), =ingest= (works, slightly more clinical).

*** TOOLED trait (post-refactor)

#+begin_src javascript
// systems/runtime/daemon/traits/tooled.js
import { Vector, shard, shape } from "@vivalence/typology";

export const TOOLED = (mode, daemon) => {
  if (!mode.cake.tools) return;

  const tools = new Vector();
  tools.use(shard.context.attach("daemon", daemon));
  tools.use(shard.context.attach("mode", mode));
  tools.slurp(mode.cake.tools);

  const compiled = shape.agentic(tools);

  mode.cake.harness.branch("/dialogue").use(async (ctx, next) => {
    ctx.hallucination.absorb(compiled);
    await next();
  });
};
#+end_src

11 LoC. =shape.agentic= compiles once at trait-resolve time. Per call,
=ctx.hallucination.absorb(compiled)= prepends the llmstxt to system prompt
and merges all tools into =ctx.hallucination.tools=. Single method call,
no =Object.entries=, no loop, no iteration boilerplate.

*** Symmetric example: future =shape.openai= or other-provider shape

If we ever ship a different LLM provider that wants tools shaped differently
(say, OpenAI's tools array with =function.parameters=), the pattern
extends: =shape.openai(vector)= compiles the same Vector to OpenAI's wire
format. One Vector, N compilers, each emitting consumer-native data.

This IS the recurring vivalence grammar: declarative metadata in a single
Vector primitive, multiple shape compilers, each emitting the format its
consumer speaks. Agentic, MCP, OpenAI, future MCP-trait — same input, four
outputs.

What it does:
1. Wraps user's =mode.cake.tools= Vector with daemon + mode context middleware.
2. Compiles via =shape.Agentic=, producing ={[name]: {valence, input, output, execute}}= and =llmstxt= (=### Tools= block listing each tool's name + valence + input/output schema).
3. Mounts a /dialogue middleware on =mode.cake.harness= that, per call:
   - prepends =agentic.llmstxt= to the system prompt (matches bak prior art =bak/teacher/iroh/aperture/agent.js:34=: =agent.enhance(controller.llmstxt)=);
   - registers all compiled tools onto =ctx.hallucination=.

=execute(input)= internally calls =steer.invoke(tools, path)(input)= — runs
the wrapped tools Vector with =ctx.input= = input + middleware-injected
=ctx.daemon= / =ctx.mode=. Per-call invocation = fresh ctx attach + cleanup
(=shard.context.attach= cleans =ctx[key]= on chain unwind).

Effect signature matches bak prior art (=bak/teacher/dewey/aperture/conversation.js:19-25=):
=async (ctx) => result= with =ctx.input= for arguments. =steer/strategy.js=
=dispatch= calls 1-arg effects with the full Context object.

** Trait order — independent (CHAOSMONKEY refactor)

CHAOSMONKEY currently slurps =mode.cake.harness= eagerly in its body, which
forces TOOLED to mutate =mode.cake.harness= *before* CHAOSMONKEY runs.
Brittle.

Refactor: move CHAOSMONKEY's slurp + shape compile + aperture mounts into
a returned finalizer. Finalizers run after all trait bodies (per
=resolution.js:51-56=). TOOLED can then mutate =mode.cake.harness= in any
order — CHAOSMONKEY's finalizer slurps after.

#+begin_src
trait body phase             trait finalizer phase
─────────────────────        ────────────────────

SELFEVIDENT  (body, no-op)
TOOLED       (body)           ← mutates mode.cake.harness   (any order)
CHAOSMONKEY  (body)           CHAOSMONKEY.finalizer
                                ├─ harness.slurp(mode.cake.harness)   ← picks up TOOLED's branch
                                ├─ daemon.cortex.shard.effects(harness)
                                ├─ mode.harness = shape.object(harness, steer.echo)
                                ├─ mode.aperture.branch("/harness").slurp(harness)
                                └─ mode.aperture.open("/capabilities", ...)
CONVERSATIONAL (body)         (no finalizer needed)
#+end_src

Verifications required during M1:
- Nothing reads =mode.harness= during another trait's body (only at request time). Verified — CONVERSATIONAL accesses =mode.harness= inside a WS handler closure that fires post-resolve.
- Nothing reads =mode.cake.harness= externally. Verified — only CHAOSMONKEY consumes it.
- No async timing issues: trait bodies run sequentially in a =for= loop;
  finalizers also sequential. No parallel race.

Open: should TOOLED also live as a finalizer? No — its mutation of
=mode.cake.harness= must happen before CHAOSMONKEY's finalizer slurp.
TOOLED stays body-only.

** Faculty scope

No new faculties needed. Faculty types are cortex I/O channels —
tool_use is a model-emitted part type that only =dialogue= produces.

#+begin_src
dialogue    text in,  text out    (LLM chat)        ← tool_use lives here
speech      text in,  audio out   (TTS)             ← provider→audio, no tool_use
verbatim    audio in, text out    (STT)             ← provider→text, no tool_use
#+end_src

Anthropic's API: tool_use is a content block returned by chat completion.
TTS providers (ElevenLabs, Fish Audio) speak text, they don't decide to
call tools. STT providers (Deepgram) transcribe audio, same. =/dialogue
only= is where tool_use semantics natively live, not a constraint TOOLED
chose to impose.

Future: if an =object= faculty (structured JSON output) lands in
=FACULTY_TYPES=, it would support tools too — Anthropic API allows tools
in any completion. TOOLED extends by adding =/object= branch alongside
=/dialogue=. Parked until cortex wires =object= via =shard.effects=.

** Two grammars in play

Toolcalling sits at the intersection of two stream protocols. Cortex
packets are the typology-internal protocol (turn/part lifecycle).
Conversation channels are the boundary protocol (server↔client WS).
Both load-bearing, neither modified by this work.

#+begin_src
cortex packet protocol (typology, internal)
  faculty.stream:
    /turn/open
    ├─ /part/open  { type: "tool_use",    id, name, input: "" }
    ├─ /part/delta { input: <json chunk> }   (streamed)
    └─ /part/close
    /turn/close { meta.stop: "tool_use" }
                  ↓
                  executeTools(parts)         ← cortex loop
                  ↓
                  soma.drain({role: "user", parts: [{type: "tool_result", id, output}]})
                  ↓
    /turn/open
    ├─ /part/open  { type: "text" }
    └─ /part/close
    /turn/close { meta.stop: "end_turn" }

conversation channel grammar (boundary, server→client send)
  /dialogue/{packet, close, error, abort}    ← packet carries cortex events
  /speech/{packet, close, error, abort}
  /verbatim/{packet, close, error, abort}
  /handshake (initiation only — client→server)

  packet payload discriminator: nature (verbatim) | event (dialogue)
#+end_src

=part.type:"tool_use"=/=part.type:"tool_result"= as collapsible =<details>=.

* Lessons crystallized

1. *Reuse audit risk: rejected primitives* — the line "I considered and rejected X" is where missed prior art hides. List SEARCHES PERFORMED, not VERDICTS RENDERED. Rev 4 of this WP rejected Vector in a confident reuse audit; missed =shape.Agentic= class + =shape.mcp= function + three =bak/= consumers + the full =mcp.test.js= test suite. Retard callout logged.

2. *"One primitive, N compilers" is the recurring vivalence grammar* — same Vector consumed by =shape.agentic= (LLM tools), =shape.mcp= (MCP server), future MCP-trait, future =shape.openai=. Each compiler emits in its consumer's idiom; no shared adapter. When a feature feels like catalog of callables / branchable namespace / declarative metadata surface — primitive = Vector; implementation = new shape compiler.

3. *Class form is a smell across gestalten* — every other =shape.X= is a function. =shape.Agentic= class form was a lift-without-refactor from old =bak/agent= mutation-during-walk pattern, never refactored. Rule: when adopting an existing primitive, audit form against siblings; outliers are usually unrefactored.

4. *Compilers should produce consumable bundles, not iteration boilerplate* — =shape.agentic= now returns ={tools, llmstxt}=; =Hallucination.absorb()= consumes in one call. If consumer iterates =Object.entries=, shape isn't done.

5. *Trait order constraints are smells* — "TOOLED before CHAOSMONKEY" was brittle. Fix: push the consuming step (=harness.slurp=) into a finalizer. Trait bodies = parallel mutations; finalizers = sequential consolidation.

6. *bak/ is prior-art reference, not dead-archive* — three =bak/teacher/*= files held the canonical Agentic-with-Vector pattern. Greppable, two-line-summarizable. Gate: before any "no existing pattern" claim, =grep -r= bak/.

7. *Channel grammar separates server-send from client-initiate* — =/X/{packet,close,error,abort}= server-send (4 verbs); =/X/open= client→server initiation (asymmetric). Tools have no analog of "client opens a tool execution" — execution is server-side, model-driven. Future tools channel = 4-verb server-send only; "start" becomes a =packet.nature= rather than its own verb.

8. *@beef inline annotations are corrections, not commentary* — embedded mid-document with rationale, requiring absorption into named architectural decisions. Each @beef became a quest rev. Routine: scan quests for unabsorbed @beef before claiming convergence.

9. *"this goes both ways" = paired alignment cue* — Finn's phrasing for "producer and consumer should fit each other without adapter code". When a refactor cleans up the producer side but leaves boilerplate at the consumer, the consumer is also out of alignment. =shape.agentic= refactor + =Hallucination.absorb= addition are paired — neither alone is the full answer.

10. *Compact discipline: substance lands in the quest, not date-specific files* — quest IS the persistent design surface. Compacts at =.ikiro/compacts/<date>.org= are for FINISHED-and-shipped sessions where the substance has settled. In-flight design work consolidates into the quest's own Lessons / Decisions / Changelog sections. Date-specific compact created and deleted this session per Finn's correction.

11. *Existing infrastructure beats greenfield design* — =Span= prototype + =shard.track= middlewares already exist in typology. M8 telemetry was almost designed as new infrastructure before the existing primitives surfaced. Routine: before any "we need observability/telemetry/logging/tracing", =grep= =typology/prototypes/= and =gestalten/shard/=. Same applies to any cross-cutting concern — odds are typology already has a primitive.

12. *Watches verify boot, not edit-by-edit correctness* — runtime watch heartbeats =Status:ALIVE= indefinitely; reload events are sparse line items easily lost in the noise. =deno --watch= DOES reload on subsystem edits (verified: =Watcher Restarting! File change detected= line appears on save). To verify a specific edit landed cleanly, run tests directly. Watches signal "process alive across edits", not "this edit works".

World-facing tools (filesystem, shell, web) are plumbing every agentic system needs. The standard library design (M6) calls this out explicitly so future iteration doesn't accidentally lump them.

** Brainstorm (the unconstrained pass)

*** What makes vivalence tooling distinctive

Two halves:

1. /World-facing/ — read/write files, run bash, fetch URLs, browse pages. Same
   surface every agentic system needs. Reuse, don't innovate.
2. /Inward-facing/ — tools that introspect and operate on the daemon: query
   entities, inspect modes, walk symbol graphs, read memory states, surface
   telemetry. Pedagogically rich: a tutor that can examine its own state and
   the learner's progress; a Finn-driven Claude that can explore the running
   system without leaving the conversation.

The world-facing half is plumbing. The inward-facing half is where vivalence
earns its identity: a self-introspecting language-learning OS exposed to LLMs.

*** Where do tools live in the registry

*** MCP exposure shape

shape.mcp already produces a Vector→MCP-server bundle: =({handle, tools, handlers})=
where =handle= is a JSON-RPC dispatcher. The question is who owns the handle and
how external clients reach it.

Options considered:

| approach | install point | client | trade-off |
|----------+--------------+--------+----------|
| HTTP/WS aperture route | =mode.aperture.branch("/mcp")= | HTTP-capable MCP client | non-standard; needs custom client |
| Per-mode stdio bridge  | shell-client subcommand | claude desktop, cursor | standard; one bridge per mode |
| Daemon-aggregating bridge | shell-client subcommand | claude desktop, cursor | namespaced tools (=dewey_learner_state=); convenience |
| In-process compile | =mode.cake.tools= → =shape.mcp= local | HTTP via aperture | works but couples daemon to MCP wire |

Hybrid commit: HTTP aperture route as the daemon-side primitive (one route per
mode); shell-client subcommand spawns stdio bridge that pipes stdin↔HTTP.
Aggregator becomes a shell-client convenience over the same primitives.

Rationale: shape.mcp's =handle(message)= is already wire-shape-agnostic — accepts
a JSON-RPC envelope, returns one. Mounting on aperture is a 1-line affect. The
shell bridge is a thin pipe, not a re-implementation. Aggregation is namespace
prefixing on the bridge side, not duplication of dispatch logic.

*** shell-client mcp subcommand

shell-client trajectory:

#+begin_src
viva mcp <type> <slug>
#+end_src

Behavior: read MCP JSON-RPC frames from stdin, POST each to
=/mode/<type>/<slug>/mcp/handle= via authenticated Connection, write responses
to stdout. Pure pipe. No per-tool logic on the shell side.

#+begin_src javascript
// systems/shell/trajectories/mcp.js (proposed)
import { Connection } from "@vivalence/typology";
import { authority }   from "../lib/session.js";

export default async ({ type, slug }) => {
  const connection = new Connection(authority.lighthouse, authority.access);
  const path = `/mode/${type}/${slug}/mcp/handle`;

  for await (const line of Deno.stdin.readable.pipeThrough(new TextDecoderStream()).pipeThrough(splitLines())) {
    const message  = JSON.parse(line);
    const response = await connection.call(path, message);
    if (response !== null) Deno.stdout.writeSync(new TextEncoder().encode(JSON.stringify(response) + "\n"));
  }
};
#+end_src

=/manifest=, namespace each mode's tools as =<slug>_<tool>=, fan-out tools/call

*** Standard tool library shape

Per-category Vector module, manifest-style:

#+begin_src javascript
// registry/tools/@vivalence/filesystem/filesystem.viva.js (proposed)
import { Vector, v } from "@vivalence/typology";
import { resolve, scope } from "./_scope.js";  // workspace path safety

export const manifest = {
  type: "tools",
  slug: "filesystem",
  name: "Filesystem",
  description: "Workspace-scoped filesystem operations.",
  version: "0.1.0",
};

export const tools = new Vector();

tools.open(
  {
    nature:  "read_file",
    valence: "Read a file's text content from the workspace.",
    input:   v.object({ path: v.string() }),
    output:  v.object({ content: v.string() }),
  },
  async (ctx) => {
    const path = scope(ctx.daemon.workspace, ctx.input.path);
    return { content: await Deno.readTextFile(path) };
  },
);

tools.open(
  {
    nature:  "list_dir",
    valence: "List entries in a workspace directory.",
    input:   v.object({ path: v.string().default(".") }),
    output:  v.object({ entries: v.array(v.object({ name: v.string(), type: v.string() })) }),
  },
  async (ctx) => {
    const path = scope(ctx.daemon.workspace, ctx.input.path);
    const entries = [];
    for await (const entry of Deno.readDir(path)) {
      entries.push({ name: entry.name, type: entry.isDirectory ? "dir" : "file" });
    }
    return { entries };
  },
);

// ... write_file, glob, mkdir
#+end_src

** Critique pass

*** Permissioning

Currently every tool placed on =mode.cake.tools= is dispatchable by anyone with
access — the LLM via TOOLED, an external MCP client via MCPEXPOSED. Three
attack surfaces:

1. /Untrusted LLM prompts in dialogue/ — model can call any tool. Today's risk:
   read-only tools fine; write tools can corrupt state if prompt-injected.
   Mitigation: separate Vector for write-tools, gate via different trait
   (e.g. =MUTABLE-TOOLED=). v1: read-only standard library only.
2. /Untrusted MCP clients/ — shell-client requires daemon auth (existing
   shard.secure.authorize). Same boundary as HTTP aperture. Acceptable.
3. /Tool-side abuse/ — bash arbitrary commands, fs read /etc/passwd, web
   fetch internal URLs. Mitigation: workspace-scoping for fs, allow-list for
   bash (default deny), URL-allowlist for web (default deny intranet).

The =shard.secure.authorize()= middleware exists at aperture-edge. Re-applying
per-tool needs design — currently shard.secure runs at aperture branch, not
within a Vector's carry. Needs investigation.

*** VCS read-only constraint

Vivalence's CLAUDE.md is explicit: VCS (git AND jj) is READ-ONLY for me. Any
git tool MUST be read-only OR excluded entirely. Decision: exclude
=@vivalence/tools/git= from v1 standard library. Bash already covers ad-hoc git
under user supervision. Re-evaluate later.

*** Bash sandboxing

Arbitrary bash is dangerous. Options:

| approach | enforcement | tradeoff |
|----------+-------------+---------|
| Deno permissions | =--allow-run=ls,cat,...= | per-process; can't change at runtime |
| Allow-list per mode | =mode.cake.bash.allow=[...]= check in handler | runtime; mode-controlled |
| Container/jail | external | overkill |
| Trust user | none | matches Claude Code; works under supervision |

For Finn-driven-via-Claude-Code use, full bash matches Claude Code's existing
pattern. For tutor modes (dewey), bash is rarely needed. Decision: bash
defaults to =allow=[]= (deny-all); modes opt in by overriding =cake.bash.allow=.

*** Filesystem scoping

read_file/write_file scoped to project workspace, not arbitrary disk. Pass
workspace root via =ctx.daemon.workspace= (new daemon field, populated at boot
from runtime config). Path resolution helper =scope(root, requested)= rejects
=..= traversal.

*** mode.cake.tools — single Vector for all consumers?

Currently TOOLED reads =mode.cake.tools= for LLM. MCPEXPOSED reads same. What
if a mode wants tool X for LLM but NOT for external MCP clients?

Two options:

1. /Branch-prefixed visibility/: =mode.cake.tools.branch("private")= → LLM only;
   default branch → both. Both traits filter accordingly.
2. /Two separate Vectors/: =mode.cake.tools= (LLM) + =mode.cake.exposed_tools=
   (LLM + MCP). Explicit declaration of intent.

Defer to v2. v1: single Vector, both traits expose everything.

*** Aggregator namespacing

=viva mcp daemon <slug>= aggregates tools from N modes. Naming collision:
=dewey_learner_state= vs =survival_learner_state=. Aggregator prefixes with mode
slug: =teacher_dewey_learner_state=. Reverse-routing on tools/call: split
prefix off, dispatch to the right mode's /mcp/handle.

*** Standard library version pinning

Tools live in registry workspace. Pin via deno workspace import map. Each
=registry/tools/@vivalence/<category>/= = own subpackage with =<slug>=
manifest. Modes reference by name, not path.

*** shell-client overlap with daemon-internal tools

shell-client trajectories already expose entity find/count, mode/status,
pick/feed, review/literal — exactly the daemon-internal tool surface. M6.9

Concrete plan deferred until shell-client trajectory tree solidifies.

// systems/runtime/daemon/telemetry.js (proposed)
export class RingPipe {
  constructor(capacity = 1000) {
    this.capacity = capacity;
    this.items = [];
  }
  send(item) {
    this.items.push({ at: Date.now(), item: typeof item.json === "object" ? item.json : item });
    if (this.items.length > this.capacity) this.items.shift();
  }
  since(ts) {
    return this.items.filter((entry) => entry.at >= ts);
  }
  clear() {
    this.items.length = 0;
  }
}

export function attach(daemon) {
  daemon.telemetry = {
    spans: new RingPipe(),
    logs:  new RingPipe(),
  };
  daemon.aperture
    .branch("/telemetry")
    .open("/spans", (ctx) => daemon.telemetry.spans.since(ctx.input?.since ?? 0))
    .open("/logs",  (ctx) => daemon.telemetry.logs.since(ctx.input?.since ?? 0));
}

export class Log {
  constructor(level, msg, attrs = {}) {
    this.level = level;     // "trace" | "debug" | "info" | "warn" | "error"
    this.msg   = msg;
    this.attrs = attrs;

** Critique pass

*** Pipe lifecycle

Pipes are unbounded if RingPipe.capacity grows. Default 1000 is arbitrary;
tune by observation. Aperture endpoints take =since= cursor for incremental
fetch — client doesn't re-pull whole ring.

*** Span hash uniqueness

Span hash uses =[nature, trace?.hash, timing.begun]=. Two tools called with
same nature in same millisecond would collide. Acceptable for v1 (tools are
sequential); add randomness (=crypto.randomUUID()=) if collisions appear.

*** Sensitive data in logs

Tool inputs/outputs MAY contain sensitive data (auth tokens, PII). v1 logs
ALL spans. Mitigation: per-tool opt-out via pattern descriptor flag
(=pattern.private= true → span captured but input/output redacted). Defer
implementation; document the constraint.

*** Drain delay

Spans drain on tool dispatch completion, not during. Long-running tools
(future: file downloads, image generation) won't show up in the span pipe
until they finish. Acceptable for v1 (no long-running tools yet).

*** Stdout pipe

For dev visibility, attach =(span) => console.log(JSON.stringify(span.json))=
as a SECOND pipe via =shard.track.span= chain. Or — simpler — daemon.telemetry
is itself a multi-pipe: =telemetry.spans.add(stdoutPipe)=. Defer multi-sink
plumbing; v1 = ring only, console.log via ad-hoc dev aid.

*** Cross-process / aggregator concern

Multi-daemon span aggregation is out of scope for MVP. Single-daemon ring
buffer + aperture access is enough to develop tooling.
