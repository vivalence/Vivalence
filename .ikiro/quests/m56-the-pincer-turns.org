*Ruled: no anchor.* Every pane folds, docks and closes alike — v3's symmetry, unchanged. The rest of this
section is kept as the decision trail, not as a live proposal.

The wireframes file says it in prose, above the wireframes:

#+begin_quote
As built, C is D | twig | E | twig | F: E (terminal) is always there, only D and F toggle from the twigs.
Every wireframe now keeps that rule — Terminal is the anchor, it never folds, closes or drops under its

and in its code:

#+begin_src js
const ANCHOR = 1;
const FL = (i, area, n) => i === ANCHOR ? Math.min(MIN, area - (n - 1) * HEAD) : HEAD;
// hints: 'terminal is the anchor · it never docks' / '· it never folds' / '· it never closes'
#+end_src

*The as-built code agrees*: =panels/c/c.svelte:102-137= gives D and F a twig toggle and gives E none — E
cannot be closed today.

*v3 drops it.* There is no =ANCHOR= in v3; =NAMES= is a flat three, =closeTap= docks any pane, =toggleFold=
folds any pane, and the only guard is "the last unfolded pane refuses to fold".

*Where my first read went wrong:* I counted =c.svelte='s "E has no twig toggle" as a second vote for the
anchor. It is not evidence of intent — it is a limitation of the twig design, which only ever hung toggles
on the wings because there is no rail outside F. An accident of the old implementation got read as a rule.
Ask what the old code COULD express before treating what it does as a decision.

** the v3 engine, measured

Constants: =BAR 44= · =FOLDZ 84= · =DOCK_PULL 34= · =MIN= (prop =minPane=, default 180).
=NAMES = ['instance','terminal','buffer']= maps onto =D · E · F= — pane 0's body is daemons/threads/intents,
pane 1's is active/mode/thread + /save as intent/, pane 2's is the buffer list.

- =tall = h >= w= picks stack vs row.
- =norm(oi, fold, weight, area)= — folded panes are exactly =BAR=; the rest share by weight over a floor of
  =min(MIN, avail / n)=, iterating until nothing is under-floor.
- =push(size, oi, b, delta, area)= over =fitRun= — dragging a boundary collapses panes in the way to =BAR=
  one after another; the next takes over. Every drag is a run, not a neighbour pair.
- the 44px header replaces the twig: grip dots · tap zone (name + digest, digest hidden under 260px) ·
  =⤢=/=⤡= · =✕=. Grip drags the boundary; tap zone folds.
- fold = tap the header, or release under =FOLDZ=. Folded in a WIDE C = a *strip*: =writing-mode: vertical-rl=,
  its own stacked grip / tap / close. Folded in a TALL C keeps the horizontal header.
- dock = drag the header into the bar (in a stack, its leading edge reaches C's top; for the first pane, or
  in a row, a pull of =DOCK_PULL= across the run axis). Dashed drop zone previews it.
- tab = tap re-opens at the average unfolded size; pull down re-opens at the pulled size.
- =⤢= folds every other open pane; =⤡= on the maxed pane equalises.
- a hint line narrates every gesture, fading 1.6s after the pointer settles.
- =recency= is written on every fold/open and *never read*.

*Seen live, same session:* tapping =INSTANCE='s header folded it to a 44px strip and the other two absorbed
the width; dragging =BUFFER='s grip up 46px docked it — the bar appeared across C's *full width at C's top
edge*, carrying =BUFFER idle= as its only tab, and =TERMINAL= took the remainder. The bar sits at C's
leading cross-axis edge in BOTH layouts; it is not a rail along the run axis.

** the engine's invariants — run, not asserted

v3's =norm= / =fitRun= / =push= lifted verbatim into node and swept
(=oi= over all 7 non-empty subsets × 8 fold masks × 5 weight vectors × 7 areas = 1960 =norm= cases;
4 runs × 4 areas × boundaries × 13 deltas = 260 =push= cases):

| invariant                                                        | result             |
|-------------------------------------------------------------------+--------------------|
| =norm= sums to the area, whenever ANY open pane is unfolded       | holds, 1960/1960   |
| a folded pane measures exactly =BAR=                              | holds              |
| no unfolded pane sits below =min(MIN, avail/n)=                   | holds              |
| a closed pane measures 0                                          | holds              |
| =push= sums to the area                                           | holds, 260/260     |
| =push= never drives a pane under =BAR=                            | holds              |
| =push= is monotone in the drag delta                              | holds              |
| =norm= sums to the area when EVERY open pane is folded            | *FAILS · 470 cases* |

*Defect.* =norm= returns early once =un= (the unfolded set) is empty, so the run measures
=oi.length × BAR= and the remainder of C paints as bare background — e.g. one open folded pane in a 100px
C gives 44px of pane and 56px of dead space. The interactive paths mostly guard it (=gripUp= unfolds the
biggest, =toggleFold= refuses the last), but *=openPane(i, px)= has no such guard*: dock all three panes,
then pull one tab down under 84px, and every open pane is folded. M2 must either give =norm= a
last-resort unfold or give =openPane= the guard the other two paths have.

* rulings owed — beef's

1. ~is terminal the anchor?~ *SETTLED — NO.* beef: /"terminal should absolutely dock and close. bullshit"/.
   No =ANCHOR= index, no privileged pane, no per-pane floor exception. Every pane folds, docks and closes.
   Consequences carried below: the engine takes no anchor parameter · E renders its =✕= like the others ·
   the all-docked empty state is REACHABLE and must be built · the all-folded dead-space defect must be
   fixed in =norm=, since no anchor is left to guarantee an unfolded pane.
2. *which C design ships?* v3 (fold/dock) is one of three. The wireframes' other four drag models
   (seam grips · detents · flick) and c-nav's five nav models are alternatives, not decoration.
   *Recommendation: v3's model, with the wireframes' =settle= grafted on* — a pane between =BAR= and =MIN=
   is BUMPED up to =MIN= when neighbours can spare it, rather than left squeezed. That is the one thing the
   wireframes have that v3 lost, and it is 12 lines. The graft survives ruling 1: =settle='s bump pass is
   anchor-free; only its =i !== ANCHOR= fold guard drops out, which restores exactly v3's behaviour.
3. *=instance= is TAKEN* — =paladin/prototypes/ledger/instances.js:18= =instance(slug)= is the one slug→instance-dir
   mapping (=paladin/tests/ledger.test.js:194=, =ghost/tests/{delete,use}.test.js=). The docked-tab bar needs
   another noun. *Recommendation: it IS the =twig=* — the twig stops being a rail between panes (the header
   takes that job) and becomes the bar panes fold out to. One noun, already in the bones family, still
   naming "the thin strip in panel C".
4. *what does C do when it is too narrow for its panes?* c-nav's =fits = clamp(floor(w / minPane), 1, 3)= is
   a real rule v3 has no answer for — v3 just squeezes to floors. *Recommendation: defer.* Fold + dock
   already degrade; adopt =fits= only if the folded row still reads badly on a phone.
5. *where does the engine live, and how big is =MIN=?* =norm= · =push= · =fitRun= · =layout= are pure.
   *Recommendation:* =stores/bridge/panes.js=, beside geometry/gesture/dock, tested like
   =tests/pincer/dock.geometry.test.js=; =MIN= a constant at 180, not a user setting. Chrome stays
   kajuit-local under =panels/c/widgets/= until a second consumer asks.
6. *does =paneSize= migrate?* The saved shape has no =fold= / =weight= / =open= / order.
   *Recommendation: new key, old key ignored* — a stale layout is worth nothing and =bridge.js:57= already
   tolerates a null read.
7. ~does the pane header replace D/E/F's first =Section= head, or stack above it?~ *SETTLED — STACK.*
   beef: /"do"/ on the recommendation. The pane header stacks ABOVE the =Section= heads and *the digest is
   dropped*: =Section= heads name CONTENT (daemons · threads · intents), the pane header names the PANE and
   owns the gestures (grip · fold · maximise · close). Different jobs, so both stay. The digest was the only
   duplicated part, and v3 already hid it under 260px. Original question: D mounts three drapes
   =<Section>= blocks; the comp adds a 44px header carrying the pane NAME + digest above them. Three
   heading levels in one pane. *Recommendation: stack, and drop the digest* — the =Section= heads name
   CONTENT (daemons/threads/intents), the pane header names the PANE and owns the gestures (grip · fold ·
   maximise · close). They are different jobs. The digest is the part that duplicates, and it is the part
   v3 already hides under 260px.

* landed in M1 — beyond the listed hunks, flagged

Two additions I made while writing, neither in the first draft's hunk list:

1. *the bone borders flip with the axis.* =shoulder= and =crown= carried =border-top= + =border-bottom=;
   at o=90/270 a vertical bone showed those as CAPS, not edges. =.bone.column= swaps them to
   =border-left= / =border-right=. Without it M1 does not achieve its own goal — the bone still reads
   wrong when turned. Strike it if you disagree; it is 6 lines per file.
2. *the spine ornaments are run-axis-relative, not suppressed* (M1.4 left this "beef's call at review").
   =.bone.row .scanline= runs left-to-right off =heartbeat-row=, =.bone.row .endcap= flips to 1×12 at
   =left: 47px=. The alternative was two lines hiding them off-axis. Both keyframes still hardcode a
   viewport-sized travel (=100vh= / =100vw=), which is the pre-existing sloppiness, not new.

*One number is mine, not measured:* =panels/a/a.svelte= =LABEL_MIN_PX = 96=. The comp gates its own
12px label on =rects.a.height - 45 - 64 >= 24=; kajuit's label is =font-size-7xl= = =4.3rem= × 1.3 ≈ 89px,
so 96 is that box plus air at a 16px root. It does NOT track =FONT_SIZES= — at a large root setting the
gate opens slightly early.

* landed in M2 — deviations from the written plan

1. *every engine export carries the =pane= register.* =index.js= re-exports =panes.js= with =export *=,
   so bare =BAR= · =MIN= · =push= · =layout= would land flat in =stores.bridge= beside =bridge.layout=.
   They are =PANE_BAR= · =PANE_MIN= · =pushPanes= · =layoutPanes= · =normalisePanes= · =settlePanes= ·
   =fitPaneRun= · =openPanes= · =dockedPanes= · =paneBoundary= · =PANE_NAMES=.
2. *no docked ORDER is persisted.* M2.2 asked for one; v3 derives the tab order from the index order and
   nothing anywhere sets a different one. Storing an order no code writes is dead state. =panes= holds
   =open= · =fold= · =weight= only.
3. *=fitPaneRun= guards the empty run.* v3's =fitRun= writes =s[undefined]= when handed an empty order —
   unreachable through =gripDown= (=b: k === 0 ? 1 : k=) but reachable by any other caller. Tested.
4. *the all-folded guard unfolds the heaviest pane inside =normalisePanes=.* With no anchor left
   (ruling 1) there is nothing else to guarantee an unfolded pane. Renderers read foldedness from the
   SIZE (=size <= PANE_BAR + 0.5=), exactly as v3's own render does, so the guard needs no second
   return value and no call-site cooperation.

*Two bugs the build caught, both fixed:* =grab= was a plain =let= read by the template, so the grip
highlight would never have updated mid-drag; and the pane digests read =bridge.view.d= / =.f= through
getters inside a =$derived=, which tracks nothing — both now subscribed.
