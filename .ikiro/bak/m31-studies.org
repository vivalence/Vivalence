* brew — mechanism brief

## 1. UNIT OF DISTRIBUTION

Three artifact kinds, one possession kind:

- **Formula** — "a package definition written in Ruby": a class `Foo < Formula` in `foo.rb`, declaring `url`, `sha256`, `depends_on`, and a `def install` that builds into a versioned prefix. It is a *recipe*, not a payload. (Formula Cookbook, docs.brew.sh/Formula-Cookbook)
- **Bottle** — "pre-built **keg** poured into a **rack** of the **Cellar** instead of building from upstream sources"; "simple gzipped tarballs of compiled binaries", e.g. `qt--6.5.1.ventura.bottle.tar.gz`. A per-platform `bottle do ... end` block in the formula carries `sha256` per OS/arch tag, `cellar` (`:any` = relocatable), `root_url`, `rebuild`. Bottles are the *default materialization* of a formula, not a separate package identity. Hosted as OCI blobs at `ghcr.io/homebrew/core/<name>` since 3.1.0 (post-Bintray). (docs.brew.sh/Bottles)
- **Cask** — a Ruby `cask "token" do ... end` block for prebuilt macOS apps: no build step; declared *artifacts* are staged into `$(brew --caskroom)/<token>/<version>` then moved/symlinked (`app "Foo.app"` → `/Applications`). `uninstall` and `zap` stanzas script removal. (docs.brew.sh/Cask-Cookbook)

**What the user "has": a keg** — a concrete versioned directory `Cellar/<name>/<version>/` produced by evaluating a formula (pour or build). The formula is upstream metadata; the keg is local state.

## 2. RECORD

**State IS the filesystem. There is no central installed-packages manifest.**

- **Cellar presence = the primary record.** `brew list` is effectively a readdir of the Cellar/Caskroom. "Homebrew installs formulae to the Cellar at `$(brew --cellar)` and then symlinks some of the installation into the prefix at `$(brew --prefix)`".
- **Per-keg receipt:** every keg contains `Cellar/<name>/<version>/INSTALL_RECEIPT.json` (internally the `Tab` class) recording version/revision, build options, compiler, runtime dependencies, source tap, and the intent bits `installed_on_request` / `installed_as_dependency` — the latter drive `brew autoremove`. `brew bundle` sets `installed_on_request: true` on Brewfile entries precisely so autoremove won't reap them.
- **Auxiliary symlink registries** (records-as-symlinks, still filesystem): `<prefix>/var/homebrew/linked/<name>` (which keg is linked), `<prefix>/opt/<name>` (active keg pointer), `<prefix>/var/homebrew/pinned` (pin state).
- **Tap list = directory listing** of `Library/Taps/`; `brew tap` with no args just enumerates it.
- **Brewfile = the opt-in declarative record.** Lines: `tap "user/repo"`, `brew "formula"`, `cask "app"`, `mas "App", id: N` (plus `vscode`, `npm`, `cargo`, …). Round-trip: `brew bundle dump` writes "all installed casks/formulae/images/taps into a Brewfile" (`--force` overwrite, `--describe` comments, `--global` → `~/.Brewfile`); `brew bundle` installs from it; `brew bundle check` diffs; `brew bundle cleanup --force` uninstalls everything *not* in the file — "you can specify the state you wish to reach." Default location: current directory, overridable via `--file` / `$HOMEBREW_BUNDLE_FILE`. (docs.brew.sh/Brew-Bundle-and-Brewfile)

## 3. TAPS

- **A tap is a git repo of package definitions.** "Code in a tap can run with your user's privileges." (docs.brew.sh/Taps)
- **Naming:** repo must be `homebrew-<name>`; the prefix is elided in commands: `brew tap username/foobar` → clones `https://github.com/username/homebrew-foobar`. The two-argument form `brew tap <user>/<repo> <URL>` accepts any git URL and skips the naming convention.
- **Clone location:** `$(brew --repository)/Library/Taps/<user>/homebrew-<name>` — canonical path `$(brew --repository)/Library/Taps/homebrew/homebrew-core/Formula/f/foo.rb` (note the `Formula/f/` shard letter).
- **Mutation:** `brew tap` clones and thereafter `brew update` git-pulls it; `brew untap` "deletes the local repositories and no longer loads their contents" — installed kegs from that tap survive but become un-upgradeable orphans; `brew untap --force` uninstalls the tap's formulae/casks first. `brew tap --repair` fixes symlinks/remotes.
- **Resolution:** short name `vim` resolves to `homebrew/core`; fully-qualified `username/repository/vim` pins the tap. On collision, `homebrew/core` wins the short name, and "dependencies of `homebrew/core` formulae cannot be replaced by those from other taps."
- **The 4.0 bifurcation:** since Homebrew 4.0.0, `homebrew/core`/`homebrew/cask` are *not* local taps by default — formula definitions come as JSON from `formulae.brew.sh` (users may `brew untap homebrew/core`); `HOMEBREW_NO_INSTALL_FROM_API=1` restores git-tap behavior; API auto-update every 24h; `HOMEBREW_API_DOMAIN` for mirrors. Third-party taps remain git clones. (brew.sh/2023/02/16/homebrew-4.0.0)

## 4. STORE

- **Layout:** `Cellar/<name>/` is the *rack*; `Cellar/<name>/<version>/` is the *keg* (formula `prefix` = `#{HOMEBREW_PREFIX}/Cellar/#{name}/#{version}`). Prefix per platform: `/opt/homebrew` (Apple Silicon), `/usr/local` (Intel), `/home/linuxbrew/.linuxbrew` (Linux).
- **Stable pointer:** `<prefix>/opt/<name>` is a version-independent symlink to the active keg — the address other software should hardcode.
- **Link/unlink:** `brew link` "symlink[s] all of formula's installed files into Homebrew's prefix" (`bin/`, `lib/`, …), done automatically at install; `--overwrite` deletes conflicting pre-existing files; `brew unlink` removes the symlinks "for temporarily disabling a formula" while the keg stays.
- **keg-only:** "installed only into the Cellar and is not linked into the default prefix" — it still gets the `opt/<name>` link, so consumers reference it by opt path. Used when linking would shadow macOS-provided software or conflict with the current version.

## 5. IDENTITY & NAMING

- The **name is the lowercase filename**: `foo.rb`; the class is a deterministic transform: `foo-bar.rb => FooBar`, `foobar.rb => Foobar`; versioned: `foo@1.2.rb => FooAT12`. "If you change the name of the class, you must also rename the file." So identity lives in the *filename*, with the class name as a derived checksum of it.
- **Global identity = `tap-user/tap-repo/name`**; the short name is sugar resolved through the collision rules above. Homebrew/core enforces social uniqueness: "Name the formula like the project markets the product… it's `pkgconf`, not `pkgconfig`", and an existing core name is never reassigned to a different project.
- The installed keg's origin tap is recorded in its `INSTALL_RECEIPT.json` — but the Cellar rack is keyed by *short name only*, so two taps' `foo` cannot coexist installed.

## 6. VERSION MODEL

- **One moving current version per formula name.** Old majors are *separate formulae*: `foo@1.2.rb` is its own file/class in the same tap, conventionally `keg_only :versioned_formula` so it "allows parallel installation without conflicting binaries." Core gatekeeps them: major/minor deltas only, upstream must still maintain the branch, "no more than five versions of a formula (including the main one)", ABI-stable for the branch lifetime. (docs.brew.sh/Versions)
- **Multi-version coexistence in the rack is transient by default:** "Homebrew automatically uninstalls old versions of each formula that is upgraded with `brew upgrade`"; opt out with `HOMEBREW_NO_INSTALL_CLEANUP=1`. `brew cleanup` also prunes "stale lock files and outdated downloads" (cache default 120 days).
- **`brew pin <formula>`** freezes a name against `brew upgrade` (state = symlink in `var/homebrew/pinned`); `brew unpin` releases. Pins are advisory — a pinned dependency may still be upgraded if a dependent requires it.

## 7. MATERIALIZE

Install pipeline: **resolve name** (JSON API for core, or `Library/Taps` clone; fully-qualified name auto-taps) → **evaluate the Ruby formula** → **pour bottle** matching the platform tag (sha256-verified, relocated if `cellar :any`; fetched from `ghcr.io`) *or* **build from source** when: `--build-from-source`, `pour_bottle?` declines, non-default install options given, checksum mismatch, or cellar incompatibility → **keg written** to `Cellar/<name>/<version>/` with `INSTALL_RECEIPT.json` → **link**: prefix symlinks (unless keg-only) + `opt/<name>` + `var/homebrew/linked/<name>` → post-install cleanup pass removes the previous keg.

- **Uninstall:** removes the keg and its symlinks; `brew uninstall --force` "delete[s] all installed versions"; casks add `--zap`. `brew autoremove` walks receipts' `installed_as_dependency`/`installed_on_request` to reap orphaned deps.
- **Untap:** deletes the *recipes* only; kegs remain installed but lose their upgrade path (no formula to re-evaluate) unless `untap --force` uninstalls them first.

## 8. USER-MANAGED REGISTRY

- **Bootstrap:** `brew tap-new $USER/homebrew-tap` scaffolds the repo; formulae live in `Formula/` (recommended), `HomebrewFormula/`, or repo root — first found wins; casks in top-level `Casks/`; custom brew subcommands in `cmd/`. Author with `brew create <url> --tap $USER/homebrew-tap`. (docs.brew.sh/How-to-Create-and-Maintain-a-Tap)
- **Publishing = `git push`:** "A tap is just a Git repository so you don't have to do anything specific when making modifications, apart from committing and pushing." Consumers get updates through normal `brew update`.
- **Consumption:** either `brew tap alice/tap` then `brew install foo`, or one-shot `brew install alice/homebrew-tap/my-script` (implicit tap).
- **Private/org distribution:** the two-arg form `brew tap <user>/<repo> <URL>` accepts any git URL (private hosts, mirrors; `--custom-remote` to switch); private prebuilt binaries ride the same formula DSL via `bottle do root_url "..."` pointing at internal storage. Orgs thus run a registry with zero registry infrastructure: a git host plus optional blob storage.

## DESIGN TENSIONS

1. **Presence-as-record cuts both ways.** With no central manifest, installed-state can never desynchronize from reality — `brew list` cannot lie. But all metadata must live *inside the artifact* (`INSTALL_RECEIPT.json` inside the keg), so the record dies with the keg, intent bits are scattered per-directory, and any *declarative* view had to be bolted on externally (Brewfile) with an explicitly lossy dump/cleanup round-trip rather than being the source of truth.
2. **Tap = git repo makes distribution free and resolution expensive.** Publishing is `git push`, namespacing is GitHub's, private registries are any git URL — zero registry infrastructure. But update cost scales with repo history and formula count, which eventually forced the 4.0 JSON-API escape hatch: the flagship namespace (`homebrew/core`) stopped being a tap on disk while third-party taps kept the old model. The uniform abstraction split under load. Also: package definitions are executable Ruby — "code in a tap can run with your user's privileges."
3. **Short names are sugar over a hard-coded namespace hierarchy.** `vim` ≡ `homebrew/core/vim`; collisions resolve by fiat (core wins, core's dependencies are unshadowable), not by user-configurable ordering. And because the Cellar rack is keyed by short name only, tap identity exists at resolve time but is flattened away at store time — two namespaces' `foo` cannot be installed simultaneously even though the receipt knows their origins differ.
4. **Version = new identity, not constraint.** The store natively supports multi-version racks, yet the naming layer permits one current version per name; parallel majors are modeled by *minting a new package* (`foo@1.2`, `FooAT12`, `keg_only :versioned_formula`) with human gatekeeping (≤5 versions, ABI-stable branches). This trades away a version solver entirely — no SAT, no lockfiles — at the cost of coarse pinning (`brew pin` is advisory) and aggressive garbage-collection of old kegs on upgrade.
5. **Three-address storage: immutable keg → stable pointer → flattened view.** `Cellar/<name>/<version>` (immutable, versioned) is separated from `opt/<name>` (mutable, stable) and from the linked prefix (`bin/`, `lib/` symlink flattening for PATH ergonomics). `keg-only` is the pressure valve: when flattening would collide with the OS, a package retreats to opt-only and pushes path burden onto consumers — proof that the *convenience* layer, not the store, is where conflicts live.

* straight.el — mechanism brief

Primary source: README at github.com/radian-software/straight.el (master, ~4200 lines). Citations are README section headings.

## 1. UNIT OF DISTRIBUTION — package = git repo, editable working copy

- A *package* is "a collection of Emacs Lisp (and possibly other) files"; it is materialized from a *local repository* — a full git clone, not a tarball. "package.el downloads pre-built packages from central servers... while straight.el clones Git (or other) repositories and builds packages locally." (§ "What is a package?", § "Comparison to package.el")
- The clone is a live working copy: "Edit packages by editing their code, no extra steps required. Allow for manual version control operations." "You literally just edit the files (`find-function` and friends all work as you would expect). Packages will be automatically rebuilt if necessary when Emacs next starts up." (§ "Guiding principles", § "Edit packages locally")
- **Many packages, one repo**: "Multiple packages can use the same local repository. If so, then a change to the local repository will cause both packages to be rebuilt. Typically, if multiple packages are drawn from the same repository, both should specify a `:files` directive." (§ "What is a package?") The build step carves each package out of the shared repo by symlinking only its `:files` selection into its own build directory. Conflict handling: two packages sharing a `:local-repo` with differing version-control keywords → new recipe used, warning signalled.

## 2. RECIPE

- Format: `(package-name :keyword value ...)` — a plist headed by the package symbol. "Similar, but not identical" to MELPA's; `:host` instead of `:fetcher`; git-only by default. (§ "The recipe format")
- Split into **fetch recipe** (how to obtain the repo: `:type` [vc backend, default git; special cases `built-in` and `nil`], `:host` [github/gitlab/sourcehut/codeberg/bitbucket], `:repo`, `:branch`, `:fork`, `:protocol`, `:nonrecursive`, `:local-repo`) and **build recipe** (how to make it loadable: `:files` — "an almost comically powerful DSL" of globs/excludes selecting what gets symlinked; `:build` t/nil/steps/`(:not ...)`; `:pre-build`/`:post-build`; `:includes` declares "this package is a superset of that one"). No `:commit` in recipes — "To lock a package to a specific commit, use a lockfile."
- **Recipe repositories** (MELPA, GNU ELPA mirror, Emacsmirror; el-get importable) are *themselves packages* — cloned into `repos/` with `:build nil`, registered via `straight-use-recipes` (register-only, lazy-clone). A backend = fetch recipe + `straight-recipes-NAME-list` + `straight-recipes-NAME-retrieve` (+ optional `-version` for caching) + an entry in `straight-recipe-repositories`. Name-only `straight-use-package` searches them in order — "By default, MELPA, GNU ELPA, and Emacsmirror are searched for recipes, in that order." Backends translate foreign formats into straight's uniform recipe. Per-package `:source` narrows/reorders. Updating a recipe registry = `straight-pull-package` on it, like any package.
- **Precedence**: user-supplied recipe > registry recipe (registries consulted only when no recipe given). First registration wins and is cached: "The first time a package is registered... its recipe is recorded. In future registration, if you just provide the package name..., the existing recipe is reused" — so a custom recipe "must be loaded *before* all of its dependencies." Two different explicit recipes → new one used + warning. Above everything sits `straight-recipe-overrides` (alist: profile → alist of recipes): "Even if an explicit recipe is supplied to `straight-use-package`, the one given in `straight-recipe-overrides` will be used instead." `straight-override-recipe` = convenience mutator; `straight-register-package` pre-registers without cloning/building.

## 3. RECORD — the user-managed registry is the init-file itself

- "Init-file and version lockfiles as the sole source of truth. No persistent state kept elsewhere." "straight.el determines what packages are to be loaded implicitly, by your invocations of `straight-use-package` during Emacs initialization." (§ "Guiding principles")
- Contrast with imperative install (package.el ≈ brew): "package.el loads every package you ever installed at startup, even if some of those packages are no longer referenced by your init-file"; straight.el "absolutely refuses to permanently install a package without an explicit reference to it in your init-file." Demand *is* the record; there is no separate install database to drift. Interactive `straight-use-package` gives only a temporary install.
- **Lockfile**: `M-x straight-freeze-versions` writes current revisions of every package, every recipe repository, *and straight.el itself* to `~/.emacs.d/straight/versions/default.el`; freeze first verifies the registry is current (offers to reload init) and "ensure[s] that all your local changes are pushed (remember, we are aiming for perfect reproducibility!)." Pinned unit = VC commit identifier (40-char SHA-1). `straight-thaw-versions` checks the revisions back out. Lockfiles are meant to be committed with the config; placed before first launch on a new machine, clones check out the locked commit immediately.
- **Profiles layer lockfiles**: every registration is tagged with `straight-current-profile`; `straight-profiles` maps profile → lockfile filename; freeze writes one lockfile per profile. Designed so a distributed config (Radian, Spacemacs) locks its packages in its repo while the user's local additions lock in their dotfiles. Conflicts: "the last one in `straight-profiles` will take precedence" — later layers win.

## 4. STORE — repos/ vs build/

- `~/.emacs.d/straight/repos/` holds the clones (user-editable, committable, pushable); `straight/build/` holds one directory per *package* containing symlinks into the repo for each `:files`-selected source file, plus generated artifacts: `NAME-autoloads.el` and `.elc` byte-code.
- Why two layers: (1) isolation — carve one package out of a multi-package repo and keep irrelevant files off the load-path; (2) generated outputs live outside the working tree so the repo stays clean for VC; (3) symlinks make edit-in-place free — editing the build path *is* editing the repo. On Windows `straight-use-symlinks` nil: files copied, `find-file` advised so edits redirect to the repo copy.
- **Modification detection** (`straight-check-for-modifications`, default `(find-at-startup find-when-checking)`): a bulk optimized `find(1)` against saved build timestamps on the first `straight-use-package` call of init (~500ms for ~100 packages on SSD). Alternatives: `check-on-save` (`before-save-hook` — no startup cost, misses out-of-Emacs edits), `watch-files` (persistent watchexec/python3 watcher), `find-when-checking` (only on explicit check). Rebuild also on recipe or Emacs-version change.

## 5. IDENTITY — package name ≠ repo name

- "A package also has a name, which must be unique. This is the name that is used for the folder holding the package's files" (in `build/`). The local repository "also has a name, which may or may not be the same as the package's name" (folder in `repos/`). Canonical example: package `straight` builds from local repo `straight.el`. `:local-repo` defaults from VC settings (usually the last component of `:repo`) "or as a last resort the package name." The lockfile keys on *local-repo* names, not package names.
- **Recipe inheritance**: with `straight-allow-recipe-inheritance` non-nil, "you only need to specify the components of the recipe that you want to override" — e.g. `(el-patch :fork "your-name/el-patch")` inherits everything else from MELPA's recipe. `:fork` itself inherits missing pieces from the upstream half.

## 6. VERSION MODEL — the repo IS the version

- No version number anywhere in the system: no semver, no MELPA date-versions, no `:commit` in recipes. A package's version *is* whatever revision its working copy is at; clone gets the branch tip unless a lockfile names a commit. The fetch recipe + lockfile "precisely define the state of a local repository... a 'canonical' state that you may revert to at any time" — but the working copy itself remains the operative truth.
- Updating = ordinary VC verbs, not a version resolution step: `straight-fetch-package/-all`, `straight-merge-...`, `straight-pull-...` (fetch+merge), `straight-push-...`; no git ops at startup except first clone. Downgrade = check out an older commit or thaw. "straight.el allows you to check out any Git revision of any package."
- Local patches are first-class: commit in `repos/<name>/`, push upstream; the `:fork` keyword gives a package "both an upstream repository and a fork" (pull from one, push to the other). Freeze refuses to record unpushed commits — a locked state must be reconstructible from public remotes. Pinning-to-tag/release is explicitly *not* a feature ("This is a planned feature"), only the experimental `straight-x` pinned-profile workaround.

## 7. MATERIALIZE — clone on demand, build = symlink + compile

- `straight-use-package` performs three ordered actions: **register** (resolve/record recipe in caches), **clone** if the local repo is missing (checking lockfiles for a commit to check out), **build+load** if changed since last build. Each stage can be the stopping point: register-only (recipe repositories), clone-without-build (straight's own bootstrap), deferred installation.
- Build = symlink `:files` into `build/<package>/` → parse main file for dependencies and recursively `straight-use-package` them → byte-compile → extract autoloads. Load = add build dir to `load-path`, eval autoloads.

## 8. BOOTSTRAP — straight installs straight

- The init-file carries a fixed snippet: if `straight/repos/straight.el/bootstrap.el` doesn't exist, `url-retrieve-synchronously` pulls `install.el` and evals it; then `(load bootstrap-file)`. `install.el` clones straight.el into its own `repos/` — consulting the user's lockfile so even the package manager's revision is pinned — after which straight registers itself as a normal package.
- Since the manager is a package in its own store, all machinery applies reflexively: it appears in the lockfile, can be forked (`straight-repository-user`), re-branched, or fully re-reciped via `straight-recipe-overrides` — which must be set *before* the bootstrap, precisely because `straight-override-recipe` (a function straight defines) can't run before straight exists; only the plain variable can predate its consumer. Caveat: a fork changing recipe *interpretation* can't affect the interpretation of its own recipe without replaying install.el's two-phase trick.

## DESIGN TENSIONS

1. **Record = code, not data.** The registry the user manages is a Turing-complete init-file; demand is expressed by *executing* it. This buys perfect no-drift (nothing installed that isn't demanded) and free abstraction (profiles are just dynamic bindings around load), but costs enumerability: straight can't know the package set without a full, side-effect-faithful re-run of init, and freeze must first ask you to reload. A data registry is queryable; a code registry is only replayable.
2. **Repo-as-version dissolves versioning — and pushes its costs to the edges.** With no version numbers there is nothing to resolve, no solver, no downgrade asymmetry: every state a repo can be in is a valid "version," and lockfiles are mere coordinates (SHA per local-repo). The costs: dependency ranges are inexpressible (deps are names only, always default recipes), tagged-release pinning needed a bolted-on experimental profile hack, and reproducibility must be *policed* socially — freeze refuses unpushed commits because a SHA is only a version if a remote can serve it.
3. **Recipe/package split makes the namespace self-hosting.** Recipes (how to obtain/build) are separated from demand (that you want it), and the recipe *sources* are themselves packages in the same store, updated, locked, and overridden by the same machinery. One mechanism, applied reflexively, all the way down to the manager's own recipe. The tension: name-only lookup + first-registration-wins makes resolution order-sensitive — custom recipes must precede any dependency edge that would register the default first, and override precedence needs three tiers (registry < explicit < `straight-recipe-overrides`) plus profile last-wins to stay deterministic.
4. **Editable store forces the store/build bifurcation.** Because the store is a first-class working copy (edit, commit, push — the *same* directory the manager manages), derived artifacts can't live in it and multi-package repos can't be loaded from it directly. Hence two layers: sacred mutable source (`repos/`, keyed by repo name) and disposable projection (`build/`, keyed by package name, symlinks + elc + autoloads). Symlinks collapse the write path while keeping the read path isolated. The price is a cache-invalidation problem the manager must solve honestly — a menu of modification detectors trading startup latency vs. coverage vs. daemons — because "did the human touch the source?" replaced "which version is installed?" as the central question.
5. **Bootstrap reflexivity finds its floor.** Everything is overridable through the system except the code that starts the system: the snippet is a fixed quine-seed in the init-file, self-configuration must use plain variables set before load rather than the manager's own functions, and a fork altering recipe semantics cannot apply those semantics to its own recipe without a staged two-phase install. Lesson: a self-hosting manager still needs a minimal, dumb, externally-fetched kernel, and its pre-boot configuration surface must be data (variables), not API.

* vivalence nature — the laws a package layer must fit

Docs (`documentation/content/`) contain **zero** mention of vip/pensieve/accio — the code below is the only truth.

## A. THE MANIFEST — identity is the manifest, filesystem is cosmetic

A `.viva.js` file is an ES module; `paladin.read.viva` = `import(path)` → `cast.viva(module)` (`subsystems/paladin/belt/read.js:36-39`), which accepts any module exporting `manifest` (or a `default` factory) — `subsystems/typology/gestalten/cast/primitives.js:4-16`. Discovery is a filename-pattern walk (`/\.(viva.js|viva.ts|viva.md|viva.org)$/`, `subsystems/paladin/belt/find.js:35`), but **classification is `manifest.type`**, never the filename: only 2 of 5 package roots are literally named `package.viva.js`. `paladin.find.type(path, type)` filters on `module.manifest?.type === type` (`subsystems/paladin/belt/find.js:56-62`).

Package manifest, verbatim (`registry/viva/package.viva.js`):
#+begin_src js
export const manifest = {
  owner: "@viva",
  type: "package",
  slug: "viva", // fork 5, RESOLVED — beef: "go on @viva instead of @vivalence"
  version: "0.0.1",
};
#+end_src

Module manifest, verbatim (`registry/education/topologies/word/word.viva.js`):
#+begin_src js
export const manifest = {
  type: "topology",
  slug: "word",
  name: "Words after Universal Dependencies",
  version: "0.2.0",
  traits: ["DATASET"],
};
export const dataset = new Dataset({ symbol: "dataset/symbols" });
#+end_src

Manifest shape is `{owner?, type, slug, name?, description?, version, traits[]}` — **metadata only**. Everything behavioral is a *sibling export*: `registry/education/modes/games/judge/judge.viva.js:132` `export { manifest, app, emitter, dataset }`; francesca exports `harness`, `tools`; the italian topography exports `freight`, `dataset`; a variant exports `daemons/runtime/lighthouse/clients/services` (`registry/viva/variant/localhost/localhost.viva.js`). Identity string = `Manifest.get identifier` → `${owner}/${type}/${slug}` (`subsystems/paladin/prototypes/manifest.js:6-8`). Types in the wild: `package, domain, topology, topography, game, tactic, teacher, dashboard, variant, service, lighthouse, datamap, fixture, daemon` — the taxonomy is open; pensieve treats `type` as an opaque map key.

`owner` on a package root is **mandatory** and stamps every module in the mount; a module's own `manifest.owner` locks/overrides it; a mount with modules but no owner **throws** (`subsystems/paladin/prototypes/vip.js:20-31`; pinned by `subsystems/paladin/tests/vip.test.js:15-56`). Stamping happens on a **copy** — `read.viva` returns the live module namespace, never mutated (`vip.js:26-31`).

## B. THE THREE LAYERS — ledger / vip / pensieve

All three are siblings on the paladin singleton, constructed in `subsystems/paladin/prototypes/paladin.js:26-29` ("mountables — siblings of vip, own their state, fn.once mount()").

**Ledger** (`subsystems/paladin/prototypes/ledger/ledger.js`) — the *system/process* surface: `mount()` (fn.once, `ledger.js:13`; builds `Instances` + `Registry` at `scope.ledger.branch("registry.json")`, `ledger.js:16-28`), `lock(instance,process)`, `log`, `locks`, `spawn`, `boot`, `kill`, `arm`, `teardown`. Its `Registry` (`subsystems/paladin/prototypes/ledger/registry.js`) is the **persisted install list**: `read()` (json or null), `write(locations)`, `seed(scope)` = `Deno.readDir(scope.absolute)` → every directory becomes a location (`registry.js:15-22`). Live file `testament/ledger/registry.json` holds 4 absolute paths — `young-ladys-primer` is on disk but **not** in the file: once `registry.json` exists it is the authority (`read() ?? seed()`), so *not-listed = deliberately not installed*. That file IS the package-install ledger today.

**Vip** (`subsystems/paladin/prototypes/vip.js`) — the acquisition seam: `mount(root)`, `supply()`, `list(query)`, `accio(query)`, `accioMany(many)`, `accioMap(many)`. `supply()` (`vip.js:40-46`):
#+begin_src js
await this.paladin.ledger.mount(); // fn.once — self-priming, no boot-order landmine
const locations = await this.paladin.ledger.registry.read()
  ?? await this.paladin.ledger.registry.seed(this.paladin.scope.registry);
for (const location of locations) await this.mount(this.paladin.source(location));
#+end_src
Locations resolve through `paladin.source` (`subsystems/paladin/belt/source.js`): absolute as-is · `./`/`../` relative to `INIT_CWD` · `{file,source}` relative to declaring file · bare segment = `scope.repository.branch(target)`.

**Pensieve** (`subsystems/paladin/prototypes/pensieve.js`) — the in-memory index, `extends Map`, nested `owner → type → slug → version → module`: `register(module)` (throws on missing owner, wraps manifest in `Manifest`, `pensieve.js:5-24`), `revelio({owner,type,slug,version})` (no version → `latest`; version → `semver.satisfies` range match, `pensieve.js:26-37`), `latest(slugMap)` (semver sort), `byType(type)`. Crucially `revelio` returns `own(module)` (`pensieve.js:54-80`) — a deep per-demand **clone** (prototype-preserving, `WeakMap` cycle-guarded) that shares anything carrying `~kind` (immutable leaves). Every daemon gets its own minted copy of a module; the pensieve's registered original is never handed out.

Call direction: `vip.supply` → `ledger.registry` (persisted) → `vip.mount` → `pensieve.register` (memory). Demand: caller → `vip.accio` → `cast.lookup` → `pensieve.revelio`. The ledger never touches the pensieve; the pensieve never touches disk.

## C. SCOPE RESOLUTION — the conditional-resolver Proxy

`paladin.scope` is a Proxy over a `Map<name, [condition, resolver]>` (`subsystems/paladin/belt/scope.js`): `get` returns `condition?.() ? resolver?.() : undefined`; `has`/`ownKeys`/`getOwnPropertyDescriptor` all condition-gate, so an unavailable scope is invisible, not null-ish garbage. Declared in `subsystems/paladin/lifecycle/populate.js scopes()`:

- `ledger` — condition `() => true`; `VIVA_LEDGER_MOUNT` ?? `$HOME/.viva` (`populate.js:23-30`).
- `repository` — always; `VIVA_REPOSITORY_MOUNT` ?? `new URL("../../../", import.meta.url)` — i.e. the repo containing paladin itself (`populate.js:70-77`).
- `registry` — condition `Deno.env.has("VIVA_REGISTRY_MOUNT") || paladin.is.citizen`; explicit env wins, else `scope.repository.branch("registry")` (`populate.js:78-90`).
- `variant`/`environment`/`mountpoint` — env-var'd or derived from variant, citizen-gated (`populate.js:32-67`).

`paladin.is.citizen` = server-side runtime with write access, not deployed/browser (`subsystems/paladin/belt/is.js:29-33`). Boot is 13 lines: `new Paladin()` → `populate.env` (only `VIVA_`/`PUBLIC_VIVA_` → env, `SECRET_VIVA_` → secret) → `populate.scopes` → citizen: `integrate.statements` (`subsystems/paladin/mod.js`). `paladin.publish()` mirrors `PUBLIC_*` back into `Deno.env` (`subsystems/paladin/belt/publish.js`).

## D. SUPPLY / DEMAND

**Supply is SYSTEM-level, boot-triggered once.** Runtime: `systems/runtime/run.js` → `die.populate()` → `lifecycle.population.registry(this)` (`systems/runtime/die.js:17`) → `await paladin.vip.supply()` (`systems/runtime/lifecycle/populate.js:6-8`). Ghost triggers it per-command: `systems/ghost/trajectories/instance/clone.js:75`, `variant/clone.js:13`, `system/doctor.js:132`. `viva ledger install` scaffolds + force-reseeds (`systems/ghost/trajectories/ledger/install.js:19` calls `registry.seed(paladin.scope.registry)` unconditionally); `viva system init` pins `scope.ledger` by re-declaring the scope entry and persists `VIVA_LEDGER_MOUNT` to `~/.config/viva/env` (`systems/ghost/trajectories/system/init.js:16-17,36-53`) — the same file `systems/ghost/ghost.sh` sources before `exec deno run --config "$VIVA_REPOSITORY_MOUNT/deno.jsonc"`.

**The variant declares NOTHING about packages.** It demands modules by identifier string inside daemon/service *masks*: `registry/viva/variant/localhost/education.js` — `kernel: ["@education/domain/language-learning", "@education/topology/word", …]`, `datamap: { module: "@viva/datamap/libsql", … }`, `hallucinators: [{ module: "@viva/hallucinator/anthropic", … }]`, `consume: { nlp: { module: "@viva/service/nlp-stanza" } }`. The demand side resolves these at daemon population: `die.register = await paladin.vip.accioMap(registry)` (`systems/runtime/daemon/lifecycle/population.js:19`) — `accioMap` recurses over `{slug: "id" | {module} | [] | {}}` shapes, and `accioMany` returns `{service, mask}` pairs when the query object carries `.module` (`vip.js:61-89`). Services: `paladin.vip.accio(mask.module)` per service mask (`systems/runtime/lifecycle/populate.js:39`). One in-registry consumer too: `registry/viva/lighthouse/multiplayer/server/entities.js:16`.

**Query parsing**: `cast.lookup` (`subsystems/typology/gestalten/cast/primitives.js:24-48`) accepts a string `"@owner/type/slug@ver"` (split on `/`, then `slug@version` on `@`), a `{owner,type,slug}` object, `{module: …}`, `{manifest: …}`, `{remote: …}` — all recursively normalized.

**The two failure classes** (`vip.js:52-59`, pinned `tests/vip.test.js:58-68`):
1. `[VIP] package @X not supplied on this system` — owner absent from pensieve: demand outran supply / package not installed.
2. `[VIP] Module 404: {...}` — owner present, module missing: bad identifier or wrong version.
Plus the supply-side third: `[VIP] mount ...: package declares no owner` (`vip.js:22-23`).

## E. IDIOM — house constraints, each with an exemplar from this code area

- **Functional lifecycle, state is data**: `subsystems/paladin/lifecycle/populate.js` exports free functions `env(paladin)`, `scopes(paladin)`; `mod.js` sequences them over the singleton. No OOP boot ceremony; lazy mounts are `fn.once(this.mount.bind(this))` (`ledger.js:13`, `variant.js:94`) so any caller can self-prime ("no boot-order landmine", `vip.js:41`).
- **No imperative walks — `paladin.find` is THE walk primitive**: `belt/find.js:27-35` defines `walk(pattern)`; `viva`, `data`, `json`, `type` are derived from it. Consumers never hand-roll: `vip.mount` uses `paladin.find.viva` (`vip.js:13`), variant resolve uses `paladin.find.type` (`prototypes/variant.js:17`). The walk skips `bak/`, `archive/`, `slp/` (`find.js:11`) — that's why 40+ `bak/` manifests under `registry/` never register. (Raw `Deno.readDir` appears only inside paladin itself — `registry.js:17`, `ledger.js:43` — "paladin does the OS"; carriers hold declarations.)
- **Barrels**: every directory exports through `index.js` — `systems/ghost/trajectories/ledger/index.js` is one line (`export { install } from "./install.js"`); `systems/runtime/lifecycle/index.js` renames namespaces (`export * as population from "./populate.js"`). Cross-module imports ride barrels/specifiers, never deep relative paths.
- **Typology primitives over hand code**: `Path.branch` for path composition (`ledger.js:19`), `Env` proxy for env (`paladin.js:9-10`), `cast.lookup` for identifier parsing (`vip.js:53`), `Vector.open` for every dispatch surface.
- **No authored comments**: the comments that exist are ownership-attributed decisions, not narration — `belt/source.js:4-7` (`beef: "absolute paths, relative to cli execution…"`), `registry/viva/package.viva.js:4`, `vip.js:26-27` (a mutation-hazard law).
- **Manifest immutable — new capability = sibling export, never a manifest field**: `judge.viva.js` grows behavior by exporting `app`/`emitter`/`dataset` beside `manifest`; `localhost.viva.js` puts all wiring (env-reading thunks like `() => new Url(paladin.env.get(...))`, hydrated lazily by `variant.js:3-10`) in sibling exports. Traits (`manifest.traits`) are the only sanctioned manifest-borne behavior switch, and they're resolved by trait appliers, not by the manifest.
- **Two-throw error discipline**: distinguish *system state* errors from *query* errors (accio's "not supplied" vs "Module 404") — any registry layer must keep "package not installed" and "module doesn't exist" as separate failure classes.

## F. IMPORT RESOLUTION REALITY for an out-of-tree package

- **Workspace**: `deno.jsonc:11-22` — members are `systems/{runtime,kajuit,ghost}`, `subsystems/{typology,paladin,dapper,drapes,sheets}`, `documentation`. **`registry/` is NOT a workspace member and no registry package has a `deno.json`** (verified: zero `registry/*/deno.json*`). Registry packages have no name, no exports, no version of their own beyond the manifest.
- **`@vivalence/*` resolution** comes solely from workspace member names (`subsystems/typology/deno.jsonc` `"name": "@vivalence/typology"` + `exports`; same for paladin, runtime). `import_map.json` has **no** `@vivalence` entries — only jsr/npm. Nothing is published (all `version: "0.0.1"`, docker images only).
- **Measured**: `deno info registry/.../word.viva.js` resolves `@vivalence/typology` → `file:///…/subsystems/typology/mod.ts` (328 deps). And a copy of the same file placed **outside the repo** resolves identically when run with `--config deno.jsonc` — workspace-name mapping applies to the whole module graph of a process launched under the root config, not just to in-tree importers. Since every loader path is a dynamic `import(absolutePath)` inside such a process (`belt/read.js:29`; ghost launches via `ghost.sh` with `--config "$VIVA_REPOSITORY_MOUNT/deno.jsonc"`), **an out-of-tree package's `@vivalence/*` imports work — but are pinned to that host checkout's source tree**. Standalone execution of the package (its own `deno run`, its own CI) has no mapping and fails; there is no vendoring, lockfile hand-off, or published fallback.
- **Buffer views double the pin**: the esbuild bundler aliases `@vivalence/typology` → `subsystems/typology/mod.client.js` and `@vivalence/drapes` → `subsystems/drapes/mod.js` via `paladin.scope.repository.branch(...)` (`subsystems/paladin/belt/bundler.js:10-13`) — client bundles resolve against repo paths, not the import map at all.
- **Location freedom already exists**: `registry.json` entries are absolute paths and `paladin.source` accepts absolute / cwd-relative / `{file,source}` / bare-repo-segment, and `VIVA_REGISTRY_MOUNT` can point the seed anywhere. So the *mount* mechanics are location-agnostic today; the *import-resolution* coupling to the host repo (and absence of any publish/version-distribution channel — semver ranges in `revelio` are live but every package is `0.0.1`) is the actual frontier a registry layer must address.
