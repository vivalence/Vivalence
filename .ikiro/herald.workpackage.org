#+TITLE: Herald — unified self-description route family
#+AUTHOR: Vivalence
#+DATE: 2026-04-17
#+STATUS: DESIGN

* Intent

Collect the scattered family of metadata-publishing routes (~/manifest~,
~/cargo~, ~/datamap~, ~/buffered~, ~/freight~, etc.) under one named prefix:
*=/herald/*=*.

Herald is the self-description layer: *who I am, what I offer, what I
can do*. Not dataflow, not queries, not mutations, not reactive state.
Cacheable by convention. Trait-contributed. Composable.

Enables the INSITU controller (in the E panel) to read a mode's full
capability surface via a single sitemap, rather than hardcoding route
names across the client.

* Why

| Problem                                                           | Herald answer                             |
|-------------------------------------------------------------------+-------------------------------------------|
| ~/manifest~, ~/cargo~, ~/datamap~ scattered at daemon root        | Grouped under ~/herald/~                  |
| ~/buffered~, ~/freight~ added to mode root by traits              | Grouped under ~/mode/.../herald/~         |
| No convention for trait-contributed metadata routes               | Traits write under their mode's herald    |
| Client hardcodes route names per capability                       | Client reads ~/herald/~ sitemap first     |
| No home for cortex faculty table, coming CONVERSATIONAL capabilities | ~/herald/cortex~, ~/herald/speech~, etc. |

* Contract

- *Self-description only.* Metadata about what exists and what's on
  offer. Not state (~/status~ stays separate — it's reflective
  telemetry, different family). Not identity (~/userspace/handshake~
  stays under userspace — auth confirmation, not capability).
- *Cacheable per connection.* Never changes mid-session. Client fetches
  on bind, stores, reuses. Daemon pushes ~/herald/refresh~ over the
  session socket if capabilities hot-reload.
- *Trait-contributed.* Traits publishing capability routes write under
  the owning mode's ~/herald/~. E.g. BUFFERED writes ~/herald/buffered~.
- *Public-by-default, auth-gated when sensitive.* Manifest and sitemap
  typically pre-auth; cortex faculty table and mode-level herald may
  be post-auth depending on tenancy concerns.
- *Sitemap-rooted.* ~GET /herald/~ returns an index of available herald
  routes at that scope. Client reads sitemap, fetches what it
  recognizes — no hardcoded route table.

** Explicitly not herald (stay put)

- ~/status~ — live state (ALIVE/STOPPING). Reactive. Separate family
  — *pulse* or *vitals* (future rename).
- ~/userspace/handshake~ — post-auth identity confirmation. Stays under
  ~/userspace~.
- ~/batch~, ~/auth/*~, ~/entities/*~, ~/dialogue/*~, ~/connect~,
  ~/view/*~ — dataflow, transport, static assets.

* New aperture module

Add ~systems/runtime/daemon/aperture/herald.js~:

#+BEGIN_SRC js
export async function herald(daemonDie) {
  const aperture = daemonDie.good.aperture;
  const branch = aperture.branch("/herald");

  branch.open("/", () => sitemap(branch));                     // sitemap
  branch.open("/manifest", () => daemonDie.good.manifest);     // moved from /manifest
  branch.open("/cargo", () => daemonDie.good.cargo);           // moved from /cargo
  branch.open("/datamap", () => shard.datamap.strip(...));     // moved from /datamap
  branch.open("/modes", async (body) => { ... });              // moved from /modes/:type/:method
  branch.open("/cortex", () => cortexManifest(daemonDie));     // new
}
#+END_SRC

Mode-level herald lives on ~mode.aperture.branch("/herald")~ —
constructed by ~daemon/lifecycle/resolution.js~ when each mode is
mounted. Traits (BUFFERED, FRAUGHT, CONVERSATIONAL) add routes
under =mode.aperture.herald= instead of the mode root.

Sitemap generator walks the branch's child routes and lists them.
One helper, shared between daemon-level and mode-level heralds.

* Consequences for INSITU controller (E panel)

Client-side composition of the session controller surface reads from
herald:

1. On daemon bind, client fetches ~/herald/~ → sitemap →
   fetch ~/herald/cortex~ → ~daemon.cortex.faculties~.
2. On mode activation (thread ACTIVE + mode attached), client fetches
   mode's ~/herald/~ → sitemap → fetches only declared capability
   routes (buffered, speech, transcription, ...).
3. INSITU controller renders controllers for the *intersection*:
   present-on-mode ∧ supported-by-cortex. Nothing shown for
   unsupported slots. No greyed-out lies.

This makes the INSITU E-panel a pure derivation, not authored wiring.

* Open questions

- *Sitemap format*: flat list of relative paths (~["manifest",
  "cargo", ...]~) or structured with metadata per entry
  (~[{name, path, auth, cacheable}]~)? Lean flat for v0; upgrade
  when we need auth markers on the client.
- */status* home: keep at root (current) or move to its own family
  word (*pulse*, *vitals*)? Orthogonal to herald — separate
  workpackage if we commit.
- *Auth gating default*: all-public except explicit opt-in to auth,
  or all-post-auth except explicit opt-out? Default post-auth is
  safer; ~/herald/manifest~ and ~/herald/~ sitemap opt-out since
  client needs them pre-login.

* Why:

Tracks the herald migration as its own work. Keeps session socket diff
(longdistance M4.0) clean — doesn't tangle route-reorg with new
transport layer.

* How to apply:

Land this before or alongside M4.0's ~/connect~ route. The session
socket mounts at daemon root (not under herald — it's dataflow, not
metadata). But the INSITU controller that decides whether to open the
session reads herald. So herald wants to exist before the client-side
INSITU controller lands.
