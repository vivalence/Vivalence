* typology-internals-import-their-own-barrel — SETTLED LATENT (ruled post-m26)

** Symptom

Under vite's SSR module runner every kajuit route 500'd:

#+begin_example
[500] GET /
TypeError: Cannot read properties of undefined (reading 'array')
    at new Signature (subsystems/typology/prototypes/signature.js:12:35)
    at new Pattern   (subsystems/typology/prototypes/pattern.js:9:1)
    at Vector.branch (subsystems/typology/prototypes/vector.js:28:21)
    at Vector.open   (subsystems/typology/prototypes/vector.js:51:10)
    at eval          (subsystems/typology/gestalten/belt/skill/buffer.js:19:4)
#+end_example

Deno ran the same code green for a whole session. Only the second module
runner exposed it.

** Root cause

*Typology's internal modules import from typology's own public barrel*, which
re-exports them — a cycle. Every hop on the crash path does it:

#+begin_example
prototypes/vector.js:1     import { Pattern, Signature }    from "@vivalence/typology";
prototypes/pattern.js:1    import { object, is, hash }      from "@vivalence/typology";
prototypes/signature.js:1  import { array, hash, is, cast } from "@vivalence/typology";
#+end_example

Measured, whole package: *62 files import their own barrel* — prototypes 23/48,
gestalten 34/76, entities 4/21, specimen 3/2, schematics 1/26. A module evaluated
before the barrel finishes populating sees =undefined= for every named import;
which modules those are is the module runner's choice, and runners differ.

** Why it only bit now

Two conditions must coincide: (a) a typology-internal module doing WORK at module
scope, and (b) that work reaching the barrel. Measured: before m26 there were
*ZERO* module-scope =new Vector/Aperture/Connection= constructions inside
=prototypes/= or =gestalten/=. =belt/skill/*= was the first, so nobody had ever
armed condition (a).

*Registry modules are NOT affected and never were* — 28 of them build
=export const tools/emitter/harness = new Vector()= at module scope today. They
sit DOWNSTREAM of the barrel, not inside it, so the barrel is fully evaluated
before they run. The hazard is specific to modules the barrel re-exports.

** Attempts

- *Deep-relative imports in the leaf — DID NOT FIX.* At crash time
  =belt/skill/buffer.js= already imported =../../../prototypes/vector.js= and
  =../../../schematics/v.js=. It bought exactly one hop before rejoining the same
  cycle three frames deeper. The trace is the proof: it never fails in the leaf's
  import line.
- *Memoized thunk — FIXED, landed.* =let vector; export const buffer = () =>
  (vector ??= new Vector()…)= — the repo's existing idiom for this hazard
  (=schematics/prototypes/yield.js= uses it for the same reason). Construction
  moves to first CALL, by which time every module is evaluated.

** Why not fixed now (the debarrel)

Making typology's internals import each other by relative path would take the
barrel off the critical path and is a genuine cycle-smell fix. NOT done:

1. 62 files is a sweep across the HOLY layer — needs beef.
2. It does not close the bug CLASS. Relative imports make the graph explicit
   rather than funnelled; internal cycles remain possible and module-scope work
   stays hostage to eval order. Laziness makes the hazard impossible; debarreling
   only makes the current order less fragile.
3. It cuts against the standing import doctrine one layer up
   ([[feedback_import_through_barrel]]: kajuit imports THROUGH the barrel, never
   deep paths). A package-internal exception is a NEW rule, beef's to state.

Do the measurement first if it is ever picked up: enumerate the actual cycle set,
do not sweep 62 files on a hunch.

** Resolution (ruled)

Beef RULED the internal self-barrel imports STAY — "i might actually like teh
internal barrel imports again" — and rejected both the thunk ("categoric no")
and any relative-import sweep. The fix was an OWNERSHIP move: the skills (the
only eval-time constructors inside the barrel) emigrated to
=systems/runtime/daemon/skills/=, downstream of the barrel, module-scope
=new Vector()= restored. The entities followed to =daemon/entities/= for the
same reason (their own emigration, not this bug).

Standing law, superseding the thunk law: *daemon-dependent effects do not live
in typology* — a layering rule that enforces itself. The 62-file cycle remains,
LATENT WITH NO TRIGGER: zero module-scope construction inside the barrel. The
memoized-thunk idiom (=schematics/prototypes/yield.js=) stays valid for anything
that must construct inside the barrel in the future. Registry + daemon modules
are unaffected — downstream.

* v-facade-pins-typebox-in-every-client-bundle — OPEN (trailing issue on m24)

** Symptom

Every buffer-view bundle carries typebox — 292 KB of 551 KB prod for
=rep-o-mat=, including typebox's *script parser* (15 KB) and its
*per-locale files* (=el_GR= 7 KB, =ru_RU= 7 KB, =hi_IN=, =th_TH=, …).
A rep game that imports =array.shuffle= and =string.fold= ships a schema
compiler and Greek error messages.

** Root cause

=subsystems/typology/schematics/index.js= assembles the =v= facade by
MUTATING the binding it imported from =./v.js=:

#+begin_src js
import { v, entityFactory } from "./v.js";
import * as scalars from "./scalars/index.js";
v.scalars = scalars;
v.rel = (schema) => v.union([scalars.ID, v.object({}, { additionalProperties: true })]);
v.literal = entityFactory(entities.LiteralDescriptor, entities.DataEntitySchema);
export { v };
#+end_src

Top-level mutation of an imported binding is a side effect esbuild may not
drop, so the module — and everything it reaches — is retained no matter what
the view actually imported. =mod.client.js= puts it in the graph via
=export * from "./schematics/index.js"=.

** Evidence

Shortest path, from the esbuild metafile:

#+begin_src text
<stdin> → registry/…/rep-o-mat/buffer/RepOMat.svelte
        → subsystems/typology/mod.client.js
        → typology/schematics/index.js
        → typology/schematics/v.js → typebox
#+end_src

Probe bypassing the barrel: =gestalten + prototypes, NO schematics: 457 KB,
typebox present: false=.

Isolated 4000-export fixture — **only one construction shape shakes**, and
the near-misses are indistinguishable by eye:

| construction                                     | v unused | v used |
|--------------------------------------------------+----------+--------|
| =export const v = { check, object, heavy }=      |     32 B | 214968 |
| =export const v = { check: core.check, heavy }=  |   214944 |        |
| =export const v = { ...core, heavy }=            |   214876 |        |
| =export const v = { ...core, get heavy() {…} }=  |   214917 |        |
| =core.heavy = heavy; export const v = core=      |   214863 |        |

ONE property access, spread, or call anywhere in the initializer marks the
whole statement impure and everything it references is retained. Getters do
NOT rescue it. Identifier references only.

** Why not fixed now

beef wants =import { v } from "@vivalence/typology"= to keep working
everywhere (73 call sites) — so the cheap fix (drop schematics from the
client barrel, one subpath import in
=registry/playground/modes/chaosmonkey/oracle/buffer/Oracle.svelte=, the
ONE client consumer) is off the table. The real fix needs =v= built as a
single pure object literal in ONE module, which collides with the cycle:
=scalars= / =primitives= / =entities= / =prototypes= import =v= and call it
at module scope.

Two routes, neither picked:
1. *factories* — each schema module exports =(v) => ({…})=. No cycle, touches
   every schema file. ~half a day.
2. *split core* — =v.js= keeps only the typebox wrappers, schema modules
   import that (no cycle), one new module builds the full =v= literal. One
   import line per schema file. ~2 hours.

** Why typebox itself is 292 KB — the same defect, one layer down

typebox is not inherently huge. What it ships us:

| build/system/locale |  134 KB | *41 languages of error messages* |
| build/schema/engine | 32.3 KB | the validator                    |
| build/type/script   |   25 KB | a runtime TypeScript-syntax parser |
| build/type/engine   | 24.5 KB | the validator                    |
| format/guard/value  |  ~35 KB | real work                        |

46% is i18n. Nothing outside =locale/= references the =Locale= namespace —
=rg "\bLocale\b" build --glob '!**/locale/**'= returns NOTHING — so the 40
non-default locales are pure dead weight. They are retained because
=typebox/build/index.mjs= ends with:

#+begin_src js
export * as Type from './typebox.mjs';
import * as Type from './typebox.mjs';
export default Type;
#+end_src

A materialized namespace plus a default export of it — *the exact defect
deleted from =drapes/mod.js= this session*, sitting in the dependency.
=v.js= does =import { Type } from "typebox"=, which touches the namespace,
which pins =typebox.mjs= → =system.mjs= → =locale/index.mjs= → all 41.

*Ruled out — bundler configuration.* esbuild's =onResolve= can return
=sideEffects: false=, and typebox declares no =sideEffects= field of its
own, so this looked like the free fix. Measured on =rep-o-mat=:

#+begin_src text
as-is              total 553 KB   typebox 292 KB   locales 134 KB
sideEffects:false  total 553 KB   typebox 292 KB   locales 134 KB
#+end_src

effect — esbuild cannot drop members of a namespace object that is used. No
esbuild setting fixes it; only not touching the namespace does.

*Ruled out — upgrading.* typebox latest is 1.3.12 (2026-08-10); we pin
1.3.0. =build/index.mjs= is byte-identical on the pin, =locale/index.mjs=
identical, =_locale.mjs= down to 40 modules from 41 (they de-duplicated a
doubled =fr_CA=). Upgrading buys ~7 KB.

*Untested, cheapest lead for next session.* =v.js= touches exactly 15
members — =Type.{Any,Array,Boolean,Integer,Intersect,Literal,Null,Number,
Object,Optional,Record,Ref,String,Union,Unknown}=. The =./type= subpath
(=build/type/index.mjs=) provably does NOT reach =system/locale= (walked 120
modules, no hit), so importing those as NAMED bindings from =typebox/type=
instead of the =Type= namespace from the root may drop the whole 134 KB with
a one-line change. Verify the names exist on that subpath first — the root's
=Type= comes from =build/typebox.mjs=, a curated named-export list (which is
also where the 25 KB =Script= TS-parser hangs off =Type=).

*On an upstream PR* — the root's =export * as Type= + =export default Type=
and =export * as Locale= are all documented public API; removing any of them
BREAKS every consumer, so those PRs will not land. The only non-breaking
upstream change is adding =sideEffects: false= to package.json, which is
correct hygiene but MEASURED not to help this case. Do not open a PR on an
unproven mechanism — the locale carrier is still unidentified (nothing
outside =locale/= references =Locale=, yet all 40 are retained, so the
retention path is not understood). Prove the named-import fix first; if it
works, no upstream work is needed at all.

Cheap mitigation available WITHOUT the facade refactor: an esbuild alias in
=subsystems/typology/gestalten/bundle/svelte.js= stubbing
=build/system/locale/_locale.mjs= down to =en_US= (=_config.mjs= already
defaults to it and only =Locale.Set()= would ever need another). ~127 KB off
every client bundle, one plugin entry, zero source changes. Untested.

** Fallback

None needed — it is weight, not breakage. The drapes half of the same

* detached-process-die-on-parent-exit

** Symptom

=viva /instance/start= reports =ghost: started temp (runtime=PID kajuit=PID)= and
writes lock files at =$VIVA_SYSTEM_MOUNT/locks/<type>_<slug>.lock=. Within
milliseconds the spawned PIDs are dead. =kill -0 <pid>= → "no such process". The
intended behaviour (background runtime+kajuit running after ghost exits) does not
happen.

** Root cause hypothesis

=Deno.Command= has no native way to put a child in a new session / process group on
unix. =child.unref()= only stops the parent's event loop from waiting on the child
— it does NOT decouple the child from the controlling terminal's session. When the
parent ghost process exits (or the shell sends SIGHUP), the cascade reaches the
detached deno child because it still shares the process group / session.

macOS lacks =setsid= as a standalone binary, so the obvious unix shim
(=setsid deno task ...=) isn't available out of the box.

** Evidence

#+begin_src text
$ deno task ghost/run /instance/start
ghost: started temp (runtime=57865, kajuit=57866)
$ kill -0 57865
(eval):kill:1: kill 57865 failed: no such process
$ kill -0 57866
(eval):kill:1: kill 57866 failed: no such process
#+end_src

Lock files contain the dead pids:

#+begin_src jsonc
// $VIVA_SYSTEM_MOUNT/locks/runtime_temp.lock
{ "pid": 57865, "type": "runtime", "slug": "temp", "mount": "/Users/.../testament/temp",
  "started": "2026-05-28T..." }
#+end_src

=/instance/init= (=piped= attachment) and =/instance/run= (=inherit= attachment)
both work end-to-end — confirms the env / instance resolution chain is fine, the
problem is specifically the =detached= attachment lifecycle.

** Attempts (none kept)

1. Wrap cmd in =nohup=. Lock pid then = nohup's pid, not the deno's, so
   =/instance/stop= reads the wrong pid; also nohup writes to =nohup.out= when
   stdout is a tty, polluting cwd.
2. =nohup sh -c 'deno ... > LOG 2>&1'=. Same lock-pid problem + shell escaping
   the env vars.
3. Pipe child stdout/stderr to log files. Tangential to the death cause,
   reverted.

All reverted. Process.js is back to its original simple form.

** Why not fixed now

We don't yet know the precise cause without a controlled experiment. Options that
would actually work (in rough order of effort):

- compile a tiny =setsid=-equivalent shim and ship it via =viva/install=
- replace the =nohup= path with a =sh -c 'exec ...'= so the shell process replaces
  itself with deno (pid preserved) and explicitly call =setpgid= / detach
- write a Deno script wrapper that uses =Deno.Command= with a fresh
  =Deno.Process=-style detach (none currently exists)
- use a real process supervisor (launchd plist, systemd unit, pm2) — overkill
  for our scale

None of these are 30-minute jobs. Currently we are using =/instance/init= and
=/instance/run= for everything that needs a live instance, which both work.

** Fallback workaround

Use =/instance/run= (inherit attachment, stays attached to terminal) or
=/instance/init= (piped attachment, holds the ink wizard until user dismisses).
Both keep the children alive for the duration of the parent process — that's
what every demo this week has used.

** measured at the connoisseur's pass (m46) — the flag exists

=Deno.Command= carries =detached: true= — deno 2.9.6, =deno types= :4210: /"Whether to detach the
spawned process from the current process. This allows the spawned process to continue running after
the current process exits."/ Probe (=sleep 20=, parent exits): with the flag the child's pgid = its
own pid and it lives; without it pgid = the parent's group. =unref()= was only ever the second half.
Every option above was a shim for this one line. Owed: the 2.x release that introduced it (README
floor is 2.7+). Design that consumes it: m46 =* the connoisseur's pass=, cluster A / =start=.
** RESOLVED — m49 M1, live-proven

=start= spawns a supervisor ghost (=instance/run <target> --instance=<mount> --logged=) with
=detached: true= + =unref()=; the supervisor claims =locks/<slug>.lock= (its own pid + a token),
integrates the children, and perpetuates. Proof on =m49-smoke=: supervisor 70721 outlived =start=,
=/status= answered on its port, =instance/stop= SIGTERM'd 70721 → it took the =deno task= wrapper
and the leaf runtime with it, lock gone, port free. Quest: =m49-process-ontology-and-control-vector=.

* deno-task-cwd-rewrite

** Symptom

=Deno.cwd()= inside a handler reflects the directory of the resolved
=deno.jsonc= (repo root) — NOT the shell directory the user typed =deno task=
from. Without correction, =viva /instance/clone localhost ./here= materializes
the instance at =<repo-root>/here= instead of =<shell-cwd>/here=.

** Cause

=deno task= walks up to find the nearest =deno.jsonc=, then chdirs to that
directory before running the task. =PWD= is also overwritten to the repo root.
The original shell cwd is preserved only in =INIT_CWD=.

** Workaround (in use)

#+begin_src js
const cwd = Deno.env.get("INIT_CWD") ?? Deno.env.get("PWD") ?? Deno.cwd();
#+end_src

Applied at every handler that resolves a user-supplied relative path
(=instance/clone=, mw in =systems/ghost/mod.js=). Should be lifted into a paladin
helper (=paladin.cwd= or =ctx.cwd=) so handlers don't have to remember.

* open-orm-holds-the-deno-event-loop — WORKED AROUND (docs capture); ProcessDie gap un-go'd

** Symptom

** Real fix (un-go'd, system code)

=ProcessDie.disintegrate()= that reaches the process's datamap — requires the

** CROWN — cross-user IDOR on the harness dialogue path (BREAKS, security)

*** Symptom

Any authenticated user reads AND writes ANY other user's conversation by putting a foreign
thread id in the request body: POST =/mode/*/harness/dialogue/stream= with
={thread: <VICTIM_ID>, parts:[…]}=.

*** Root cause

Isolation rests ENTIRELY on the MikroORM =user= filter (=default:true=); =authorize()=
only sets =ctx.user=, there is NO server-side thread-ownership check anywhere. =Turn.ts:54-93=
declares no =user= filter and no user column (every sibling userspace entity has one).
=harnessed.js:27= loads the thread row USER-scoped (foreign id → null) but never gates on the
null and discards the row; :62 binds the raw id STRING; the =/dialogue= branch runs
=turn.history({thread})= (victim's convo → attacker's LLM context) and =turn.chain({thread})=
(create+flush BEFORE any LLM call → attacker+assistant turns in the victim's thread).

*** Why not fixed

m25 design decision (beef's). The fix is two moves: (1) give Turn a =user= filter through the
thread relation (={thread:{user:args.user}}=, like =Buffer.ts:36-41=) — also closes the
=entity_find= skill leak/enumeration (rank 5); (2) gate the harness on the already-loaded
=harnessed.js:27= thread row being non-null. Typology/entities are HOLY — needs go.

Needs a transactional / finally-guarded scribe. Design call in the quest.

* bundle-store-never-prunes — OPEN (design, marked at his ask during the vdex scroll session)

** Symptom

=~/.viva= holds *757* =*.svelte.mjs= artifacts. Nothing has ever been unlinked.
=stucatch/dashboard/watch/bundle/= alone carries 15 generations of the same view.

Each dev artifact is *6385 kb* (inline sourcemap — =sourcemap: prod ? false : "inline"=,
=subsystems/typology/gestalten/bundle/svelte.js:38=), and one =Vdex.svelte= compile measures
*858ms cold · 426ms warm*.

** Why it just got sharper

The dev-rebundle landing (this session, =daemon/aperture/metadata.js= + =daemon/traits/application.js=)
makes =/metadata/app= recompile whenever =paladin.is.dev=. That is once per mode per *client boot*, so a
page reload now mints a fresh artifact for every source change instead of once per daemon boot. The store
grows at the speed of the edit loop.

Second multiplier: one module at two mountings writes *byte-identical output into two stores* —
=office/vdocs/bundle/b5b4fa174fc598eb.svelte.mjs= and =office/corpo/bundle/b5b4fa174fc598eb.svelte.mjs=
are the same bytes under the same hash, because the store path is keyed by the MOUNTING
(=bundles/${manifest.type}/${manifest.slug}=) while the content is keyed by the module.

** The design he ruled out, in his own words

#+begin_quote
lets think aaabout how to do this. we want a cleanup process in the runtime. runtime goes through the
waste and cleans up anything older than xyz or something.
no that would force the runtime to regularly re-compile. stupid. hmmm.
no clue.
#+end_quote

He is right and the reason is worth keeping: the artifacts are *content-addressed*, so an age-keyed reaper
cannot tell a dead generation from the live one. The only pointer to the live artifact is
=mode.app.view.mount=, held in the runtime's memory — not on disk, not in the ledger. Sweep by age and you
either delete the artifact the running daemon is still serving (next client boot 404s until something
recompiles), or you have to ask the runtime what is live — at which point age is the wrong key entirely.

** The key that is actually available

*Supersession, not age.* =mode.app.compile()= knows both hashes: the one it is replacing and the one it just
minted. Everything else under that mode's =bundle/= is dead the instant =compile()= returns a different hash.
That is a one-=Deno.remove= prune with zero inference and no reaper process.

It only prunes going forward. The standing 757 need a separate one-shot, and that one CAN be age-keyed
because nothing is serving them.

** Unsettled — what a "go" would have to decide

- *Whose verb.* =paladin.bundler(store)= mints and serves, so it could own =prune=; but only the trait knows
  which hash is live. Runtime lifecycle is a third candidate and the one he reached for first.
- *Does prod want it.* Prod compiles once per daemon boot, so the store grows once per deploy — slow enough
  that pruning may be a dev-only concern, and deleting in prod costs the rollback.
- *Shared stores.* Two daemons under one mountpoint, or one module at two mountings, both write into paths
  that a naive prune would treat as exclusively its own.
- *The dedup.* Whether the store should be keyed by module identity rather than by mounting, which would
  make vdocs/corpo one artifact instead of two and shrink the problem before pruning it.

** Workaround meanwhile

=find ~/.viva -name "*.svelte.mjs" -delete= while every runtime is down. The next boot re-mints what is live.

31031      └ deno run -A npm:vite@6 dev                        ← holds 127.0.0.1:1794
#+end_example
