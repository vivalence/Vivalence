#+TITLE: Client Layout — T-Bone, Viket, and the Panel Engine
#+AUTHOR: Vivalence
#+DATE: 2026-04-07
#+STATUS: ACTIVE

* Intent

The HTML client today is a half-finished SvelteKit route tree with no
shared layout language. Pages render whatever they want, the modeline is
inconsistent, there's no concept of how panels relate to each other, and
the only "layout" primitive is the BSP CSS skeleton from drapes which
nothing in the new client uses.

This workpackage defines the client's layout system from the ground up.
Not as a CSS framework. As a set of named, addressable, composable
*panels* arranged into a *T-bone* — a structural skeleton — with a
draggable controller called the *viket* at the junction. Panels are
where content lives. Bones are the structural separators between panels.
The viket is the user's grip on the whole thing.

The system is designed mobile-first. The viket is the primary input
device. All layout state (panel sizes, viket position, orientation,
overlay visibility) is a serializable JSON blob that can be saved,
restored, swapped, and patched.

** Desired End State

After this work:

1. The HTML client uses a single shared layout primitive (the T-bone)
   for all pages and modes. Pages declare which panels they fill;
   layout is not their concern.
2. The viket is a real component, available everywhere, draggable,
   tap/double/triple-actionable, long-press-rotatable. Its position
   determines panel sizes.
3. Layout state is a JSON blob — viket position, orientation, panel
   visibility, overlay flags — owned by a layout engine. Components
   read it, the engine owns the writes.
4. The panels A/B/C (and D/E/F inside C) and the overlays G/H have
   fixed semantic roles documented in totems. Mode authors know which
   panel their content belongs in.
5. The terminal-first client (see =terminal-first-client.workpackage.org=)
   plugs into this layout: terminals render inside panel E, modeline in
   H or its own slot, REPL phase as one of E's render modes.
6. The whole thing is themed exclusively through dapper's six color
   sets — no raw hex values, no Tailwind utility classes for colors,
   only =var(--colors-...)=.

** Terminology

| Term         | Definition                                                                          |
|--------------+-------------------------------------------------------------------------------------|
| T-bone       | The structural skeleton: crown + spine + viket. Always visible.                     |
| Crown        | Horizontal bone perpendicular to the stem direction. Passes through viket.          |
| Spine        | The stem of the T. Extends from viket in the orientation direction.                 |
| Viket        | The square at the junction of crown and spine. Draggable. Layout controller.        |
| Junction     | Where crown and spine meet. Always equals (viket.x, viket.y).                       |
| Panel        | A content region. A, B, C are the three primary panels of the T-bone.               |
| D, E, F      | Sub-panels inside C. E is dominant. D and F are configurable rails.                 |
| G            | Right-side overlay. System tray — operational alerts, above-the-hood errors.        |
| H            | Top overlay. Dev console — logs, layout state, debug controls.                      |
| Orientation  | The direction the stem points: 0/90/180/270. Selected via long-press radial.        |
| Snap grid    | Fibonacci-ish percentages where viket position attracts during drag.                |
| Sticky hold  | After long-press, the radial menu stays open without finger contact.                |
| Layout blob  | The serializable JSON object holding all layout state.                              |
| Bone         | A structural separator between panels. Crown and spine are the two bones today.     |
| Totem        | The 4-facet documentation method (see =methods/totem:4-quadrant-component-development.md=). |

* Architecture

** The T-bone

A T-bone has 3 visible parts and 1 movable controller:

#+begin_src
┌──────────────────────────────────────────────────────────────┐
│                                                              │
│                            A                                 │  panel A  (sk1)
│                                                              │
├────╳───────────────────────────────────────────────────────┤  ← crown          (sk1)
│    │                                                         │
│    │                                                         │
│    │                                                         │
│    │                                                         │
│ B  │                          C                              │  panels B, C
│    │                       (D | E | F)                       │  (sk2 / sk3)
│    │                                                         │
│ s  │                                                         │
│ p  │                                                         │
│ i  │                                                         │
│ n  │                                                         │
│ e  │                                                         │
│    │                                                         │
│ ★  │                                                         │  ← viket
│    │                                                         │
└────┴─────────────────────────────────────────────────────────┘
#+end_src

- *Crown* and *spine* are sk1-surface divs with theme-primary-boundary
  borders. They pass through the viket position. They're always visible
  even when all panels collapse to 0.
- *Viket* is a square at the junction (size = bone thickness). Sk1 surface,
  theme-primary border, contains the vinca-viket pictogram. Sharp corners
  (no border-radius). Draggable.
- *Panels A/B/C* fill the area around the bones. Each can collapse to 0
  width or 0 height when viket reaches an edge.

** Panel inventory

| id | role family            | typical job                                                |
|----+------------------------+------------------------------------------------------------|
| A  | header / nav / status  | breadcrumbs, mode banner, lighthouse status, global controls |
| B  | left rail              | persistent secondary nav / context list (when viket low)  |
| D  | inspector / source     | tree, palette, list of things E acts on                    |
| E  | stage                  | the actual work surface — REPL, form, viewer, game         |
| F  | aux / preview          | map, preview, secondary visualisation, related             |
| G  | system tray (overlay)  | runtime alerts user should see                             |
| H  | dev console (overlay)  | logs, network, errors, layout state                        |
| ★  | anchor (viket)         | constant home + layout-state controller                    |

** Orientation

The stem can point in 4 directions:

- 0° — stem down (default T)
- 90° — stem right (⊢)
- 180° — stem up (⊥)
- 270° — stem left (⊣)

Orientation is selected via long-press on the viket, opening a radial
menu. Drag finger toward direction OR release-near-center to enter
sticky mode then click a target.

When orientation rotates, the panel layout follows but the *semantic
role* of each panel is preserved (A is always "across the cross", B is
always one side of the stem, C is always the other, D/E/F always live
inside C).

** Snap grid

During drag, viket position snaps to a Fibonacci-ish set of percentages
on each axis: =[0, 13, 21, 34, 50, 66, 79, 87, 100]=. The 3 dominant
points (0, 50, 100) are always present; the secondaries fall off to
the sides at golden-ratio-ish intervals. Snap distance is 28px (2× the
default — generous gravity).

The snap is *attractive*: viket follows the finger but pulls toward
nearest grid point when within range. No sticky lock — drag continues
freely outside snap zones.

** Layout blob

The full layout state is a flat JSON object the engine reads/writes.
Save it, ship it, JSON-patch it, hot-swap it.

#+begin_src json
{
  "viket":  { "x": 540, "y": 320, "snap": null },
  "previous": { "x": 200, "y": 240 },
  "standard": { "x": 540, "y": 320 },
  "orientation": 0,
  "panels": { "a": true, "b": true },
  "stage":  {
    "ratio": "1 3 1",
    "d": { "show": true,  "orient": "tree" },
    "e": { "phase": "repl" },
    "f": { "show": false, "orient": "map" }
  },
  "overlays": { "g": false, "h": true },
  "bones":  { "notch": true }
}
#+end_src

The engine takes this blob and emits CSS variables on the document
root. Components read those variables. There is one source of truth.

** The viket gesture state machine

#+begin_src
idle ──hold──→ longpress ──release-far──→ idle (commit orientation)
                  │
                  └──release-near──→ sticky ──tap-spoke──→ idle (commit)
                                       │  ──tap-outside──→ idle (cancel)
                                       │  ──hold-viket──→ longpress
                                       └──drag-viket──→ idle (sticky cancelled)
#+end_src

Tap actions (idle state only):
- 1 tap → jump to standard ($HOME)
- 2 taps → swap with previous (toggle back)
- 3+ taps → mark current as standard

Sticky-mode tap on viket is a no-op — user must HOLD to re-enter
drag-pick. Tap outside the radial closes it.

** Animations

The viket pictogram is a base64 PNG wrapped in SVG (no real vector
paths inside). Animation is therefore element-level CSS transforms only:

- *Idle*: static
- *Dragging*: =scaleX(1.2) scaleY(0.1)= — eye blinks closed
- *Release*: transition back to =scaleY(1)= over 180ms

A future task is to re-trace the pictogram into real vector paths so
the eye can blink independently of the petals (see =Gaps= below).

** Mobile-first

- Pointer events (unified mouse + touch + pen) — never separate
  touch/mouse handlers.
- =setPointerCapture= on pointerdown so drag continues even when finger
  leaves the viket div.
- =touch-action: none= on viket and =overflow: hidden= +
  =overscroll-behavior: none= on body to suppress browser gestures.
- =maximum-scale=1, user-scalable=no= viewport meta to prevent iOS
  double-tap zoom.
- Optional =navigator.vibrate()= on long-press start and commit.

* Dapper Skeleton Rebuild

The pincer layout exposes a deficit in dapper's color system: a global
=theme= group and a global =system= group, shared across every pane,
produce colors that are only accidentally legible on any given surface.
A red error message tuned to sit on skeleton-1 (dark) looks wrong on
skeleton-3 (light). The pincer layout, which renders multiple surfaces
simultaneously side-by-side, makes this obvious.

The fix: flatten =theme= and =system= into each skeleton. Every skeleton
becomes a self-contained universe with its own =primary/secondary/accent/
info/success/warning/danger/error= tuned specifically for that pane. A
button asks "give me my error", where "my" is the skeleton it's mounted on.

This is a sister workpackage to the pincer layout, but lives here
because the pincer prototype is the first real consumer. It blocks
Phases 2–5 above: you cannot totem the components or wire the terminal-
first client into the layout without the color system resolving how
panels of different skeletons coexist.

** Model

One skeleton = a flat populated set of roles. Twelve roles, some static,
some interactive. No nested =theme= or =system= wrappers — everything is
a top-level key inside the skeleton.

#+begin_src js
skeleton[N] = {
  // structural — 3 static values
  surface,   // the pane fill
  contrast,  // the ink on it
  boundary,  // the edge around it

  // emphasis — 3 interactive roles, 3 states each (base/hover/active)
  primary:   { base, hover, active },
  secondary: { base, hover, active },
  accent:    { base, hover, active },

  // semantic — 4 interactive roles, 3 states each (base/hover/active)
  info:      { base, hover, active },
  success:   { base, hover, active },
  warning:   { base, hover, active },
  danger:    { base, hover, active },

  // error is a box — fill + ink + edge, static (no interaction)
  error: {
    surface,
    contrast,
    boundary,
  },

  // tokenspaces (not colors)
  font: { heading, body, code },
}
#+end_src

Counts:
- Structural: 3 values
- Emphasis: 3 × 3 = 9 values
- Semantic (interactive): 4 × 3 = 12 values
- Error (box): 3 values
- *Total: 27 scalars per skeleton*
- × 5 skeletons (0/1/2/3/4) = *135 values total*

No =disabled= role at either level. Disabled states are rendered at the
component level via opacity + =pointer-events: none=, not via a dedicated
color.

** Statespace derivation

Each role's statespace was chosen by looking at actual usage, not by
multiplying axes:

| Role      | Why                                                                      | States |
|-----------+--------------------------------------------------------------------------+--------|
| surface   | Pane backgrounds are not clickable. They do not hover.                   | 1      |
| contrast  | Plain text does not hover. Clickable text is =primary=, not =contrast=.  | 1      |
| boundary  | Pane edges are structural, never change. Focused inputs use =primary=.   | 1      |
| primary   | The most interactive color in the system. Buttons, links, active tabs.  | 3      |
| secondary | Secondary buttons, secondary tabs, less-prominent links.                | 3      |
| accent    | Rare but fully interactive when present.                                | 3      |
| info      | Info banners/icons can be clickable drill-downs.                        | 3      |
| success   | Success states may include retry/undo actions on the colored surface.   | 3      |
| warning   | Warning badges with dismiss actions.                                    | 3      |
| danger    | Delete/discard/force-push buttons. Fully interactive.                   | 3      |
| error     | Error is aftermath, not trigger. A displayed box: surface + ink + edge. | 3 (box)|

** Root color spaces

Ten root palettes, each a 12-step ramp: =50, 100, 200, 300, 400, 500, 600,
700, 800, 850, 900, 950=. Skeletons pull from these; they never define
raw hex.

| Root   | Role in the system                       | Identity                               |
|--------+------------------------------------------+----------------------------------------|
| IRON   | backbone — grays, surfaces, chrome        | cool blue-gray, nordsee concrete       |
| DEEP   | skeleton 0 background                     | warm dark blue, nordic winter sky      |
| GOLD   | skeleton 0 contrast (pale lettering)      | muted iron-gold, worn gilt / antique brass |
| AQUA   | brand color, =primary= on most skeletons  | =#1EBCB5= anchor, teal, kept from current |
| INDIGO | secondary emphasis + =info=               | pale nordic blue                       |
| MOSS   | =success=                                 | forest lichen, not neon lime           |
| AMBER  | =warning=                                 | warm honey                             |
| RUST   | =danger= + =error=                        | iron oxide, earthy                     |
| SLATE  | reserved (disabled-looking if needed)     | cold dead iron                         |
| PINK   | =accent=                                  | loud celebratory pop                   |

Vibe anchor: dark scandinavian, nordsee meets concrete. All five brand
descriptors at once — terminal/scholarly/neon/clinical/organic. One
shared color space; skeletons differ gradially and contrastively within it.

** CSS variable naming convention

*Explicit, always.* No shorthand. Every scalar gets a fully-qualified name
including the =base= state when it has one.

#+begin_example
--colors-skeleton-1-surface
--colors-skeleton-1-contrast
--colors-skeleton-1-boundary

--colors-skeleton-1-primary-base
--colors-skeleton-1-primary-hover
--colors-skeleton-1-primary-active

--colors-skeleton-1-secondary-base
--colors-skeleton-1-secondary-hover
--colors-skeleton-1-secondary-active

--colors-skeleton-1-danger-base
--colors-skeleton-1-danger-hover
--colors-skeleton-1-danger-active

--colors-skeleton-1-error-surface
--colors-skeleton-1-error-contrast
--colors-skeleton-1-error-boundary
#+end_example

Rationale: grep-ability and predictability. =var(--colors-skeleton-1-primary)=
is ambiguous — is it the base or is it the whole role? Always spelling
=-base= removes the question and makes every consumer identical in shape.

** Value pickup — factory / middleware architecture

Skeletons do not hand-pick 27 hex values. They hand-pick ~12 anchors
(one per role) and a small factory function fans out the rest via a
middleware chain.

#+begin_src js
// primitive: pick a value from a ramp with optional transforms
export const pick = (ramp, anchor, ...middlewares) =>
  middlewares.reduce((value, mw) => mw(value, ramp, anchor), ramp[anchor]);

// fan-out: one anchor → {base, hover, active}
export const interactive = (ramp, anchor) => ({
  base:   ramp[anchor],
  hover:  ramp[anchor - 100],
  active: ramp[anchor + 100],
});

// fan-out: one ramp → {surface, contrast, boundary}
export const box = (ramp, anchors = [800, 100, 300]) => ({
  surface:  ramp[anchors[0]],
  contrast: ramp[anchors[1]],
  boundary: ramp[anchors[2]],
});

// the skeleton factory — composable, middleware-friendly
export const skeleton = (config) => {
  const { surface, contrast, boundary, roles, error, font } = config;
  const result = { surface, contrast, boundary, font };
  for (const [name, { ramp, anchor }] of Object.entries(roles)) {
    result[name] = interactive(ramp, anchor);
  }
  result.error = box(error.ramp, error.anchors);
  return result;
};
#+end_src

Each skeleton definition becomes a small config:

#+begin_src js
skeletons[1] = skeleton({
  surface:  IRON[850],
  contrast: IRON[100],
  boundary: AQUA[400],
  roles: {
    primary:   { ramp: AQUA,   anchor: 300 },
    secondary: { ramp: INDIGO, anchor: 300 },
    accent:    { ramp: PINK,   anchor: 300 },
    info:      { ramp: INDIGO, anchor: 300 },
    success:   { ramp: MOSS,   anchor: 300 },
    warning:   { ramp: AMBER,  anchor: 300 },
    danger:    { ramp: RUST,   anchor: 300 },
  },
  error: { ramp: RUST, anchors: [800, 100, 300] },
  font: { heading: "sans-heading", body: "sans-text", code: "code" },
});
#+end_src

~60 hand-picked numbers total parameterize the whole 5-skeleton system.
The middleware shape (=pick(...middlewares)=) leaves room for future
transforms — gamma correction, contrast boosting, per-skeleton tint — without
rewriting consumers.

* Decisions

| Decision | Choice | Rationale |
|----------+--------+-----------|
| Layout primitive name | T-bone | Visual metaphor matches the structure (crown + stem). "Layout" was too generic. |
| Junction controller name | Viket | Already exists as a brand element. Reuses the pictogram. The viket has always been an anchor. |
| Bones as DOM siblings | Yes | Addressable, animatable, themable independently. Borders-on-panels was rejected because you can't restyle a single bone segment. |
| Bones color | sk1-surface + theme-primary-boundary | Modeline material from screenshot reference. Not sk4 (too dark, too distinct). |
| Viket shape | Square (no radius) | User explicitly chose this. Modeline button feel. |
| Viket size = bone thickness | Yes | The junction = the viket. Anything else creates a gap. |
| Panel collapse to 0 | Yes | User explicitly required. Allows full-screen single-panel modes. |
| Snap grid | Fibonacci-ish percentages | Discussed earlier. Combines dominant common positions (0/50/100) with golden-ratio-ish secondaries. |
| Snap distance | 28px (2× default) | User explicitly doubled it. |
| Sticky hold | Yes | User wanted post-release radial. Long-press → release → menu stays. |
| H as panel not float | Yes | User explicitly moved it from a floating box to a 50px top bar. |
| G as overlay not panel | Yes | G slides in from right, doesn't claim layout space permanently. Different from H. |
| Pictogram format | SVG-wrapped PNG (for now) | Real vector vectorization is Phase 6. Element-level animation is sufficient for current needs. |
| Layout state shape | Flat JSON blob | Serializable, JSON-patchable, transportable, easy to version. |
| Token namespace | =--colors-...= raw form | User stated preference. No Tailwind utility classes for colors. |
| Mobile-first | Pointer events + touch-action: none | One unified gesture handler set; works on touch + mouse + pen. |
| Color model | Flat scoped skeletons | Global =theme= + =system= groups produce accidentally-legible colors. Per-skeleton populated sets fix legibility and enable context-aware components. |
| Skeleton shape | 27 scalars, flat, no disabled role | Role-by-role statespace analysis. Structural roles static (1). Emphasis + semantic interactive (3: base/hover/active). =error= as a box triplet. Disabled handled via opacity at component level. |
| CSS var naming | Explicit, always | =--colors-skeleton-1-primary-base= never shorthand. Grep-able, predictable, every consumer identical in shape. |
| Value pickup | Factory + middleware | Each skeleton hand-picks ~12 anchors; =skeleton({...})= factory + =interactive= / =box= helpers fan out the rest. ~60 numbers parameterize the whole 5-skeleton system. Middleware chain leaves room for future transforms. |
| Root palette count | 10 (IRON/DEEP/GOLD/AQUA/INDIGO/MOSS/AMBER/RUST/SLATE/PINK) | 12-step ramps each. Shared color space; skeletons differ gradially and contrastively within it. Vibe: dark scandinavian, nordsee meets concrete. |

* Gaps

- Panel naming: A/B/C/D/E/F/G/H are placeholder letters. Need real
  names eventually (mode-bar, left-rail, stage, inspector, etc.).
  Letters are fine for prototyping, must be replaced before this is
  used in production.
- Per-route layout state vs global: localStorage one blob for the whole
  app, or per-route? Per-route is more natural for users (different
  layout for repl vs game vs settings) but more complex to implement
  and confusing on first visit.
- D/E/F orientation modes (tree, icons, list, map, etc.) are not yet
  implemented or even fully enumerated. Currently D/E/F just render as
  flex children of C with margin and border-radius.
- Notch behavior: the original design said the crown notch above B
  could collapse when viket left-aligns. This isn't implemented and
  may be deferred indefinitely if it's not needed.
- The viket pictogram blink affects the whole image (scaleX +
  scaleY). To blink only the eye, the SVG needs to be re-traced
  (Phase 6).
- Keyboard controls: there's no keyboard interface to the viket yet.
  Should there be? If the layout is the OS shell, keyboard shortcuts
  are mandatory eventually.
- Multi-touch: pinch to zoom panels, two-finger rotate orientation?
  Not designed.
- The fix that the viket shrinks proportionally with bone thickness:
  if you change =BONE_THICKNESS=, the viket follows. But the pictogram
  size is hard-coded at 36px. Should it be a fraction of viket size?
  Probably yes.
- The H bar font size (9px) is very small. Works on desktop, may be
  unreadable on mobile. Needs responsive sizing.
- G overlay close button is inside the G overlay header. If G is
  closed, you re-open it from H. If H is closed (later when hide is
  added), there's no way to re-open H. Need a permanent "show H"
  affordance — perhaps part of the viket's tap menu.
- The state dump in H is large and scrolls. Should it be in a
  collapsible section, or moved to a separate dev panel?
- Animation for orientation change: currently snapping. Should be a
  smooth tween from old layout to new layout. Looks janky right now.
